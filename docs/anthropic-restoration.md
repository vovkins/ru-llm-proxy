# Восстановление масок в Anthropic Messages

`RuPIIGuardrail` поддерживает нативные ответы `/v1/messages`: восстанавливает
`content[].text` и JSON-значения вложенных `tool_use.input` / `server_tool_use.input`.
Используется mapping только текущего запроса. Имена инструментов, идентификаторы,
ключи схемы и подписанные thinking-блоки не переписываются.

Входящий `tool_use.input` в истории также анализируется. Для Analyzer используется
JSON-представление аргументов, а в запросе к провайдеру сохраняется объект, не строка.
Это позволяет повторно скрывать восстановленные исходные значения в следующем ходе
агента. Пустые объекты не вызывают отдельный анализ.

В streaming поддерживаются нативные event-объекты и SSE в bytes/str. Обработчик
сохраняет отдельное состояние каждого content block, учитывает разрывы масок между
дельтами, экранирование JSON и границы UTF-8 транспортных фрагментов. Остаток текста
выводится до `content_block_stop`, а не после него. Обрыв/отмена не создаёт успешный
`message_stop`; mapping удаляется через существующий shielded cleanup.
SSE-событие ограничено существующим MAX_SSE_EVENT_BYTES, JSON-аргументы одного
потокового инструмента — 8 MiB. Некорректный или незавершённый JSON останавливает
обработку до успешного завершения блока.

При `dictionary_collision_resolution: reject` (значение по умолчанию) запрос,
где одновременно присутствуют исходное слово и его словарный псевдоним,
блокируется при fail_closed. Вместо внутреннего RuntimeError/500 возвращается
структурированная ошибка 422 `dictionary_substitution_ambiguous`; сами исходные
слова и псевдонимы в сообщение ошибки не включаются.

Отдельный режим [`unique_aliases`](dictionary-collision-resolution.md) позволяет
продолжить такой запрос: текущий оригинал получает новое свободное обозначение,
а существующий псевдоним сохраняется как входные данные. Режим нужно включить явно.
Он не угадывает прежние соответствия и не ремонтирует уже записанные файлы.

Исправление не меняет NER-предсказания и не исключает код/пути из защиты.
Ложная маска вроде `<ORGANIZATION_1>PWA` восстанавливается обратно по mapping,
но само ложное обнаружение остаётся отдельной задачей качества.
Настройки и реализация prompt caching не изменяются.

## Сохранность подстановок во всём запросе

Литеральные плейсхолдеры во входящих полях и схемах резервируются: новый
`<PERSON_n>` не совпадает с уже написанным `<PERSON_n>`. Это не доверенная
маска и не исключение из распознавания. Словарная неоднозначность проверяется
до изменения всех полей, включая случай, когда оригинал и псевдоним находятся
в разных сообщениях. Для разных регистров исходного слова используются разные
обратимые псевдонимы; исходное написание сохраняется.

JSON-ключи данных, действительно замаскированные в этом запросе, также
восстанавливаются. Это отмечается локальным `json_keys` в mapping; ключи без
такой отметки, определения инструментов и подписанные блоки не переписываются.
Повторение ключа после восстановления отклоняется: 502 для полного ответа,
ошибка без успешного завершения вызова для потока. Молчаливое затирание данных
не допускается. Правило общее для Chat, Responses и Anthropic tool arguments.

Для mapping с ключами данных используется версия 4; старые версии 1–3 читаются
как раньше, обычные mappings сохраняют прежний формат. Перед развёртыванием
нужно обновить все gateway-процессы, читающие общий mapping/Responses state:
старый код не умеет читать v4 и безопасно отклонит такое состояние.

## Проверка настоящего HTTP-маршрута

Локальный стенд проверяет зарегистрированный LiteLLM 1.98.0 `/v1/messages`,
авторизацию master key, Router, преобразования форматов, callbacks и middleware
через HTTPX ASGITransport. Подменены только сеть провайдера/Analyzer и Redis.
Сетевые соединения запрещены; Docker, корпоративная DLP и реальный провайдер
не используются. Стенд запускается отдельно и не меняет активную конфигурацию.

При сквозной проверке добавлены три исправления совместимости:

- В промежуточном Responses→Messages преобразовании внутренние generic-объекты
  SDK нормализуются через публичный deployment callback. Сериализованное
  содержимое не меняется, обратная подстановка на этом этапе не выполняется.
  Остальные маршруты не затрагиваются.
- Для Chat→Messages streaming первый инструмент продолжает передаваться сразу,
  а фрагменты остальных собираются по индексу и выдаются раздельно перед
  настоящим finish. Это предотвращает склейку JSON параллельных инструментов
  адаптером SDK. Вторичные аргументы ограничены 8 MiB на инструмент и 16 MiB
  суммарно; максимум 128 инструментов. Чужие IDs/имена не угадываются, отказ
  или неполное завершение не преобразуется в успешный набор вызовов.
- Request-owned cleanup в существующем middleware освобождает mapping и HTTP
  streams даже тогда, когда error callback получает копию запроса без внутренних
  metadata. Успешная post-call очистка снимает fallback; анализ-кэш не удаляется.

Неверный непустой JSON аргументов отклоняется до того, как SDK сможет заменить его
пустым объектом. В потоковом ответе повреждение/обрыв даёт error и не даёт
успешный message_stop. Проверка native протокола выполняется и без PII mapping.
Обычные тексты без масок сохраняются.

Для исходного `/v1/messages` принудительный выбор конкретного инструмента
в Responses→Chat streaming нормализуется: остаётся ровно выбранное определение
function, а `tool_choice` становится `required`. Провайдер обязан вызвать именно
этот инструмент; свободный выбор `auto` не используется. Это обходит ошибку
SDK, создающего Responses-снимок с несовместимой Chat-формой named tool choice.
Неизвестное или неоднозначное имя отклоняется 400 до запроса провайдеру.
История вызовов, схема выбранной функции и остальные параметры сохраняются.

Штатные Messages-адаптеры также теряют `disable_parallel_tool_use`. Для OpenAI
Chat/Responses маршрутов этот boolean считывается из исходного HTTP-запроса
прокси и передаётся как противоположное `parallel_tool_calls`. Исходный body
при этом не пересылается; другие типы значений не приводятся к bool.

Нормализация named selection касается только исходного Messages streaming
через Responses→Chat. Прямой `/v1/responses` с таким bridge по-прежнему получает
400; нативный Responses backend, прямой Chat и nonstream named selection
сохраняют прежнее представление. Ограничение previous_response_id в Chat bridge
сохранено. Ни маршрутизация, ни prompt caching не переключаются исправлением.
