# Развёртывание Docker Compose

Параметры состава, топологии и политики независимы:

| Параметр | Выбор |
| --- | --- |
| `STACK` | `litellm-presidio` или `litellm-presidio-codex-lb`; расширенный состав включает базовый |
| `TOPOLOGY` | `functional` по умолчанию; `production` для нескольких экземпляров на одном сервере |
| `PII_GUARDRAIL_MODE` | `MASK`/`mask` либо `BLOCK`/`block` |
| `ENV_FILE` | Файл секретов и настроек; по умолчанию `.env` |
| `TOPOLOGY_ENV` | Необязательный файл дополнительных количеств и ресурсов production |

Нужны Python 3.9+, Docker Compose 2.24+ с поддержкой `!reset`, GNU Make.
Образы и их версии одинаковы для обеих топологий; патчей платформ нет.
Обе топологии используют единственный комплект Tiny2/Triton на CPU.
Селекторов модели и GPU-профилей нет. При переходе удалите прежние параметры
по [инструкции миграции](configuration.md#переход-со-старой-конфигурации).

## Первичный запуск

Для базового состава:

```bash
make setup STACK=litellm-presidio PII_GUARDRAIL_MODE=MASK
# Заполните два ключа Z.AI в .env.
make build
make up STACK=litellm-presidio TOPOLOGY=functional
make health STACK=litellm-presidio TOPOLOGY=functional
```

Для расширенного состава сначала подготовьте `.env` из примера и соберите
образы, затем выполните штатную [настройку codex-lb](codex-lb.md).
Параметры `TOPOLOGY` и `ENV_FILE` должны быть одинаковыми у `setup` и `up`.
Выполнять два отдельных `setup` не нужно.

```bash
make build
make setup STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=BLOCK
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`build` собирает образы, `setup` готовит секреты и первичную настройку,
`up` запускает без сборки. **На время развёртывания оператор исключает реальный
пользовательский трафик внешними средствами.** Nginx запускается первым с полной
конфигурацией; двухфазного переключения и автоматического закрытия входа нет.
После `nginx -t` проверяются каждый Triton, внутренний маршрут Nginx к модели,
прогретые Analyzer и затем LiteLLM. Готовность реплики не заменяет готовность
маршрута: Docker DNS может обновиться чуть позже запуска модели.
Холодные экземпляры запускаются последовательно, чтобы ограничить пик памяти.
При ошибке команда завершается, Nginx остаётся доступным, часть маршрутов может
временно отвечать ошибкой. Изучите журналы и повторите `up`.
При защёлкнутой ошибке NER нужен `restart`, а не повторный запуск того же процесса.
При смене политики или топологии старые LiteLLM также останавливаются до
записи режима: в functional это закрывает прямой вход на порт `4000`.

## Двухузловые роли: местные пулы

Двухузловой режим разделяет роли `primary`/`compute` через штатный Compose
`extends`. Общие определения NER лежат в `docker-compose.ner.yml`; это не
самостоятельный файл запуска. Обычные команды выше без `NODE_ROLE` не меняются.

Команды управляют выбранным локальным узлом, не запускают второй сервер. С `NODE_ROLE` команда
`build` готовит только образы локального состава, без роли по-прежнему оба
состава и тестовые образы. Для сборки не нужны `NODE_CONFIG`, секреты, подписки
или доступный B. Тестовые образы готовят существующие тестовые команды.

Ниже последовательность для **нового отдельного проекта compute**, не команда
миграции работающего стенда. Сначала подготовьте локальную копию JSON-примера
с адресами своего контура. Для корпоративной сборки заранее создайте
`ENV_FILE` из `.env.compute.example` и настройте прокси, зеркала, доступ к
закреплённым артефактам и локальные CA по [инструкции](air-gapped.md#compute-в-корпоративной-сети).
Без файла `build` возьмёт значения из примера, а не настройки узла A.
Используйте одинаковый контекст во всех командах:

```bash
export STACK=litellm-presidio-codex-lb TOPOLOGY=production NODE_ROLE=compute
export ENV_FILE=.env.compute NODE_CONFIG=deploy/nodes.local.json
export COMPOSE_PROJECT_NAME=ru-llm-proxy-compute
unset PII_GUARDRAIL_MODE
make build
make setup
make up
make health
make metrics
# Далее: make logs, make restart или make down с тем же контекстом.
```

`setup` compute создаёт минимальный файл с правами 0600, не генерирует секреты
A и при повторе сохраняет значения/права существующего файла. MASK/BLOCK на
compute не задают ни в оболочке, ни в файле: политика работает в LiteLLM primary.
`up` запускает Nginx, затем последовательно Triton и Analyzer, без сборки;
`restart` пересоздаёт компоненты. `health/metrics` относятся ко всем местным
репликам и закреплённому комплекту NER, не ко второму серверу.
`logs/down` используют установленный bundle без исходного `NODE_CONFIG` и
доступного B. `clean` требует подтверждения и действует
только на локальный проект; `STACK=all` с ролью запрещён. Клиентские проверки,
управление LiteLLM, `monitor-smoke` и `ner-evaluate` на compute не поддерживаются.

Для нового primary используется `NODE_ROLE=primary` и собственный `ENV_FILE`;
первичная настройка codex-lb остаётся прежней. Для уже работающего A
сохраните существующие `ENV_FILE` и имя проекта: другое имя создаёт другие тома.
Несовпадение ролей уже созданного проекта отклоняется до мутаций, включая
попытку управлять ролевым проектом без `NODE_ROLE`.

Compute содержит только Nginx/Analyzer/Triton, без БД, подписок и админок.
Единственный опубликованный вход B привязан к фиксированному IPv4/порту из
JSON. Он разрешает только health (GET/HEAD) и analyze (POST) с адресов A из
`source_cidrs`; поддельные `X-Forwarded-For`/`X-Real-IP` не дают доступа.
HEAD health передаётся Analyzer как GET, клиент получает только заголовки.
Не открывайте этот порт вне доверенного контура. Учитывайте Docker NAT:
проверьте фактический источник на целевых Linux-хостах, не расширяйте allowlist
до всей Docker-подсети при подмене адреса посредником. Одного UFW недостаточно
для контроля опубликованных Docker-портов.

Primary балансирует между местным и удалённым пулами. Местный вход
`127.0.0.1:5002` находится в том же Nginx A и не публикуется; каждый Analyzer
использует только Triton своего узла. Сам JSON описан
в [справочнике](configuration.md#роли-двух-узлов-параметры).

`setup/up/restart` создают версию конфигурации в `deploy/generated/`, проверяют
`nginx -t`, затем подключают каталог read-only. Изменение JSON/шаблона создаёт
новую версию и пересоздаёт Nginx; прежние файлы не перезаписываются. Ошибка
проверки сохраняет предыдущий bundle. Не удаляйте используемые поколения;
каталог исключён из Git и сборки, секретов в нём нет. Адреса не встраиваются
в образы. Перед применением оператор изолирует реальный клиентский трафик.

Только центральный вход A может повторить один анализ: максимум две попытки
по сетевой ошибке, transport timeout или HTTP 502. Полученные HTTP 503/429/504
не повторяются. Местные Nginx и маршрут Triton повторов не делают. Потеря уже
вычисленного ответа может вызвать повторный анализ целиком; exactly-once
не гарантируется. Общий бюджет guardrail не обновляется при переключении,
перегрузка первого пула всё ещё может дать 503 при здоровом втором.

Health имеет короткие ожидания 5 с; POST сохраняет 1500 с. Центральный пул
не хранит свободные HTTP-соединения. TCP-пробы включены только в Nginx A:
10/5/3 в его сетевом пространстве, без изменения хоста. Это не SLA обнаружения
отказа и не ограничение длительности здорового анализа.

**Не запускайте эти файлы напрямую через Docker Compose:** используйте Make
с проверкой локальной роли. Setup/up/restart требуют корректный JSON, но не
проверяют доступность второго сервера. Не меняйте имя существующего проекта и
не пытайтесь переключить его роль через `restart`: сначала выполните переход
по инструкции ниже.

### Подключение B к работающему production

Это смена топологии **без смены выпуска**. Если A ещё на `v0.6.2`, сначала
[обновите и проверьте его на одном узле](#обновление-с-v062-до-v070).

Переход меняет состав контейнеров A и требует окна обслуживания. До окна:

1. На обоих узлах подготовьте образы одного выпуска и локальные копии
   [JSON адресов](../deploy/nodes.example.json). Закрепите текущий выпуск и
   образы A, его `STACK`, имя проекта, `ENV_FILE` и, если задан, `TOPOLOGY_ENV`.
   Имя сверяйте с меткой `com.docker.compose.project` уже запущенных контейнеров.
   На A, пока запущен обычный проект, при необходимости выполняйте `make build`
   **без `NODE_ROLE` и `NODE_CONFIG`**. Сборка с ролью primary в том же проекте
   будет отклонена. Если A только что обновлён на тот же выпуск, пересборка не нужна.
2. На A сделайте проверяемую резервную копию PostgreSQL LiteLLM и, для
   расширенного состава, PostgreSQL и каталога данных codex-lb. Сохраните
   конфигурацию, секреты и сертификаты в защищённом месте. Проверьте, что
   архивы БД восстанавливаются в отдельные базы. Не меняйте ключи и пароли
   в ходе смены роли.
3. На B выполните `build/setup/up/health` с контекстом compute из примера выше.
   Убедитесь, что опубликован только нужный внутренний IPv4/порт, модели
   A/B совпадают, а ACL использует реальный адрес A после Docker NAT. Проба
   с отличимым источником должна получить отказ от ACL, а не просто не
   достичь порта. На B не переносите ключи, подписки или базы A.

В окне обслуживания прекратите приём нового трафика на A и дождитесь завершения
текущих запросов, включая SSE. Выполните команды из каталога выпуска с
подставленными значениями **уже работающего проекта** (пример для расширенного
состава, `TOPOLOGY_ENV` оставьте как до перехода):

```bash
export STACK=litellm-presidio-codex-lb TOPOLOGY=production
export COMPOSE_PROJECT_NAME=ru-llm-proxy ENV_FILE=.env
unset NODE_ROLE NODE_CONFIG
make down

export NODE_ROLE=primary NODE_CONFIG=deploy/nodes.local.json
make up
make health
```

Используйте обычный `make down`, **не** `down -v`, `clean` или удаление томов.
Ожидаются те же постоянные тома проекта: `pgdata`, а в расширенном составе также
`codex-lb-pgdata` и `codex-lb-data`. Bootstrap codex-lb не повторяйте.

Перед открытием трафика проверьте готовность всех местных реплик на обоих
узлах и фактический маршрут A→B: одного `make health` на A недостаточно.
С A проверьте HTTP-доступ до адреса `compute.analyzer_url` из `NODE_CONFIG`,
подставив его вместо примера:

```bash
curl --noproxy '*' -fsSI --max-time 5 http://192.0.2.20:5001/api/v1/health
```

Ожидается 200. С неразрешённого, но сетево доступного источника тот же маршрут
должен вернуть 403. Сверьте фактический адрес клиента в журнале B; проверка с
хоста A не заменяет сквозную пробу из контейнерного маршрута.
Проведите синтетическую сквозную пробу с ранее выданным виртуальным ключом
для Chat Completions и Responses, включая SSE. Подтвердите восстановление
ответа, рост счётчика анализа B и сохранность БД и настроек. При неожиданном
адресе источника, открытом лишнем порте, другом томе или сбое проб не
открывайте пользовательский трафик.

Штатный Compose не закрепляет за Redis постоянный именованный том. Кэш
анализа и состояние Responses могут потеряться при пересоздании. В репетиции
прежний `previous_response_id` после перехода давал HTTP 409 без отправки
провайдеру; клиенту нужно начать запрос заново с полной историей без старой
ссылки. Действующие SSE не переживают остановку, поэтому сначала нужен дренаж.

### Возврат к одному узлу

Снова остановите приём трафика и дождитесь дренажа. На A оставьте прежние
`STACK`, `TOPOLOGY`, имя проекта и файлы. Остановите его **с установленной
ролью primary**, затем уберите роль и адресный файл:

```bash
make down
unset NODE_ROLE NODE_CONFIG
make up
make health
```

Не удаляйте тома. Проверьте прежний ключ, БД и сквозной запрос без B; затем
на B выполните `make down` с его прежним compute-контекстом. Если B недоступен,
A может работать с меньшей ёмкостью, но не обязан выдерживать всю прежнюю
нагрузку. Потеря A останавливает сервис.

Этот откат возвращает **топологию на том же выпуске**. При откате версии
сначала подтвердите совместимость образов с текущими схемами БД. Старые образы
не откатывают схемы. При несовместимости восстановите проверенную резервную
копию в отдельном контуре и согласуйте перенос данных, записанных после неё;
не перезаписывайте работающую БД вслепую.
Для возврата на прежний релиз следуйте [отдельной процедуре](#откат-версии-на-v062).

[Межхостовой NAT и ACL](https://github.com/vovkins/ru-llm-proxy/issues/116#issuecomment-6749160998)
проверены на двух Linux-хостах. В
[нагрузочных сериях](https://github.com/vovkins/ru-llm-proxy/issues/116#issuecomment-6777392626)
прошли профили с 24 Analyzer / 12 Triton на каждом узле. Это не максимальная
плотность и не SLA с реальным провайдером.
Предельные большие входы, ёмкость A при потере B под нагрузкой и профиль
400 пользователей остаются за рамками приёмки.

### Готовность и диагностика двух узлов

Выполняйте `make health` и `make metrics` **на каждом сервере** с контекстом его
локального проекта (STACK/TOPOLOGY/NODE_ROLE/ENV_FILE/TOPOLOGY_ENV).
Команды используют установленный bundle, исходный NODE_CONFIG им не требуется.
Они не перезапускают сервисы и не обращаются к удалённому Docker API.

`health` показывает `scope=local`, роль/проект, `configured_bundle`, ожидаемое,
найденное и готовое количество каждого сервиса, причины по репликам и местные
маршруты. Для ролевого Nginx проверяется совпадение метки установленного bundle.
Analyzer и каждый Triton должны соответствовать доверенному комплекту сборки;
`trusted_model` показывает проверяемые model_id/revision/onnx_sha256 для сравнения A/B.

| Статус | Значение | Результат команды |
| --- | --- | --- |
| `full` | Весь проверяемый местный состав и маршруты готовы | Успех |
| `degraded` | Часть вычислительного пула недоступна, оставшаяся ёмкость и маршруты подтверждены | Ненулевой код |
| `unavailable` | Ёмкость/маршрут не подтверждены либо отказал обязательный компонент | Ненулевой код |

`remote_node=not_checked` означает, что второй сервер этой командой не проверен.
Исправный A проходит свою проверку и запускается при недоступном B. Полную
двухузловую готовность подтверждают два местных отчёта и доступный с A маршрут
B; один HTTP 200 от балансировщика не проверяет все его реплики. `degraded`
не обещает успех каждого запроса и не исключает неисправные реплики из маршрута.
Насыщенная очередь сама по себе не делает прогретую модель неисправной.
Проверки имеют конечные таймауты; `health` с ожиданием повторяет целые обходы,
а не ограничивает каждый обход оставшимся временем ожидания.

`metrics` собирает доступные реплики даже при неуспешном `health`: остановленные,
недоступные и отсутствующие экземпляры отмечаются, остальные результаты
сохраняются. Неполный сбор возвращает ненулевой код; нездоровый, но доступный
`/metrics` всё равно опрашивается. Заголовки разделяют сервисы и экземпляры.
Это диагностический снимок, **не единый Prometheus endpoint**: имена/метки
штатных метрик не переписываются, одинаковые серии нельзя склеивать или дважды
суммировать. Для внешнего Prometheus нужны отдельные доступные ему targets
реплик с различимыми `node`/`instance`; новые порты и collector здесь не создаются.
Балансируемый `/metrics` не представляет весь пул. После пересоздания контейнера
счётчики могут сброситься; анализируйте прирост/скорость для того же экземпляра.

| Где искать причину | Существующие сигналы |
| --- | --- |
| Очередь Analyzer | `ru_presidio_analyzer_capacity_active`, `capacity_waiting`, `capacity_rejections_total{reason}`, `queue_wait_seconds` |
| Анализ и NER | `ru_presidio_analyzer_latency_seconds`, `phase_duration_seconds`, `ner_failures_total{phase,failure_class}`, `ru_presidio_ner_ready` |
| Очередь/исполнение Triton | `nv_inference_pending_request_count`, `nv_inference_queue_duration_us`, `nv_inference_exec_count`, `nv_inference_request_failure` |
| Бюджет/кэш guardrail | `ru_pii_guardrail_preprocessing_duration_seconds`, `analyzer_latency_seconds`, `analysis_cache_requests_total`, `redis_latency_seconds` |
| Сеть между узлами | Журнал Nginx: `request_id`, `field`, `upstream`, `upstream_status`, `time`; до двух центральных попыток |
| Внешний провайдер | Ошибка/длительность LiteLLM и codex-lb после успешной предобработки; очередь Analyzer сама по себе её не доказывает |

В таблице сокращённые имена продолжают префикс первой метрики своей строки.
Метрики Triton с `_us` измеряются в микросекундах, наши `_seconds` — в секундах.
`request_id` служит корреляции журналов, не меткой Prometheus. Тексты, исходные
значения, Authorization и ключи в диагностические сводки не включаются.

## Режим обработки

Приоритет: **параметр make > окружение оболочки > ENV_FILE > mask**.
Неизвестное или пустое значение отклоняется до изменения файлов и контейнеров.
Явный параметр `PII_GUARDRAIL_MODE` в `setup`, `up` или `restart` атомарно
сохраняется в `ENV_FILE` в нижнем регистре; остальные записи и права файла
сохраняются. Значение из окружения применяется, но не записывается в файл.

```bash
make restart STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=MASK
```

Все экземпляры LiteLLM получают одинаковую политику. Повторный `setup` на
работающей установке допускается только с её текущей топологией и политикой;
для изменения используйте `restart`, а не первичную настройку.
Предварительная и финальная проверки, словарные подстановки и другие защитные
политики сохраняют собственные настройки.

## Стандартные профили

Оба профиля применяются к любому `STACK`; политики MASK/BLOCK не меняют ресурсы.

| Параметр | functional | production |
|---|---:|---:|
| LiteLLM / Analyzer / Triton | 1 / 1 / 1 | 2 / 24 / 12 |
| Процессов в каждом Analyzer | 1 | 1 |
| Активных анализов / ожидающих на процесс | 2 / 32 | 2 / 32 |
| Ожидание места в очереди | 30 с | 45 с |
| Исполнений модели в каждом Triton | 2 | 2 |
| Окон в одном пакете NER | 4 | 4 |

Functional не навязывает жёсткие лимиты памяти и CPU. Профиль production ниже —
измеренный профиль A для сервера 32 CPU / 64 GB RAM с намеренной переподпиской.
Основание: [длительная нагрузка](research/production-steady-cache-corrected.md) и
[приёмка](research/production-acceptance.md). Это не абсолютный оптимум на другом
оборудовании и не гарантия ёмкости 400 одновременно активных пользователей.
[Проверка штатной поставки](research/production-defaults.md) выполнена без
переопределений ресурсов и эксплуатационных параметров.

## Ресурсы production

| Компонент | Экземпляров | CPU / память на экземпляр |
| --- | ---: | --- |
| LiteLLM | 2 | 2 / 4 GiB |
| Analyzer | 24 | 1 / 2 GiB |
| Triton | 12 | 2 / 4 GiB |
| Redis | 1 | 1 / 16 GiB |
| PostgreSQL LiteLLM | 1 | 2 / 4 GiB |
| codex-lb, только расширенный состав | 1 | 2 / 4 GiB |
| PostgreSQL codex-lb | 1 | 1 / 2 GiB |
| Nginx | 1 | 1 / 256 MiB |

Расширенный состав имеет суммарные **лимиты** 59 CPU / 130.25 GiB, обычный —
56 CPU / 124.25 GiB. Они намеренно превышают ресурсы узла: это потолки каждого
контейнера, не резервирование и не требование иметь 130 GiB RAM.
В проверках плотности пик R6 был 22.63 GiB, в двух длительных A — 20.84/20.71 GiB;
CPU в пике доходил до всех 32 логических ядер. Это наблюдения конкретных входов,
не гарантия максимального расхода. Контролируйте доступную память узла, OOM,
очереди и задержки; не планируйте ёмкость делением RAM/CPU на лимит контейнера.
Суффикс Docker `g` означает GiB (1024³ байт), не десятичный GB; нужен запас ОС.
Redis получил 16 GiB с учётом квоты 32 MiB x 400 ключей = 12.5 GiB без накладных
расходов. Общий кэш также занимает память: это не гарантия предельного заполнения
и не изменение политики удаления данных Redis. Функциональная проверка на
меньшем сервере не подтверждает производительность для 400 пользователей.
Новые/смешанные входы насыщались на 2 запросах/с, а экранированный JSON может
замедляться из-за сохранённого ограничения кэша. При физическом отказе Triton
возможны защитные 503. Подробности — в указанных отчётах;
[прежняя матрица](research/scaling-matrix.md) относится к другой модели.
Ни отдельного фонового LiteLLM, ни второго балансировщика нет.

Прежняя локальная проверка обоих составов и политик относится к старому 4A/2T,
не к нынешней плотности: [исторические результаты](../presidio/evaluation/reports/tiny2-default-profiles.json).
Серверная приёмка A выполнена с настоящим NER и тестовым провайдером; это не
приёмка внешнего миллионного контекста или 400 пользователей.

Для изменения скопируйте [`production.env`](../deploy/topologies/production.env)
в локальный файл либо запишите только переопределяемые значения:

```dotenv
LITELLM_REPLICAS=3
ANALYZER_REPLICAS=6
ANALYZER_CPUS=4
ANALYZER_MEMORY=8g
```

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production TOPOLOGY_ENV=/secure-config/production.env
```

Файл содержит только количества и ресурсы, не секреты и не защитные политики.
Полный перечень параметров — в [справочнике](configuration.md#топологии-и-ресурсы).
Для последующих команд используйте тот же файл.

### Применение к существующей установке

Переход на Tiny2/Triton принят с [ограничениями качества](research/tiny2-quality-comparison.md).
Профиль измерен на 32 vCPU с SMT / 62.79 GiB; результат на другом CPU может отличаться.
Выполняйте обновление в окно обслуживания без пользовательского
трафика; Nginx сам не закрывает вход на время работ.

Перед обновлением сохраните:

- ревизию кода и неизменяемые ID/digest всех используемых образов;
- `.env`, сертификаты, локальные конфигурации и `TOPOLOGY_ENV` вне Git;
- проверяемые резервные копии PostgreSQL LiteLLM, PostgreSQL codex-lb и
  `codex-lb-data` с ключом шифрования ([порядок](codex-lb.md#резервное-копирование)).

Не меняйте имя Compose-проекта и расположение рабочего каталога без явного
сохранения имени проекта: иначе Compose может подключить новые пустые тома.
Удалите только [отменённые настройки](configuration.md#переход-со-старой-конфигурации)
из копии окружения для нового выпуска, сохранив прежний файл для возврата.

#### Обновление с v0.6.2 до v0.7.0

Первый шаг для обеих схем одинаков: обновите A **без смены топологии** и
проверьте его на одном узле. Без `NODE_ROLE` сохраняются штатные одноузловые
профили, прежний набор переменных и существующие переопределения ресурсов.
Повторный `setup`, замена `.env`, OAuth-вход и переимпорт подписок не нужны.

**До смены тега.** Выделите окно обслуживания. На действующем `v0.6.2`
зафиксируйте имя проекта по метке `com.docker.compose.project` уже запущенных
контейнеров, фактические `STACK`, `TOPOLOGY`, `ENV_FILE`, `TOPOLOGY_ENV` и режим
защиты. Сохраните `.env`, сертификаты, локальные конфигурации и файлы авторизации
в защищённом месте. Ниже пример для расширенного production; используйте свои
значения. Для `functional` не задавайте `TOPOLOGY_ENV`.

```bash
export STACK=litellm-presidio-codex-lb TOPOLOGY=production
export COMPOSE_PROJECT_NAME=ru-llm-proxy ENV_FILE=.env
# Если уже задан, сохраните прежний TOPOLOGY_ENV.
unset NODE_ROLE NODE_CONFIG
export BACKUP=/secure-backups/ru-llm-proxy-v0.6.2
```

Прекратите приём нового клиентского трафика на всех входах A и дождитесь
завершения активных запросов, включая SSE. Не меняйте рабочий checkout до
дренажа: контейнеры используют привязанные файлы из этого каталога. Пока старый
состав запущен, сделайте резервные копии. `BACKUP` должен быть новым каталогом
вне репозитория с доступным защищённым родительским каталогом.

```bash
(
  set -euo pipefail
  umask 077
  make health
  mkdir "$BACKUP"
  git rev-parse HEAD > "$BACKUP/revision.txt"
  cp "$ENV_FILE" "$BACKUP/env"
  if [ -n "${TOPOLOGY_ENV:-}" ]; then
    cp "$TOPOLOGY_ENV" "$BACKUP/topology.env"
  fi
  cp -R certs "$BACKUP/certs"

  ids=$(python3 scripts/deployment.py compose ps --quiet)
  test -n "$ids"
  read -r -a containers <<< "${ids//$'\n'/ }"
  docker inspect --format '{{.Config.Image}} {{.Image}}' "${containers[@]}" |
    sort -u > "$BACKUP/images.txt"
  refs=()
  while read -r ref id; do
    test "$(docker image inspect --format '{{.Id}}' "$ref")" = "$id"
    refs+=("$ref")
  done < "$BACKUP/images.txt"
  docker image save -o "$BACKUP/images.tar" "${refs[@]}"

  python3 scripts/deployment.py compose exec -T db sh -c \
    'exec pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > "$BACKUP/litellm.dump"
  if [ "$STACK" = litellm-presidio-codex-lb ]; then
    python3 scripts/deployment.py compose exec -T codex-lb-db sh -c \
      'exec pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > "$BACKUP/codex-lb.dump"
    python3 scripts/deployment.py compose exec -T codex-lb \
      tar -C /var/lib/codex-lb -cf - . > "$BACKUP/codex-lb-data.tar"
  fi
)
```

Если сохранение образов обнаружило, что локальный тег уже не соответствует
запущенному ID, не продолжайте: сначала сохраните проверенный старый комплект
и его привязку к именам Compose. Не удаляйте закреплённые по digest образы;
заранее проверьте доступ к их точным digest в разрешённом реестре. Проверьте
восстановление дампов в отдельных базах и наличие ключа шифрования codex-lb
в архиве. Не переносите резервные копии, секреты и авторизацию на B.

**Обновление A.** В прежнем рабочем каталоге, в том же контексте и с закрытым
клиентским трафиком выполните:

```bash
git fetch origin tag v0.7.0
git switch --detach v0.7.0
python3 scripts/deployment.py compose config --quiet
make build
make restart
make health
make metrics
```

Если Git недоступен из контура, заранее перенесите проверенный комплект того
же тега. При любой ошибке остановитесь и не возвращайте трафик. Не применяйте
новую версию к части пула: обновление меняет наш код Analyzer и разбор
JSON-аргументов в LiteLLM; должны быть обновлены все их реплики. Проверьте
готовность каждого экземпляра, прежний виртуальный ключ, политику MASK/BLOCK,
каталог и доступные подписки codex-lb. Выполните согласованные
[синтетические пробы Chat Completions и Responses](examples.md), с SSE и без,
по штатному входу Nginx. Для MASK проверьте точное восстановление, для BLOCK
ожидаемый отказ; не переключайте боевую политику ради теста и не отправляйте
корпоративные данные во внешние модели.

Для одноузлового режима после успешных проверок верните трафик. Для двух узлов
продолжите по [инструкции подключения B](#подключение-b-к-работающему-production):
она применяется только к production. Подготовьте B на **том же теге**, с его
собственным `ENV_FILE` и JSON адресов. Проверьте локальную готовность обоих узлов,
маршрут A→B и отказ ACL с отличимого источника перед открытием трафика. На A
смените роль через `make down` без `-v` и `make up` с `NODE_ROLE=primary`;
не выполняйте смену роли через `restart`. При смене топологии штатный Redis
может потерять кэш и состояние диалога: при 409 на прежний `previous_response_id`
повторите запрос с полной историей без старой ссылки.

#### Откат версии на v0.6.2

Сначала снова исключите входящий трафик и дождитесь дренажа. Остановите новый
состав **из checkout `v0.7.0`**, сохранив имя проекта и его окружение:

- На одном узле выполните `make down` с прежними `STACK`, `TOPOLOGY`,
  `ENV_FILE`, `TOPOLOGY_ENV`, без `NODE_ROLE`.
- В двухузловой схеме сначала выполните `make down` на A с контекстом
  `NODE_ROLE=primary`, затем на B с его собственным `NODE_ROLE=compute`.
  Не меняйте тег на A, пока его ролевые контейнеры не удалены; `v0.6.2`
  не управляет этими ролями. Возврат только топологии без смены версии
  [описан отдельно](#возврат-к-одному-узлу).

Ни на одном узле не выполняйте `down -v`, `clean` или очистку Docker. До запуска
старого выпуска подтвердите совместимость текущих баз с прежними образами.
Если схемы несовместимы, сначала восстановите проверенные резервные копии в
отдельном контуре и согласуйте перенос записей, появившихся после копирования;
не перезаписывайте рабочие базы и ключ шифрования вслепую.

На A верните сохранённую конфигурацию `v0.6.2` в прежние пути, не генерируя
секреты заново. Загрузите архив и проверьте **все исходные ссылки на образы**:
смена Git-тега сама по себе не восстанавливает локальные теги Docker.

```bash
unset NODE_ROLE NODE_CONFIG
git switch --detach v0.6.2
(
  set -euo pipefail
  docker image load -i "$BACKUP/images.tar"
  test -s "$BACKUP/images.txt"
  while read -r ref id; do
    test "$(docker image inspect --format '{{.Id}}' "$ref")" = "$id"
  done < "$BACKUP/images.txt"
)
```

Если после `load` отсутствует точная ссылка по digest, получите именно её из
разрешённого реестра и повторите проверку ID. Не заменяйте её похожим тегом.
Только после успешной проверки образов и совместимости данных запустите A с
сохранёнными `STACK`, `TOPOLOGY`, `ENV_FILE`, `TOPOLOGY_ENV` и именем проекта:

```bash
python3 scripts/deployment.py compose config --quiet
make up
make health
```

Сверьте фактические ID запущенных образов с `images.txt`, затем проверьте ключи,
подписки, защитную политику и сквозные запросы. B оставьте выключенным.
После `down` прежним диалогам Responses может понадобиться полная история.
Допускайте трафик только после проверок. Воспроизведённый
[откат топологии](#возврат-к-одному-узлу) на одном выпуске не подтверждает
восстановление версии или схем БД конкретной установки.

#### Переход production с v0.5.0 на v0.6.0

| Настройка | v0.5.0 | v0.6.0 |
|---|---|---|
| LiteLLM | 2 по 2 CPU / 4 GiB | Без изменений |
| Analyzer | 4 по 2 CPU / 4 GiB | 24 по 1 CPU / 2 GiB |
| Triton | 2 по 2 CPU / 2 GiB | 12 по 2 CPU / 4 GiB |
| Очередь Analyzer / ожидание | 32 / 30 с | 32 / 45 с |

Не меняются: один процесс и два активных анализа на Analyzer, пакет четыре окна,
два исполнения модели на Triton, HTTP-пул 20/10, бюджет 240 с и предел тела 25 MiB.
Секреты, подписки, сертификаты и настройки корпоративного прокси сохраняются.
Новые переменные окружения не требуются.

1. После резервного копирования и исключения трафика перейдите на выпуск
   **в прежнем рабочем каталоге**, сохранив локальные изменения вне Git:

   ```bash
   git fetch origin --tags
   git switch --detach v0.6.0
   ```

2. Проверьте `TOPOLOGY_ENV`: старый файл, скопированный целиком из пресета,
   сохранит 4 Analyzer / 2 Triton и прежние ресурсы. Для новых стандартных
   значений уберите эти записи либо не передавайте такой файл; сохраните только
   действительно нужные переопределения. Не подменяйте новый проектный
   `deploy/topologies/production.env` старой копией.
3. Проверьте `.env` и экспортированное окружение. Уберите явную
   `PRESIDIO_ANALYZER_QUEUE_TIMEOUT_SECONDS=30`, чтобы production унаследовал 45 с.
   Ранее изменённые число процессов, параллельность, размеры пакета/очереди и HTTP-пул не сбрасываются:
   сверьте их со [стандартными профилями](#стандартные-профили) и справочником.
   `TRITON_REPLICAS=2` противоречит новому пресету: удалите запись из `.env`/оболочки
   либо перенесите намеренное уменьшение пула в `TOPOLOGY_ENV`.
   `TRITON_MODEL_INSTANCES=2` остаётся корректным; это не число контейнеров.
4. Проверьте конфигурацию без вывода секретов, затем соберите и пересоздайте состав:

```bash
STACK=litellm-presidio-codex-lb TOPOLOGY=production python3 scripts/deployment.py compose config --quiet
make build STACK=litellm-presidio-codex-lb TOPOLOGY=production
make restart STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
make metrics STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

Укажите прежние `ENV_FILE` и `TOPOLOGY_ENV`, если они используются. Для обычного
состава смените только `STACK`, для функционального — `TOPOLOGY=functional`.
Задавайте одинаковый контекст во всех командах, включая `build` и проверку
конфигурации. После удаления ненужных переопределений запуск должен показать
2 LiteLLM / 24 Analyzer / 12 Triton, а `health` — готовность каждой реплики.
Холодный запуск последовательный и занимает несколько минут; `STACK_START_TIMEOUT`
ограничивает ожидание отдельного этапа, не общее время развёртывания.
`restart` пересоздаёт управляемые контейнеры с сохранением томов PostgreSQL,
codex-lb и подписок; повторные `setup`, OAuth-вход и `down -v` не требуются.
При сборке нужны сеть и свободный диск, при запуске модель из интернета не
скачивается. Если сборка завершилась ошибкой, не запускайте смешанный комплект
нового Analyzer и старого Triton. После запуска проверьте сохранённую политику,
восстановление обычного/потокового ответа и метрики. Обе политики и отсутствие
исходных маркеров у тестового провайдера проверяйте в отдельном испытательном
составе, не меняя защитную политику потребителей ради теста; команды собраны в
[матрице проверок](research/ner-migration-test-coverage.md).
Только после успешной проверки оператор возвращает пользовательский трафик.

### Возврат к предыдущему выпуску

Возвращается весь проверенный выпуск, а не только веса или контейнер Analyzer.
Резервного исполнения прежней модели в новом коде нет.

1. Исключите трафик и сохраните безопасные сведения о сбое без текстов и секретов.
2. Остановите новый состав его командой `make down STACK=<состав> TOPOLOGY=<топология>`
   с прежними `ENV_FILE`/`TOPOLOGY_ENV`, **без удаления томов**. Удалятся также
   контейнеры Triton нового состава; одной смены Git-ветки для этого недостаточно.
3. Верните код, проверенные образы и согласованную конфигурацию предыдущего
   выпуска. Секреты не генерируйте заново. Если обновление мигрировало базы,
   используйте совместимую резервную копию; один старый образ схему не откатывает.
4. Выполните команды запуска и проверки из документации предыдущего выпуска,
   затем верните трафик. Не переносите новые переменные и команды на старый код.

`down` не сохраняет привязку анонимного тома Redis для следующего `up`:
кэш, временные таблицы и продолжения Responses могут стать недоступны.
Для таких диалогов клиенту понадобится новая сессия/полная история. PostgreSQL
и том ключа codex-lb не удаляются; `clean`, `down -v` и глобальная очистка Docker
для обновления или возврата недопустимы. Это инструкция, а не подтверждение
испытания восстановления резервных копий конкретной установки.

## Tiny2

Сборка автоматически получает закреплённые файлы и проверяет SHA-256.
Analyzer обращается к модели через тот же Nginx по внутреннему порту `8000`.
Production запускает 12 контейнеров; для одного задайте `TRITON_REPLICAS=1`
в `TOPOLOGY_ENV`. Functional использует один контейнер.
Для изменения пула используйте тот же `TRITON_REPLICAS` в
`TOPOLOGY_ENV`: требуется положительное целое. Доступные CPU, память
и измеренная пропускная способность ограничивают полезный размер пула;
увеличение числа реплик само по себе не подтверждает ёмкость установки.
`TRITON_MODEL_INSTANCES` задаёт число исполнений внутри каждого контейнера.
Nginx обновляет DNS без перезагрузки и не повторяет отправленные POST-запросы.
Порты Triton `8000`/`8002` на хост не публикуются.

`make health` проверяет каждый экземпляр по закреплённой ревизии и SHA графа,
а не только ответ балансировщика. `make metrics` выводит метрики отдельно для
каждого Triton, Analyzer и LiteLLM. Не суммируйте их повторно через общий адрес.
Несколько Triton не гарантируют отсутствие отказов при нагрузке: очереди ограничены,
при перегрузке остаётся безопасный `503`. Сквозная отмена пока не гарантирует
немедленного прекращения анализа. Откат выполняется предыдущим выпуском целиком,
без резервной модели; принятие перехода не устраняет известные пропуски и лишние маски.

## Большой новый ввод

При обновлении исправления границ NER пересоберите Analyzer и пересоздайте
состав штатными `make build` и `make restart` с прежними `STACK`, `TOPOLOGY`,
`ENV_FILE` и `TOPOLOGY_ENV`, как в инструкции обновления выше. Одна пересборка
Analyzer без пересоздания контейнеров не применит новый образ.
При переходе с v0.6.1 исправление текстовых абзацев внутри Markdown-блоков
требует нового образа каждого Analyzer, а новый тайм-аут провайдера
`router_settings.timeout: 600` — перечитывания YAML всеми процессами LiteLLM.
В стандартном production обновляются все 24 Analyzer и обе реплики LiteLLM;
один обновлённый контейнер не гарантирует одинакового поведения пула.
После `make restart` выполните `make health` с теми же параметрами:
проверяется каждый экземпляр, а не только адрес Nginx.
Тома, ключи и подписки сохраняются; повторный `setup` и `down -v` не нужны.
При переходе с v0.6.1 формат Redis не меняется, историю очищать не нужно.
Если обновляетесь с версии до v0.6.1, обновляйте все процессы LiteLLM согласованно
без пользовательского трафика: исправления словаря и экранирования находятся
в нашем модуле LiteLLM, а прежний восстановитель не читает новые сведения Redis.
Старые записи читаются новым кодом без угадывания утраченного контекста.
Если старый диалог уже содержит искажённое значение, начните новый или передайте
полную историю; очищать весь Redis не требуется.

Обычный бюджет предварительной проверки — **240 секунд**. Для редкого нового
файла до миллиона текстовых токенов выбран бюджет **1200 секунд**. Задайте
существующую переменную в `ENV_FILE`:

```dotenv
# Предварительная обработка: история, Analyzer, кэш и сохранение замен.
PII_GUARDRAIL_ANALYZER_TIMEOUT_SECONDS=1200
```

Стандартные ресурсы и очередь из таблиц выше сохраняются. Само по себе
повышение CPU до 8 не требуется: локально новый миллионный ввод прошёл при
Analyzer 2 CPU + Triton 2 CPU. Это не гарантия времени на другой машине или
при нескольких больших файлах одновременно.
Примените настройки обычной командой `make up` с прежними `STACK`, `TOPOLOGY`,
`ENV_FILE` и `TOPOLOGY_ENV`. Нового режима или команды нет: бюджет одинаков
для всех запросов процесса, а не выбирается по размеру файла. Суммарные ресурсы
зависят от числа экземпляров Analyzer.

Nginx ждёт LiteLLM и Analyzer до **1500 секунд** в обеих топологиях; тайм-аут
провайдера в обоих профилях LiteLLM — **600 секунд**, вместо прежних 60.
Новые переменные и повторный `setup` не нужны; изменённый YAML применяется
после пересоздания всех LiteLLM-реплик. Клиент и корпоративные посредники должны
допускать предварительную проверку и последующее ожидание модели. Если одновременно
нужны предварительная проверка до 1200 секунд и длительное ожидание провайдера,
предел 1500 секунд Nginx требуется согласовать отдельно: автоматически он не повышается.
Обычный бюджет проверки остаётся 240 секунд, политика повторов не меняется. SSE начинается
только после проверки; большой новый ввод не становится интерактивным.
Стандартный Compose подключает наш ASGI-адаптер перед штатной CLI LiteLLM.
Обнаруженный ранний обрыв отменяет предварительную обработку, не дожидаясь
бюджета; новая настройка не требуется. При обновлении нужно обычное
пересоздание контейнера, чтобы применить точку входа. Сетевой посредник может
задержать сигнал, а уже принятое Triton вычисление может завершиться.

Измерения и границы применимости: [отчёт этапа 3](research/release-040-followups.md#третий-этап-бюджет-предварительной-проверки-10-октября-2026).
Синтетический миллионный ввод не подтверждает такой контекст у внешней модели
или производительность для 400 пользователей.

## Балансировка и диагностика

Один Nginx распределяет запросы между LiteLLM и обращения к Analyzer по числу
активных соединений. Docker DNS обновляет состав пулов. Это пассивная
обработка сетевых ошибок, а не автоматическое исключение всех контейнеров со
статусом `unhealthy`. Переданные POST-запросы к модели не повторяются Nginx;
для анализа разрешены максимум две попытки при ошибке соединения или HTTP `502`.
HTTP `503` Analyzer передаётся без повтора и не исключает отвечающую реплику;
сохраняются исходная причина и `Retry-After`, если он задан.
Потоковые ответы передаются без буферизации.
Оборванный поток не переносится на другую реплику: проверка отказа подтверждает
обработку нового запроса оставшимися экземплярами, не продолжение прежнего SSE.

В production порты `4000` и `5001` публикует Nginx, а не отдельные экземпляры.
Порты `80`, `2455` и `9090` сохраняют назначение; HTTP и метрики доступны только
в доверенной сети, сетевые ограничения остаются обязанностью оператора.

```bash
make logs STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
make metrics STACK=litellm-presidio-codex-lb TOPOLOGY=production
make guardrails-smoke STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`health` проверяет каждый ожидаемый экземпляр и прогрев NER, а `metrics`
опрашивает каждую реплику отдельно. Для Prometheus нужны отдельные цели по
контейнерам: балансируемый `/metrics` не является суммой метрик пула.

## Переключение и остановка

На одном Compose-проекте выполните `up` с новой топологией либо изменённым
числом экземпляров. Обслуживание временно прерывается; базовые хранилища и тома
сохраняются. Возврат к `functional` выполняется так же. Имена Compose-проекта
и `ENV_FILE` менять нельзя, если требуется сохранить прежние данные.

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=functional
make down STACK=litellm-presidio-codex-lb TOPOLOGY=functional
```

`down`, `logs`, проверки и очистка должны указывать фактическую топологию.
Перед переходом с расширенного состава на базовый выполните `down` расширенного
состава без `-v`. `clean` намеренно удаляет данные и не используется для
переключения. Перед изменением production сохраните резервные копии обеих баз,
тома `codex-lb-data`, `.env` и сертификатов.

После `down` анонимный том локального Redis не подключается автоматически:
временный кэш и привязки маршрутизации будут утрачены. Для изменений профиля,
политики или числа экземпляров **без смены роли** используйте `up`/`restart`.
Смена `NODE_ROLE` требует [отдельной последовательности](#подключение-b-к-работающему-production).
