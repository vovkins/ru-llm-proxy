# Развёртывание Docker Compose

Параметры состава, топологии и политики независимы:

| Параметр | Выбор |
| --- | --- |
| `STACK` | `litellm-presidio` или `litellm-presidio-codex-lb`; расширенный состав включает базовый |
| `TOPOLOGY` | `functional` по умолчанию; `production` для нескольких экземпляров на одном сервере |
| `PII_GUARDRAIL_MODE` | `MASK`/`mask` либо `BLOCK`/`block` |
| `ENV_FILE` | Файл секретов и настроек; по умолчанию `.env` |
| `TOPOLOGY_ENV` | Необязательный файл дополнительных количеств и ресурсов production |

Нужны Python 3.9+, Docker Compose 2.24+ с поддержкой `!reset`, GNU Make.
Образы и их версии одинаковы для обеих топологий; патчей платформ нет.
GPU-профиль остаётся доступным только для `functional` и не входит в этот
production-пресет.

## Первичный запуск

Для базового состава:

```bash
make setup STACK=litellm-presidio PII_GUARDRAIL_MODE=MASK
# Заполните два ключа Z.AI в .env.
make build
make up STACK=litellm-presidio TOPOLOGY=functional
make health STACK=litellm-presidio TOPOLOGY=functional
```

Для расширенного состава сначала подготовьте `.env` из примера и соберите
образы, затем выполните штатную [настройку codex-lb](codex-lb.md).
Параметры `TOPOLOGY` и `ENV_FILE` должны быть одинаковыми у `setup` и `up`.
Выполнять два отдельных `setup` не нужно.

```bash
make build
make setup STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=BLOCK
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`build` собирает образы, `setup` готовит секреты и первичную настройку,
`up` запускает без сборки. `up` и `restart` закрывают вход через Nginx до
готовности всех экземпляров. Холодный запуск Analyzer и LiteLLM выполняется
последовательно, чтобы ограничить пик памяти и одновременные миграции базы.
При ошибке Nginx остаётся остановленным: изучите журналы и повторите `up`.
При защёлкнутой ошибке NER нужен `restart`, а не повторный запуск того же процесса.
При смене политики или топологии старые LiteLLM также останавливаются до
записи режима: в functional это закрывает прямой вход на порт `4000`.

## Режим обработки

Приоритет: **параметр make > окружение оболочки > ENV_FILE > mask**.
Неизвестное или пустое значение отклоняется до изменения файлов и контейнеров.
Явный параметр `PII_GUARDRAIL_MODE` в `setup`, `up` или `restart` атомарно
сохраняется в `ENV_FILE` в нижнем регистре; остальные записи и права файла
сохраняются. Значение из окружения применяется, но не записывается в файл.

```bash
make restart STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=MASK
```

Все экземпляры LiteLLM получают одинаковую политику. Повторный `setup` на
работающей установке допускается только с её текущей топологией и политикой;
для изменения используйте `restart`, а не первичную настройку.
Предварительная и финальная проверки, словарные подстановки и другие защитные
политики сохраняют собственные настройки.

## Ресурсы production

| Компонент | Экземпляров | CPU / память на экземпляр |
| --- | ---: | --- |
| LiteLLM | 2 | 2 / 4 GiB |
| Analyzer | 4 | 4 / 8 GiB |
| Redis | 1 | 1 / 2 GiB |
| PostgreSQL LiteLLM | 1 | 2 / 4 GiB |
| codex-lb, только расширенный состав | 1 | 2 / 4 GiB |
| PostgreSQL codex-lb | 1 | 1 / 2 GiB |
| Nginx | 1 | 1 / 256 MiB |

Расширенный состав имеет суммарные **лимиты** 27 CPU / 52.25 GiB. Это не
резервирование и не измеренное потребление. Ориентир сервера — 32 выделенных
vCPU / 64 GiB RAM / SSD; нужны также ресурсы ОС. Функциональная проверка на
меньшем сервере не подтверждает производительность для 400 пользователей.
Измерения и ограничения длинного контекста: [матрица масштабирования](research/scaling-matrix.md).
Ни отдельного фонового LiteLLM, ни второго балансировщика нет.

Для изменения скопируйте [`production.env`](../deploy/topologies/production.env)
в локальный файл либо запишите только переопределяемые значения:

```dotenv
LITELLM_REPLICAS=3
ANALYZER_REPLICAS=6
ANALYZER_CPUS=4
ANALYZER_MEMORY=8g
```

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production TOPOLOGY_ENV=/secure-config/production.env
```

Файл содержит только количества и ресурсы, не секреты и не защитные политики.
Полный перечень параметров — в [справочнике](configuration.md#топологии-и-ресурсы).
Для последующих команд используйте тот же файл.

## Большой новый ввод

Обычный бюджет предварительной проверки — **240 секунд**. Для редкого нового
файла до миллиона текстовых токенов выбран бюджет **1200 секунд**. Задайте
существующую переменную в `ENV_FILE`:

```dotenv
# Предварительная обработка: история, Analyzer, кэш и сохранение замен.
PII_GUARDRAIL_ANALYZER_TIMEOUT_SECONDS=1200
```

В production задайте `ANALYZER_CPUS=8` в существующем `TOPOLOGY_ENV`; память
8 GiB, параллельность 1, очередь 8 и ожидание очереди 1 секунда сохраняются.
Примените настройки обычной командой `make up` с прежними `STACK`, `TOPOLOGY`,
`ENV_FILE` и `TOPOLOGY_ENV`. Нового режима или команды нет: бюджет одинаков
для всех запросов процесса, а не выбирается по размеру файла. Суммарные ресурсы
зависят от числа экземпляров Analyzer.

Nginx ждёт LiteLLM и Analyzer до **1500 секунд** в обеих топологиях; тайм-аут
провайдера 60 секунд не меняется. Клиент и корпоративные посредники должны
допускать ожидание до первого ответа с запасом на вызов модели. SSE начинается
только после проверки; большой новый ввод не становится интерактивным.
Ранний обрыв клиента в LiteLLM 1.98.0 ограничивается бюджетом, но не вызывает
немедленную отмену анализа. Это принятое ограничение без патча платформы.

Измерения и границы применимости: [отчёт этапа 3](research/release-040-followups.md#третий-этап-бюджет-предварительной-проверки-10-октября-2026).
Синтетический миллионный ввод не подтверждает такой контекст у внешней модели
или производительность для 400 пользователей.

## Балансировка и диагностика

Один Nginx распределяет запросы между LiteLLM и обращения к Analyzer по числу
активных соединений. Docker DNS обновляет состав пулов. Это пассивная
обработка сетевых ошибок, а не автоматическое исключение всех контейнеров со
статусом `unhealthy`. Переданные POST-запросы к модели не повторяются Nginx;
для анализа разрешены максимум две попытки при сетевой ошибке, `502` или `503`.
Потоковые ответы передаются без буферизации.
Оборванный поток не переносится на другую реплику: проверка отказа подтверждает
обработку нового запроса оставшимися экземплярами, не продолжение прежнего SSE.

В production порты `4000` и `5001` публикует Nginx, а не отдельные экземпляры.
Порты `80`, `2455` и `9090` сохраняют назначение; HTTP и метрики доступны только
в доверенной сети, сетевые ограничения остаются обязанностью оператора.

```bash
make logs STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
make metrics STACK=litellm-presidio-codex-lb TOPOLOGY=production
make guardrails-smoke STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`health` проверяет каждый ожидаемый экземпляр и прогрев NER, а `metrics`
опрашивает каждую реплику отдельно. Для Prometheus нужны отдельные цели по
контейнерам: балансируемый `/metrics` не является суммой метрик пула.

## Переключение и остановка

На одном Compose-проекте выполните `up` с новой топологией либо изменённым
числом экземпляров. Обслуживание временно прерывается; базовые хранилища и тома
сохраняются. Возврат к `functional` выполняется так же. Имена Compose-проекта
и `ENV_FILE` менять нельзя, если требуется сохранить прежние данные.

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=functional
make down STACK=litellm-presidio-codex-lb TOPOLOGY=functional
```

`down`, `logs`, проверки и очистка должны указывать фактическую топологию.
Перед переходом с расширенного состава на базовый выполните `down` расширенного
состава без `-v`. `clean` намеренно удаляет данные и не используется для
переключения. Перед изменением production сохраните резервные копии обеих баз,
тома `codex-lb-data`, `.env` и сертификатов.

После `down` анонимный том локального Redis не подключается автоматически:
временный кэш и привязки маршрутизации будут утрачены. Для смены топологии,
политики и числа экземпляров используйте `up`/`restart`, а не `down` → `up`.
