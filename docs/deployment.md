# Развёртывание Docker Compose

Параметры состава, топологии и политики независимы:

| Параметр | Выбор |
| --- | --- |
| `STACK` | `litellm-presidio` или `litellm-presidio-codex-lb`; расширенный состав включает базовый |
| `TOPOLOGY` | `functional` по умолчанию; `production` для нескольких экземпляров на одном сервере |
| `PII_GUARDRAIL_MODE` | `MASK`/`mask` либо `BLOCK`/`block` |
| `ENV_FILE` | Файл секретов и настроек; по умолчанию `.env` |
| `TOPOLOGY_ENV` | Необязательный файл дополнительных количеств и ресурсов production |

Нужны Python 3.9+, Docker Compose 2.24+ с поддержкой `!reset`, GNU Make.
Образы и их версии одинаковы для обеих топологий; патчей платформ нет.
Обе топологии используют единственный комплект Tiny2/Triton на CPU.
Селекторов модели и GPU-профилей нет. При переходе удалите прежние параметры
по [инструкции миграции](configuration.md#переход-со-старой-конфигурации).

## Первичный запуск

Для базового состава:

```bash
make setup STACK=litellm-presidio PII_GUARDRAIL_MODE=MASK
# Заполните два ключа Z.AI в .env.
make build
make up STACK=litellm-presidio TOPOLOGY=functional
make health STACK=litellm-presidio TOPOLOGY=functional
```

Для расширенного состава сначала подготовьте `.env` из примера и соберите
образы, затем выполните штатную [настройку codex-lb](codex-lb.md).
Параметры `TOPOLOGY` и `ENV_FILE` должны быть одинаковыми у `setup` и `up`.
Выполнять два отдельных `setup` не нужно.

```bash
make build
make setup STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=BLOCK
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`build` собирает образы, `setup` готовит секреты и первичную настройку,
`up` запускает без сборки. **На время развёртывания оператор исключает реальный
пользовательский трафик внешними средствами.** Nginx запускается первым с полной
конфигурацией; двухфазного переключения и автоматического закрытия входа нет.
После `nginx -t` проверяются каждый Triton, внутренний маршрут Nginx к модели,
прогретые Analyzer и затем LiteLLM. Готовность реплики не заменяет готовность
маршрута: Docker DNS может обновиться чуть позже запуска модели.
Холодные экземпляры запускаются последовательно, чтобы ограничить пик памяти.
При ошибке команда завершается, Nginx остаётся доступным, часть маршрутов может
временно отвечать ошибкой. Изучите журналы и повторите `up`.
При защёлкнутой ошибке NER нужен `restart`, а не повторный запуск того же процесса.
При смене политики или топологии старые LiteLLM также останавливаются до
записи режима: в functional это закрывает прямой вход на порт `4000`.

## Режим обработки

Приоритет: **параметр make > окружение оболочки > ENV_FILE > mask**.
Неизвестное или пустое значение отклоняется до изменения файлов и контейнеров.
Явный параметр `PII_GUARDRAIL_MODE` в `setup`, `up` или `restart` атомарно
сохраняется в `ENV_FILE` в нижнем регистре; остальные записи и права файла
сохраняются. Значение из окружения применяется, но не записывается в файл.

```bash
make restart STACK=litellm-presidio-codex-lb TOPOLOGY=production PII_GUARDRAIL_MODE=MASK
```

Все экземпляры LiteLLM получают одинаковую политику. Повторный `setup` на
работающей установке допускается только с её текущей топологией и политикой;
для изменения используйте `restart`, а не первичную настройку.
Предварительная и финальная проверки, словарные подстановки и другие защитные
политики сохраняют собственные настройки.

## Стандартные профили

Оба профиля применяются к любому `STACK`; политики MASK/BLOCK не меняют ресурсы.

| Параметр | functional | production |
|---|---:|---:|
| LiteLLM / Analyzer / Triton | 1 / 1 / 1 | 2 / 4 / 2 |
| Процессов в каждом Analyzer | 1 | 1 |
| Активных анализов / ожидающих на процесс | 2 / 32 | 2 / 32 |
| Ожидание места в очереди | 30 с | 30 с |
| Исполнений модели в каждом Triton | 2 | 2 |
| Окон в одном пакете NER | 4 | 4 |

Functional не навязывает жёсткие лимиты памяти и CPU. Профиль production ниже —
согласованная исходная конфигурация для сервера 32 CPU / 64 GB RAM, не гарантия
ёмкости на 400 человек. [Измерения Э10](research/tiny2-capacity.md) и
[матрица очередей](research/tiny2-queues.md) подтверждают пользу параллельности
и ожидания, но не абсолютный оптимум на другом оборудовании.

## Ресурсы production

| Компонент | Экземпляров | CPU / память на экземпляр |
| --- | ---: | --- |
| LiteLLM | 2 | 2 / 4 GiB |
| Analyzer | 4 | 2 / 4 GiB |
| Triton | 2 (допустим 1) | 2 / 2 GiB |
| Redis | 1 | 1 / 16 GiB |
| PostgreSQL LiteLLM | 1 | 2 / 4 GiB |
| codex-lb, только расширенный состав | 1 | 2 / 4 GiB |
| PostgreSQL codex-lb | 1 | 1 / 2 GiB |
| Nginx | 1 | 1 / 256 MiB |

Расширенный состав имеет суммарные **лимиты** 23 CPU / 54.25 GiB, обычный —
20 CPU / 48.25 GiB. Это не резервирование и не измеренное потребление.
Суффикс Docker `g` означает GiB (1024³ байт), не десятичный GB; нужен запас ОС.
Redis получил 16 GiB с учётом квоты 32 MiB x 400 ключей = 12.5 GiB без накладных
расходов. Общий кэш также занимает память: это не гарантия предельного заполнения
и не изменение политики удаления данных Redis. Функциональная проверка на
меньшем сервере не подтверждает производительность для 400 пользователей.
Измерения и ограничения: [Tiny2 Э10](research/tiny2-capacity.md);
[прежняя матрица](research/scaling-matrix.md) относится к другой модели.
Ни отдельного фонового LiteLLM, ни второго балансировщика нет.

Локальная проверка профилей прошла на обоих составах и политиках с имитацией
провайдера. Это не приёмка качества, внешнего миллионного контекста или 400
пользователей. [Результаты и ограничения](../presidio/evaluation/reports/tiny2-default-profiles.json).

Для изменения скопируйте [`production.env`](../deploy/topologies/production.env)
в локальный файл либо запишите только переопределяемые значения:

```dotenv
LITELLM_REPLICAS=3
ANALYZER_REPLICAS=6
ANALYZER_CPUS=4
ANALYZER_MEMORY=8g
```

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=production TOPOLOGY_ENV=/secure-config/production.env
```

Файл содержит только количества и ресурсы, не секреты и не защитные политики.
Полный перечень параметров — в [справочнике](configuration.md#топологии-и-ресурсы).
Для последующих команд используйте тот же файл.

### Применение к существующей установке

Переход на Tiny2/Triton принят с [ограничениями качества](research/tiny2-quality-comparison.md).
Ёмкость целевого сервера ещё не подтверждена. Выполняйте обновление в окно обслуживания без пользовательского
трафика; Nginx сам не закрывает вход на время работ.

Перед обновлением сохраните:

- ревизию кода и неизменяемые ID/digest всех используемых образов;
- `.env`, сертификаты, локальные конфигурации и `TOPOLOGY_ENV` вне Git;
- проверяемые резервные копии PostgreSQL LiteLLM, PostgreSQL codex-lb и
  `codex-lb-data` с ключом шифрования ([порядок](codex-lb.md#резервное-копирование)).

Не меняйте имя Compose-проекта и расположение рабочего каталога без явного
сохранения имени проекта: иначе Compose может подключить новые пустые тома.
Удалите только [отменённые настройки](configuration.md#переход-со-старой-конфигурации)
из копии окружения для нового выпуска, сохранив прежний файл для возврата.
Если в `.env` явно заданы старые ограничения Analyzer, удалите только эти
переопределения для принятия новых стандартных значений или сохраните их осознанно.
Секреты и настройки корпоративной сети менять не нужно.
Параметры `TRITON_REPLICAS`/`TRITON_MODEL_INSTANCES` из `.env` или окружения
должны совпадать с профилем; прежние явные `1` перенесите в `TOPOLOGY_ENV`,
если хотите сохранить их в production, либо удалите для принятия новых значений.

```bash
make build
make restart STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
make metrics STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

Укажите прежние `ENV_FILE` и `TOPOLOGY_ENV`, если они используются. Для обычного
состава смените только `STACK`, для функционального — `TOPOLOGY=functional`.
`restart` пересоздаёт управляемые контейнеры с сохранением томов PostgreSQL,
codex-lb и подписок; повторные `setup`, OAuth-вход и `down -v` не требуются.
При сборке нужны сеть и свободный диск, при запуске модель из интернета не
скачивается. Если сборка завершилась ошибкой, не запускайте смешанный комплект
нового Analyzer и старого Triton. После запуска проверьте обе политики,
восстановление обычного/потокового ответа и отсутствие исходных маркеров у
тестового провайдера; команды собраны в [матрице проверок](research/ner-migration-test-coverage.md).
Только после успешной проверки оператор возвращает пользовательский трафик.

### Возврат к предыдущему выпуску

Возвращается весь проверенный выпуск, а не только веса или контейнер Analyzer.
Резервного исполнения прежней модели в новом коде нет.

1. Исключите трафик и сохраните безопасные сведения о сбое без текстов и секретов.
2. Остановите новый состав его командой `make down STACK=<состав> TOPOLOGY=<топология>`
   с прежними `ENV_FILE`/`TOPOLOGY_ENV`, **без удаления томов**. Удалятся также
   контейнеры Triton нового состава; одной смены Git-ветки для этого недостаточно.
3. Верните код, проверенные образы и согласованную конфигурацию предыдущего
   выпуска. Секреты не генерируйте заново. Если обновление мигрировало базы,
   используйте совместимую резервную копию; один старый образ схему не откатывает.
4. Выполните команды запуска и проверки из документации предыдущего выпуска,
   затем верните трафик. Не переносите новые переменные и команды на старый код.

`down` не сохраняет привязку анонимного тома Redis для следующего `up`:
кэш, временные таблицы и продолжения Responses могут стать недоступны.
Для таких диалогов клиенту понадобится новая сессия/полная история. PostgreSQL
и том ключа codex-lb не удаляются; `clean`, `down -v` и глобальная очистка Docker
для обновления или возврата недопустимы. Это инструкция, а не подтверждение
испытания восстановления резервных копий конкретной установки.

## Tiny2

Сборка автоматически получает закреплённые файлы и проверяет SHA-256.
Analyzer обращается к модели через тот же Nginx по внутреннему порту `8000`.
Production уже запускает два контейнера; для одного задайте `TRITON_REPLICAS=1`
в `TOPOLOGY_ENV`. Functional использует один контейнер.
`TRITON_MODEL_INSTANCES` задаёт число исполнений внутри каждого контейнера.
Nginx обновляет DNS без перезагрузки и не повторяет отправленные POST-запросы.
Порты Triton `8000`/`8002` на хост не публикуются.

`make health` проверяет каждый экземпляр по закреплённой ревизии и SHA графа,
а не только ответ балансировщика. `make metrics` выводит метрики отдельно для
каждого Triton, Analyzer и LiteLLM. Не суммируйте их повторно через общий адрес.
Два Triton не гарантируют отсутствие отказов при нагрузке: очереди ограничены,
при перегрузке остаётся безопасный `503`. Сквозная отмена пока не гарантирует
немедленного прекращения анализа. Откат выполняется предыдущим выпуском целиком,
без резервной модели; принятие перехода не устраняет известные пропуски и лишние маски.

## Большой новый ввод

Обычный бюджет предварительной проверки — **240 секунд**. Для редкого нового
файла до миллиона текстовых токенов выбран бюджет **1200 секунд**. Задайте
существующую переменную в `ENV_FILE`:

```dotenv
# Предварительная обработка: история, Analyzer, кэш и сохранение замен.
PII_GUARDRAIL_ANALYZER_TIMEOUT_SECONDS=1200
```

Стандартные ресурсы и очередь из таблиц выше сохраняются. Само по себе
повышение CPU до 8 не требуется: локально новый миллионный ввод прошёл при
Analyzer 2 CPU + Triton 2 CPU. Это не гарантия времени на другой машине или
при нескольких больших файлах одновременно.
Примените настройки обычной командой `make up` с прежними `STACK`, `TOPOLOGY`,
`ENV_FILE` и `TOPOLOGY_ENV`. Нового режима или команды нет: бюджет одинаков
для всех запросов процесса, а не выбирается по размеру файла. Суммарные ресурсы
зависят от числа экземпляров Analyzer.

Nginx ждёт LiteLLM и Analyzer до **1500 секунд** в обеих топологиях; тайм-аут
провайдера 60 секунд не меняется. Клиент и корпоративные посредники должны
допускать ожидание до первого ответа с запасом на вызов модели. SSE начинается
только после проверки; большой новый ввод не становится интерактивным.
Стандартный Compose подключает наш ASGI-адаптер перед штатной CLI LiteLLM.
Обнаруженный ранний обрыв отменяет предварительную обработку, не дожидаясь
бюджета; новая настройка не требуется. При обновлении нужно обычное
пересоздание контейнера, чтобы применить точку входа. Сетевой посредник может
задержать сигнал, а уже принятое Triton вычисление может завершиться.

Измерения и границы применимости: [отчёт этапа 3](research/release-040-followups.md#третий-этап-бюджет-предварительной-проверки-10-октября-2026).
Синтетический миллионный ввод не подтверждает такой контекст у внешней модели
или производительность для 400 пользователей.

## Балансировка и диагностика

Один Nginx распределяет запросы между LiteLLM и обращения к Analyzer по числу
активных соединений. Docker DNS обновляет состав пулов. Это пассивная
обработка сетевых ошибок, а не автоматическое исключение всех контейнеров со
статусом `unhealthy`. Переданные POST-запросы к модели не повторяются Nginx;
для анализа разрешены максимум две попытки при сетевой ошибке, `502` или `503`.
Потоковые ответы передаются без буферизации.
Оборванный поток не переносится на другую реплику: проверка отказа подтверждает
обработку нового запроса оставшимися экземплярами, не продолжение прежнего SSE.

В production порты `4000` и `5001` публикует Nginx, а не отдельные экземпляры.
Порты `80`, `2455` и `9090` сохраняют назначение; HTTP и метрики доступны только
в доверенной сети, сетевые ограничения остаются обязанностью оператора.

```bash
make logs STACK=litellm-presidio-codex-lb TOPOLOGY=production
make health STACK=litellm-presidio-codex-lb TOPOLOGY=production
make metrics STACK=litellm-presidio-codex-lb TOPOLOGY=production
make guardrails-smoke STACK=litellm-presidio-codex-lb TOPOLOGY=production
```

`health` проверяет каждый ожидаемый экземпляр и прогрев NER, а `metrics`
опрашивает каждую реплику отдельно. Для Prometheus нужны отдельные цели по
контейнерам: балансируемый `/metrics` не является суммой метрик пула.

## Переключение и остановка

На одном Compose-проекте выполните `up` с новой топологией либо изменённым
числом экземпляров. Обслуживание временно прерывается; базовые хранилища и тома
сохраняются. Возврат к `functional` выполняется так же. Имена Compose-проекта
и `ENV_FILE` менять нельзя, если требуется сохранить прежние данные.

```bash
make up STACK=litellm-presidio-codex-lb TOPOLOGY=functional
make down STACK=litellm-presidio-codex-lb TOPOLOGY=functional
```

`down`, `logs`, проверки и очистка должны указывать фактическую топологию.
Перед переходом с расширенного состава на базовый выполните `down` расширенного
состава без `-v`. `clean` намеренно удаляет данные и не используется для
переключения. Перед изменением production сохраните резервные копии обеих баз,
тома `codex-lb-data`, `.env` и сертификатов.

После `down` анонимный том локального Redis не подключается автоматически:
временный кэш и привязки маршрутизации будут утрачены. Для смены топологии,
политики и числа экземпляров используйте `up`/`restart`, а не `down` → `up`.
