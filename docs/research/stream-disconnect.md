# Сетевые Обрывы Потоковых Ответов

Этап 4 задачи #94, PR #95. LiteLLM 1.98.0 закреплена по версии и digest;
платформенных патчей нет. **Этап не закрыт:** собственная очистка усилена,
но раннее закрытие Router и синтетический `stop` требуют решения по платформе.

## Собственные Исправления

- Закрытие переданного итератора и удаление записи защищены от отмены ASGI.
  Каждая операция ограничена двумя секундами; ошибка закрытия не пропускает
  удаление. TTL 3600 секунд не изменён.
- Очистка защищена и от повторного прямого `asyncio.Task.cancel()`: отдельная
  задача дожидается завершения под защитой AnyIO/asyncio, затем сохраняется
  отмена вызывающего запроса. Модульные проверки подтверждают отсутствие
  оставшихся задач очистки.
- Отмена/ошибка загрузки сопоставления инициирует закрытие и удаление записи
  этого запроса. Подтверждённое отсутствие записи не требует DEL.
- Голый EOF не выдаёт недополученный плейсхолдер или JSON-escape как новое
  событие. Буферы очищаются при отмене. Настоящие завершающие события,
  служебные поля и `encrypted_content` сохранены.
- Незавершённый EOF отмечается `pii_guardrail_stream_incomplete` и
  `ru_pii_guardrail_post_calls_total{result="incomplete"}`. Синтетическое
  завершение платформы обработчик пока не может отличить от настоящего.
- Исправлена гонка тестового наблюдателя: отдельно ожидаются фактическое
  удаление записи и публикация отметки, без предположения об их атомарности.

## Нерешённые Дефекты

### Закрытие Router до первого чтения

В итоговом повторе четыре из 200 ранних отключений не закрыли соединение
провайдера за пять секунд. Сопоставления удалены. Диагностика обнаружила
также Responses-обёртку, а не только Chat Completions.

`FallbackStreamWrapper` и `FallbackResponsesStreamWrapper` закрывают внутренний
асинхронный генератор. Если он ещё не начал выполняться, `aclose()` не запускает
его `finally`, где Router закрывает исходный поток провайдера. Наш guardrail
вызывает доступный `aclose()`, но этого недостаточно.

Воспроизведение на настоящем Router без guardrails и без сети: для обоих API
закрытие обёртки **до чтения** не вызывает закрытие исходного итератора;
после первого чтения — вызывает. Сетевая диагностика наблюдала одну отмену:
повторная отмена не является причиной этой гонки. Отдельный тест настоящих
LiteLLM/OpenAI SDK/HTTPX подтверждал прерывание закрытия при повторном
`Task.cancel()`; этот механизм исправлен в нашем коде.

### Ложное завершение при EOF

Четыре случая Chat Completions: EOF текста внутри плейсхолдера или SSE-записи,
напрямую/через Nginx. Провайдер не отправил `finish_reason` или `[DONE]`, но
`CustomStreamWrapper._finalize_completed_stream()` вызывает
`finish_reason_handler()`, подставляющий `stop` при отсутствии причины.
Воспроизведение через `litellm.acompletion()` без наших callbacks также
получает `stop`. Наличие `[DONE]` само по себе не доказывает завершение.

## Решение Требует Согласования

Поток Router не предоставляет надёжного публичного признака происхождения
`stop` или ссылки на исходный незапущенный итератор. Защиту на основе кадров
генератора и внутренних флагов не включаем.

В просмотренных участках [Router 1.104.0](https://github.com/BerriAI/litellm/blob/v1.104.0/litellm/router.py)
и [обработчика потока](https://github.com/BerriAI/litellm/blob/v1.104.0/litellm/litellm_core_utils/streaming_handler.py)
сохраняются эти механизмы. Выпуск не устанавливался и целиком не тестировался;
само обновление пока не считается решением.

Предложены версионные патчи при сборке с проверкой исходников, без постоянного
форка, одинаковые в рабочих и тестовых образах. Требуется явное одобрение.
Критерии приёмки не ослаблены. Закрытие локального HTTP не гарантирует
остановку генерации/оплаты у внешнего провайдера. Временные ресурсы удаляются
после проверок; основной стенд, `.env`, сертификаты и `auth.json` сохраняются.
