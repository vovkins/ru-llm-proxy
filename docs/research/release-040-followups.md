# Разбор проверки v0.4.0 и план исправлений

Проверен `v0.4.0`, коммит `dd403a1`, на локальном Docker Desktop: ARM64,
10 CPU, 7,75 GiB памяти. Ниже разделены доказанные дефекты, ограничения
конфигурации и поведение внешней модели. Исходные диагностические результаты
сохранены локально; секреты и полные журналы не публикуются.

## 1. Старый контакт превращается в новый

**Дефект нашего guardrail-кода**, задача [#99](https://github.com/vovkins/ru-llm-proxy/issues/99).

Пример двух запросов к `/v1/responses`:

1. «Первый контакт — `alpha-contact@example.test`. Запомни его», `store=true`.
2. «Второй контакт — `beta-contact@example.test`. Повтори первый»,
   `previous_response_id=<идентификатор первого ответа>`.

Модель получает не адреса, а метки. В первом запросе первый адрес заменён на
`<EMAIL_ADDRESS_1>`; после ответа временная таблица замен удаляется. Второй
запрос не содержит исходной истории, поэтому у прокси нет старого адреса.
При этом счётчик нового запроса снова начинает с единицы: новый адрес тоже
получает `<EMAIL_ADDRESS_1>`. Старый контакт восстанавливается как новый.

Если во втором запросе нет нового адреса, старая метка остаётся нераскрытой.
Все четыре сочетания «новый адрес есть/нет» × `stream=false/true` не прошли,
хотя клиент получил HTTP 200. Четыре контроля с передачей полной истории
прошли: исходные значения снова доступны прокси.

Последствие — неправильный ответ, в том числе адрес или реквизит для
инструмента. Отправка исходных адресов внешнему провайдеру в этом опыте не
выявлена. Дополнительный CPU/RAM ошибку не исправит.

**Согласованное и реализованное решение:** ограниченные снимки таблиц замен
в Redis, изолированные по виртуальному ключу и модели, с неизменяемыми
родителями и продолжением нумерации. Владелец явно одобрил более длительное
хранение исходных значений. Временные `pii_mapping:*` очищаются как прежде;
при недоступной прежней версии требуется полная история. `encrypted_content`
не изменяется. Результаты этапа 2 приведены ниже.

## 2. Запрошенное имя модели недоступно подпискам

**Несоответствие активной конфигурации каталогу**, задача
[#100](https://github.com/vovkins/ru-llm-proxy/issues/100).

В проверяемом `v0.4.0` модели `gpt-5.4` и `gpt-5.4-mini` опубликованы в конфиге
LiteLLM, но отсутствуют в каталоге codex-lb. Запрос с `model=gpt-5.4-mini` получает
`503 no_plan_support_for_model`: codex-lb не выбирает аккаунт и не обращается
к внешней модели. Это не проблема SSE и не утверждение, что моделей вообще
нет у OpenAI.

По запросу владельца новые стандартные модели — `glm-5.3-flash` и
`gpt-6-luna`. Их доступность проверена 9 октября 2026 года:

| Проверка | Результат |
| --- | --- |
| GLM-5.3-Flash, первый Z.AI Coding Plan ключ, оба режима потока | 2/2 |
| GLM-5.3-Flash, второй ключ, оба режима потока | 2/2 |
| GPT-6 Luna, Chat Completions/Responses, оба режима, два повтора | 8/8 |
| Использование двух ChatGPT-профилей по журналу codex-lb | 6 и 2 успешных запроса |

Оба ChatGPT-профиля имеют статус `active`: ограничение повторной авторизации
из предыдущего отчёта снято. Четыре GLM-проверки выполнялись напрямую к Coding
Plan, восемь GPT-проверок — к codex-lb. Это подтверждение доступности, **не
полный прогон новых моделей через LiteLLM и guardrails**. Неравномерность 6/2
в малой выборке не свидетельствует о дефекте штатной балансировки.

Для первого этапа согласованы основной GLM-пул `glm-5.3-flash`, дополнительная
`glm-5.3`, основная GPT `gpt-6-luna` и дополнительные `gpt-6-sol`,
`gpt-6-astra`, `gpt-6.1-sol`. Исторические измерения не переписываются, старые
имена не перенаправляются молча на новую модель. Результат реализации — ниже.

У GPT-6 Luna есть отдельная проверка совместимости инструментов: официальный
API требует `reasoning_effort=none` для инструментов Chat Completions; для
Responses поддержка шире. Поведение OAuth-тракта необходимо проверить отдельно
([OpenAI](https://developers.openai.com/api/docs/models/gpt-6-luna)).
GLM доступна через Coding Plan
([Z.AI](https://zcode.z.ai/en/docs/configuration)); платный общий API вместо
подписки не используется.

## 3. Analyzer успевает обработать текст, но не за 30 секунд

**Вычислительная стоимость и рабочие тайм-ауты**, задача
[#101](https://github.com/vovkins/ru-llm-proxy/issues/101).

| Новый синтетический текст | Прямой Analyzer | Обычный прокси |
| --- | --- | --- |
| 50 000 слов, около 300 тысяч символов | успех за 35,37 с | 503 за 30,14 с |
| 128 000 слов, около 768 тысяч символов | успех за 97,88 с | стандартный бюджет анализа — 30 с |
| Миллион слов, около 6 млн символов | успех за 1039,35 с | полный тракт с реальной моделью не проверен |

Прокси ждёт Analyzer 30 секунд и безопасно останавливает непроверенный запрос.
Разбиение на части работает; оно ограничивает память и размер модельного окна,
но не отменяет вычисление всех частей. Пик рабочего набора Analyzer на
миллионном тексте был около 1,14 GiB, RSS — 1,59 GiB; OOM не наблюдался.

Накопленная история из уже проверенных неизменных полей — другой случай:
срабатывает кэш. Новый большой файл или изменение объединённого большого поля
требует анализа нового текста. В потоковом режиме первый ответ также должен
дождаться предварительной проверки; `stream=true` не обходит защиту.

Размеры здесь — слова генератора, не токены GPT. По одному измерению на размер
нельзя делать вывод о производственном p95 или работе 400 пользователей.
Рост RAM сам по себе это не ускорит. В прежних измерениях T4 ускоряла 50k
примерно вдвое, но часть Presidio оставалась на CPU
([результаты GPU](gpu-analyzer-benchmark.md)).

Сначала согласуем допустимое ожидание и измерим этапы существующим инструментом,
после — бюджет полного тракта и безопасные настройки. Не поднимаем все
тайм-ауты до 1800 секунд, не ослабляем `fail_closed` и не повторяем целиком уже
завершённые #55, #82 и #70. Для функциональных исправлений сервер сейчас не
нужен. Для независимого CPU-сравнения предварительный ориентир — выделенный
Linux x86_64 с 16–32 vCPU, 32–64 GiB RAM и SSD; аренда согласуется отдельно.
Промышленное распределённое подтверждение остаётся в #59.

## 4. Значение восстановлено, но модель ответила не по инструкции

**Неполная диагностика и наблюдаемое поведение GLM**, задача
[#102](https://github.com/vovkins/ru-llm-proxy/issues/102).

Пример: клиент просит «Ответь только этим адресом». Модель видит
`<EMAIL_ADDRESS_1>` и вместо его копирования пишет пояснение о незаполненном
шаблоне. Guardrail заменяет метку внутри пояснения исходным адресом. Адрес
восстановлен, но инструкция клиента не выполнена. Поиск адреса внутри ответа
не делает такой строгий тест успешным.

Другой пример: «Точно скопируй `Base64: <значение>`». Все 15 000 символов
значения восстановились, но в двух из четырёх попыток отсутствовала подпись
`Base64:`. Подпись — обычный текст, не часть таблицы замен; конкретная причина
её исчезновения пока не установлена. Один первоначальный короткий провал
также остаётся неразобранным: тело ответа не сохранено.

Это не основание угадывать удалённые значения или менять строгий критерий.
Сравним прямой ответ с синтетической меткой, ответ через LiteLLM и полный путь
маскирования; сохранённые тестовые ответы позволят локализовать изменение.
Повторим серию на новых моделях и обоих ключах/аккаунтах. Исправление кода
потребуется, только если обнаружено повреждение в нашем слое. Возможная
инструкция о неизменности меток сначала исследуется отдельно и не добавляется
во все рабочие запросы без согласования. Более мощный локальный сервер не
исправляет поведение внешней модели.

## Результат второго этапа, 9 октября 2026

Логика находится в `litellm_guardrails/responses_state.py` и хуках нашего
`pii_guardrail.py`; код LiteLLM/codex-lb не менялся. Учтены обе штатные формы
ID LiteLLM: маршрутизационная и шифрованная для клиента. Словарные замены с
другим исходным написанием получают отдельную метку вместо перезаписи родителя.

Новый успешный ответ получает срок `PII_MAPPING_TTL_SECONDS` (3600 секунд).
Наследуемые значения могут храниться дольше с каждым успешным ходом. Лимиты:
1 МиБ / 10 000 пар на снимок, 1024 ссылки / 32 МиБ сериализованных данных на
виртуальный ключ. HMAC скрывает имена Redis-ключей, но не шифрует значения.
Ошибки состояния не обходятся режимом `fail_open`: неизвестная версия — 409,
ошибка хранилища — 503, превышение размера — 413. Успешное завершение SSE
выдаётся только после сохранения связи.

Живой прогон сделал 28 успешных вызовов внешней модели. Журнал штатного выбора
codex-lb подтверждает обе подписки (по 9 событий выбора на каждую, продолжения
могут переиспользовать уже выбранное соединение); индивидуальные ключи подписок
не создавались. Все 12 потоковых случаев проверены также по тексту дельт,
не только финальному событию.
Защитный слой корректно восстановил первый и второй контакты. `store=false` с
продолжением подтверждён только для этого OAuth-тракта, не всех провайдеров.

При первоначальной квоте 128 ссылок / 16 МиБ проверка 500 чистых продолжений
на Redis дала один снимок, 128 ссылок и 22 187 байт

в широком предварительном прогоне; она не используется для итоговой приёмки.

оставлен работающим. Секреты, сертификаты и обе базы сохранены.

### Увеличение квоты для параллельных диалогов

По согласованию владельца квота увеличена до **1024 ссылок / 32 МиБ** на
виртуальный ключ, суммарно для всех его моделей и диалогов. TTL, предел
снимка 1 МиБ / 10 000 пар, изоляция и правила ошибок не менялись.
Агентская система должна хранить свой `previous_response_id` для каждого
диалога: общий ключ не запрещает доступ к другой допустимой ссылке владельца.

В существующий `make test-pre-egress-proxy` добавлены пограничные проверки.
Контракт Redis: **9/9**. 1280 чистых продолжений сохраняют один снимок,
1024 ссылки и 177 195 байт сериализованных значений. Проверены общий бюджет
двух моделей, конкуренция при заполненном индексе, TTL и вытеснение снимков
при достижении 32 МиБ; последний ответ остаётся доступен, удалённый получает 409.

| Операция | Число измерений | p95 со стороны клиента | Среднее время EVAL в Redis |
| --- | --- | --- | --- |
| Чтение при 1024 ссылках, малая таблица | 50 | 2,30 мс | 1,93 мс |
| Запись с вытеснением одной ссылки | 50 | 3,27 мс | 2,42 мс |
| Чтение почти предельного снимка при 1024 ссылках и около 31 МиБ | 30 | 6,57 мс | 3,17 мс |
| Массовое вытеснение 994 ссылок и освобождение снимка | 1 | 269,74 мс — одно измерение, не p95 | 264,69 мс |

Это локальный последовательный эксперимент: отдельный Redis ограничен
1 CPU / 192 МиБ, тестовый Python 3.13 — 1 CPU / 384 МиБ. Клиентское время
включает сериализацию, передачу и проверку результата. Lua-очистка атомарна и
на время исполнения задерживает другие команды Redis; массовое вытеснение
заметно дороже обычной операции. Эти числа не являются промышленным p95.

В состоянии после вытеснения осталось 32 509 665 байт сериализованных данных;
пик памяти изолированного Redis за эксперимент — около 39 МиБ. Лимит относится
к данным и индексу, не к физической памяти Redis. Для 400 полностью заполненных
ключей 12,5 ГиБ — только расчёт сериализованных данных, без служебных структур,
временных выделений памяти и остальных данных Redis. Такой предел и нагрузка
400 пользователей локально **не проверялись**; для функциональной приёмки
этого изменения дополнительный сервер не требуется.

После изменения повторно прошли 576 тестов guardrail, 617 управляемого потока,
383 статических и 18 проверок Make. `make test-pre-egress-proxy` прошёл,
включая 9 проверок Redis и 18 HTTP-проверок истории с текстом/инструментами и
обоими режимами ответа. Новые вызовы внешних моделей для изменения двух
лимитов не выполнялись; результаты живой приёмки этапа 2 выше сохранены.
Локальный LiteLLM пересоздан с новой квотой; Redis и базы не пересоздавались.
Основной состав 7/7 healthy, временные тестовые контейнеры удалены.

### Изменения нашего кода

- Один бюджет `PII_GUARDRAIL_ANALYZER_TIMEOUT_SECONDS` охватывает весь
  предварительный хук: загрузку истории, все поля, кэш и сохранение замен.
  Раньше HTTP-тайм-аут ограничивал отдельные операции; много полей могло
  последовательно занять существенно больше времени.
- Превышение даёт 503 `pii_preprocessing_timeout`, `retryable=false`, без
  `Retry-After` и вызова провайдера. Поля возвращаются в исходное состояние,
  собственная временная таблица удаляется; чужое состояние не затрагивается.
  Отказ остаётся безопасным и при `fail_open`.
- Общий анализ одинакового поля отменяется, когда не осталось ожидающих.
  Отмена одного запроса не прерывает соседний. Завершение процесса также
  закрывает активные задачи. Результат незавершённого анализа не кэшируется.
- Новая ограниченная метрика `ru_pii_guardrail_preprocessing_duration_seconds`
  разделяет успех, ошибку, бюджет и отмену. Содержимое запросов не публикуется.
  Существующий измеритель получил необязательный подсчёт текстовых токенов;
  новых Make-команд и переменных нет.
- Штатная отмена BERT больше не записывается как ошибка модели: Analyzer
  различает `NERInferenceCancelled` и настоящую ошибку вычисления. Алгоритм
  распознавания, модель и политика маскирования не менялись.

Бюджет кооперативный: сетевые ожидания отменяются, но синхронная обработка
прерывается только в доступных точках. Дополнительная проверка перед возвратом
не позволяет передать провайдеру результат, полученный после срока. Очистка
может добавить время ограниченной Redis-операции.

контекста каждой внешней моделью. Для 400 пользователей результат неприменим.

### Какие интервалы ограничены

| Участок | Текущее значение | Граница действия |
| --- | --- | --- |
| Клиент | Зависит от клиента; в штатной проверке 180 с | Может оборвать весь запрос раньше серверов; во время анализа SSE ещё не выдаётся |
| Nginx → LiteLLM / Analyzer | Чтение/отправка 600 с, соединение production 5 с | Интервал ожидания данных, не полный бюджет; большой новый ввод может превысить его до первого ответа |
| Guardrail | 30 с, HTTP-соединение 5 с | Вся предварительная обработка; не включает генерацию модели |
| Очередь Analyzer | 8 мест / 1 с / 1 активный запрос на процесс | Только ожидание места; 503 с динамическим `Retry-After` |
| LiteLLM → провайдер | 60 с, до 3 повторов | Провайдерская фаза после проверки, не весь предварительный анализ |
| codex-lb | Соединение 8 с; общий прокси 600 с; поток Responses/мост 7200 с | Начиная с поступления запроса в codex-lb, не включает работу Analyzer; применяется конкретным маршрутом |

Текущий `proxy_read_timeout=600s` не подходит для нового ввода, анализируемого
17 минут. Увеличивать только тайм-аут guardrail недостаточно. Провайдерское
время и клиентский предел нужно учитывать отдельно; все интервалы не следует
автоматически складывать или выставлять одинаковыми.

### Ограничение ранней отмены

LiteLLM 1.98.0 начинает штатно следить за отключением HTTP-клиента после
предварительного хука. В хук не передаётся объект HTTP-запроса или событие
отключения. При обрыве во время удерживаемого анализа работа не остановилась
немедленно, но новый бюджет 3 секунды во временном составе закрыл соединение
Analyzer примерно за 3 секунды. Провайдер не был вызван в этих случаях.

Если проверка завершится раньше бюджета после обрыва клиента, платформа может
успеть начать провайдерский вызов и затем отменить его. Это **не** гарантия
немедленной отмены по TCP или полного отсутствия такой попытки. Не добавляем
скрытую подмену платформы: устранение требует отдельного выбора интеграционного
подхода или штатного исправления LiteLLM. При увеличении бюджета незавершённый
запрос может дольше занимать Analyzer; ограничение необходимо согласовать.

### Отмена и перегрузка

При временном бюджете 3 с настоящий Analyzer проверен на обоих API и в обоих
режимах потока: четыре отказа 503 за 3,02–3,31 с. После HTTP-ответа вычислительное
место освобождалось ещё за 0,55–0,81 с. Провайдер не вызывался, NER оставался
`ready`, следующий короткий ответ восстанавливался точно; временных таблиц нет.
Синхронную часть нельзя прервать посреди вычислительной операции.

Во время миллионного анализа всплеск из восьми других запросов дал восемь
`queue_timeout`; всплеск из шестнадцати — восемь `queue_full` и восемь
`queue_timeout`. Все ответы — 503, примерно за 0,05–1,11 с; очередь оставалась
ограниченной и освобождалась. `Retry-After=237` рассчитан по предыдущей средней
длительности, не означает известное оставшееся время текущей работы. Повторы
тяжёлого ввода не выполняются скрыто самим guardrail; клиентские повторы
всё равно должны быть ограничены.

Изолированная проверка нормализации/токенизации на 50 000 повторениях слова
«данные» с рабочими параметрами токенизатора дала 0,363 / 0,197 с. Это отдельный
опыт, не разложение всего запроса и не измерение чистого времени BERT.

### Приёмка настроек остаётся открытой

Измерения поддерживают следующий **предварительный выбор**, не новую
конфигурацию: 240 с для обычной предварительной обработки на реплике с 4 CPU;
1200 с для установки, которой необходим редкий большой новый ввод, и 1500 с
ожидания Nginx в таком составе. Оба бюджета задаются существующей переменной
на весь процесс, не выбираются автоматически по размеру запроса. Для большого
ввода ориентир — не менее 8 CPU на реплику Analyzer: в миллионном опыте фактический
пик CPU составлял около 750%. Лимиты промышленной конфигурации ещё не меняются.
Клиент также должен допускать длительное ожидание до первого события с запасом
на провайдера. Предел провайдера 60 с, очередь 8/1 с и параллельность 1 пока
не меняются.

120 секунд недостаточно для проверенного 128k-поля, а ровно 1020 секунд — для
миллионного. Запас нужен, но один локальный опыт не гарантирует 20 минут на
любом CPU. Миллион на реплике с 4 CPU не проверен: успешный миллионный опыт
использовал до десяти доступных CPU. Подтверждение 8 CPU остаётся проверкой
профиля после выбора настроек, а не результатом уже завершённого измерения.
Статистическое подтверждение целевой машины и 400 пользователей не выполнено.

Перед применением значений требуется согласовать запас сверх ориентира
17 минут и ограничение раннего TCP-обрыва. Если ограничение неприемлемо,
отдельно выбирается поддерживаемый способ отмены в интеграционном слое;
подмена платформенного кода не добавляется. Этап 4 не начинается автоматически.
