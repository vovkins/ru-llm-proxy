# Расширение плотности

Продолжение: [подбор параллельности, пакетов и HTTP-пула](production-tuning.md).

2 ноября 2026, [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Выполнены все 36 сравнительных волн. Скоростной финалист при неизменных
настройках — 24 Analyzer / 12 Triton; 20/10 — менее затратный кандидат.
Это не утверждённые настройки production и не абсолютный предел сервера.
[Данные](../../presidio/evaluation/reports/production-density-expanded.json),
[предыдущее сравнение](production-overcommit.md).

## Условия

Тот же сервер: 32 vCPU (16 ядер с SMT), 62,79 GiB RAM, Intel Ice Lake,
Linux x86_64. Те же 382 исходных файла, образы и проверенный комплект Tiny2.
Провайдер тестовый, оба API с SSE; внешние LLM не вызываются.
Общие компоненты сохранены: два LiteLLM, Nginx, Redis, обе PostgreSQL,
codex-lb. Они не получают эквивалентную промышленную нагрузку.

У Analyzer по 1 CPU / 2 GiB, у Triton по 2 CPU / 4 GiB. Не менялись:
один процесс и два активных анализа на Analyzer; два экземпляра модели
на Triton; четыре окна в клиентском пакете; очередь 32, ожидание 45 с;
HTTP-пул 20/10 на цикл событий; максимум пакета Triton 32.

| Вариант | Analyzer / Triton | Сумма CPU-квот | Сумма лимитов памяти |
|---|---|---:|---:|
| R3, контроль | 12 / 6 | 35 | 82,25 GiB |
| R4 | 16 / 8 | 43 | 98,25 GiB |
| R5 | 20 / 10 | 51 | 114,25 GiB |
| R6 | 24 / 12 | 59 | 130,25 GiB |

Лимиты не являются резервированием. Защиты прежние: 90% лимита контейнера,
6 GiB доступной памяти хоста и OOM. Между составами вычислительные процессы
создавались заново; БД/Redis сохранялись. По три чередуемых повтора:
R3/R4/R5/R6, R6/R5/R4/R3, R4/R6/R3/R5. В каждом волны 32, 64 и 96
запросов по 32000 единиц генератора за две секунды. Это не токены внешней LLM.
Перед волной очереди освобождены, тестовый кэш очищен. Все хэши входов
между вариантами совпали; контроль 32 совпал с прежними тремя повторами.
Использовались прежние 64 виртуальных ключа: на 96 запросах есть параллельные
диалоги одного ключа. У каждого нового состава стандартный прогрев 4×1000.

## Задержки

p95 ниже — медиана трёх отдельных p95, не общий процентиль объединённых
ответов. Своевременность считается отдельно для каждого запроса: первый
точно восстановленный текст до 60 с и корректное завершение SSE.

| Вариант | p95: 32 / 64 / 96 запросов, с | До 60 с: 32 / 64 / 96 |
|---|---|---|
| R3 | 39,40 / 67,08 / 96,24 | 96/96; 164/192; 150/288 |
| R4 | 32,02 / 58,35 / 84,50 | 96/96; 191/192; 157/288 |
| R5 | 30,15 / 56,62 / 81,81 | 96/96; 192/192; 139/288 |
| R6 | 29,91 / 53,91 / 79,51 | 96/96; 192/192; 156/288 |

Все 2304 сравнительных ответа восстановлены точно; до минуты 1725/2304.
С прогревами — 2352/2352 корректны, 1773/2352 своевременны, по 1176 на API.
HTTP 503, нарушений восстановления, утечек маркеров провайдеру и целевых
ошибок маршрутизации Nginx нет. Опоздания не исключены. В частности,
R5 не лучше R3/R4 по числу своевременных ответов на 96 запросах, несмотря
на меньший p95. Один агрегированный процентиль скрывал бы это расхождение.
Максимальная задержка старта генератора — 49 мс. Обработано 83 976 108
токенов NER / 264 600 окон, включая прогревы.

## CPU И Память

CPU всего хоста рассчитан по `/proc/stat`, без двойного учёта guest.
Среднее взвешено по интервалам внутри сравнительных волн. Пики — максимумы
наблюдаемых интервальных средних, не мгновенные значения. RAM — наибольшая
снятая сумма `memory.current` состава, не строго одновременный пик всего хоста.

| Вариант | Среднее CPU | Пик CPU из 32 | Интервал пика | RAM состава |
|---|---:|---:|---:|---:|
| R3 | 15,17 | 20,83 (65,1%) | 3,45 с | 13,06 GiB |
| R4 | 21,03 | 29,59 (92,5%) | 3,37 с | 16,47 GiB |
| R5 | 23,20 | 31,72 (99,1%) | 2,99 с | 20,05 GiB |
| R6 | 25,34 | 31,76 (99,2%) | 3,46 с | 22,63 GiB |

Интервалы измерений во время волн 2,11–6,05 с; более короткие пики неизвестны.
Неверных интервалов CPU нет. Короткие пики отдельных контейнеров по общей
метке времени не вычислялись: cgroup читаются последовательно.
Минимум доступной памяти хоста 38,24 GiB; OOM, достижения лимитов и
защитных остановок нет. `memory.stat` сохранён во всех 29 266 строках.
Были 13 пропусков из 13 460 опросов очередей в клиентских волнах;
выборочные максимумы очереди не являются её непрерывным измерением.
Ещё 28 сбросов соединения статистики Triton относятся к смене контейнеров
вне клиентских волн, не к отказам запросов. Пропуски сохранены в JSON.

Выборочный максимум активных/ожидающих полей Analyzer: R3 — 24/17,
R4 — 32/9, R5 — 40/0, R6 — 41/0. Эти суммы сняты неатомарно;
нулевая очередь не исключает ожидания перед HTTP-пулом. Реально исполнялись
пакеты до 12 у R3–R5 и до 8 у R6, не максимальные разрешённые 32.
Достижение CPU-квот отдельными контейнерами также осталось в данных;
низкое среднее потребление не доказывает отсутствия ограничений в пике.

## Вывод

12/6 не был пределом переподписки. Измеренный полезный диапазон для
дальнейшей настройки — 20/10–24/12. R6 даёт лучшие медианные p95 всех
трёх волн, но переход R5 → R6 добавляет 20% вычислительных контейнеров
ради 4,8% снижения медианного p95 на 64 запросах. Оба уже используют
практически все логические CPU в наблюдаемых пиках. Продолжать простое
увеличение плотности сейчас менее обоснованно, чем настраивать C/I/B/HTTP.
Абсолютный предел не установлен: сохранялись прежние ограничения подачи,
и более плотные составы не проверялись. Наличие свободной RAM не равно
запасу пропускной способности. Ни один состав не принял всю волну 96 до минуты.

Для следующего подбора предлагаем R6 как скоростной финалист, R5 как
ресурсное сравнение. До production остаются настройка параллельности,
пакетов/HTTP-пула, постоянная подача, смешанные истории, большие файлы,
отмены/отказы и проверка состояния 400 пользователей. Новые длительные
серии R5/R6 в эту матрицу не входили. Двухузловая схема согласуется отдельно.

Все 12 запусков прошли, но прежний сбой готовности не объявляется исправленным.
Собственных повторов волн и принудительных reload не добавляли. Исторические
JSON сохранены. После прогона вычисления сервера остановлены с кодом 0,
БД/тома сохранены, основной локальный стенд 8/8 healthy. Прошли 102 проверки
частной обвязки и 136 адресных тестов локально и на Linux; локально также
804 статические, 869 проверок защитной обработки и 32 проверки Make.
Наборы пересекаются. Платформы и стандартные production-настройки не менялись.
