# Разрыв Связи: Почему Запрос Ждал 90 Секунд

4 ноября 2026, TWO-NODE-LINK-01 из [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
[Двухузловой прототип](production-two-node-design.md),
[данные диагностики](../../presidio/evaluation/reports/production-two-node-link-diagnostic.json).
**Причина воспроизведена; исправление ещё не согласовано и не реализовано.**

## Результат

Выполнены ровно три клиентских запроса, без повторов, на прежнем отдельном
сервере с настоящими Analyzer/Triton и синтетическим провайдером.
Платформы, модель, guardrail и production-настройки не менялись.
Пассивно сохранены ответы, фазы исходного клиента Probe, журналы компонентов,
TCP-состояния и 27 пакетов только испытательной связи. Тела, заголовки и адреса
не публикуются; исходные неуспехи остаются в первом отчёте.

| Запрос | Связь | Результат |
|---|---|---|
| Chat без stream | Исправна | 200, точное восстановление, 0.760 с |
| Chat без stream | Разорвана | 200 через местный пул, 0.278 с |
| Responses со stream | Разорвана | Клиентский TimeoutError через 90.091 с, заголовков и тела нет |

Провайдер получил только два успешных замаскированных запроса и не увидел
исходный контрольный телефон. У неуспешного запроса не началась ни генерация,
ни обработка SSE: клиент остановился в `headers_wait`.

## Установленный Механизм

1. Перед анализом наш `_prepare_analysis_cache_context` вызывает
   `_get_analyzer_signature`: `GET /api/v1/health` подтверждает готовность и
   подпись поведения Analyzer перед использованием кэша в данном сценарии.
   Это проверка готовности, не запуск NER на тексте.
2. Центральный Nginx направил GET к вычислительному Nginx B по сохранённому
   HTTP/TCP-соединению, ранее успешно использованному контрольным запросом.
3. После отключения B от испытательной сети соединение осталось `ESTAB` у A.
   Запись пакетов показывает повторную передачу 131 байта без ответных пакетов;
   `ss` подтверждает неподтверждённые данные и до 1310 повторно переданных байтов.
4. Соединение не устанавливалось заново, поэтому `proxy_connect_timeout=5s`
   не ограничивал ожидание ответа. Общий `proxy_read_timeout=1500s` применялся
   и к короткой проверке здоровья. Наш общий HTTP-клиент использует 240 с,
   отдельного короткого срока у `_get_analyzer_signature` нет.
5. Клиентский предел 90 с наступил раньше. Nginx записал 499 и отсутствие
   заголовков на входном `/v1/responses` и на внутреннем GET здоровья.
   LiteLLM/guardrail зафиксировал уход клиента. Для этого request ID в журналах
   Analyzer нет анализа текста; вызова провайдера также нет.

Это воспроизведённое ожидание транспорта **до анализа и до SSE**, а не ошибка
распознавания, восстановления плейсхолдера или разбора SSE измерителем.
Снимки очередей во время опыта не показали ожидающих анализов.
Это не доказывает, что каждый прежний таймаут имел ту же причину.

Nginx хранит простаивающие соединения для повторного использования;
`proxy_read_timeout` ограничивает паузу чтения, а не установление соединения
([keepalive](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive),
[read timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)).
В опыте применялся Nginx 1.27.5; новые умолчания других версий не проверялись.
По исходному коду общий бюджет guardrail составляет 240 с; его фактического
истечения не ждали. 90 с — предел испытательного клиента, не таймер сервера.

## Предлагаемый Следующий Опыт

Сначала проверить вариант **только с конфигурацией испытательного Nginx**,
не добавляя собственного платформенного кода или новых env-параметров:

1. Выделить `GET /api/v1/health` в управляющий маршрут с короткими сроками
   соединения/ожидания и ограниченным общим временем переключения. Кандидат
   ожидания ответа — 5 с; согласованность сроков уточнить по A/B, не выдавать
   его за проверенное production-значение.
2. Для GET разрешить ограниченное сетевое переключение на оставшийся пул при
   ошибке соединения, таймауте или 502. Не повторять семантический 503 и не
   менять политику POST анализа или запрет повтора принятого Triton inference.
   Использовать тот же пул адресатов, чтобы отказ связи учитывался балансировщиком.
3. Не сокращать бюджет больших текстов, не отключать проверку подписи и не
   использовать старую подпись как разрешение передать необработанный текст.
4. Повторить трёхзапросный сценарий, затем проверить оба API/stream-режима,
   здоровый всплеск и незавершённые отказные сценарии: отдельный Triton,
   возврат связи, остановка/возврат второго пула. Сохранить точность
   восстановления, контроль провайдера и очистку Redis. Успешный GET не
   гарантирует сохранность связи при последующем POST: этот случай проверяется
   отдельно; новый неуспех сначала выносится владельцу.
5. Если конфигурационного варианта недостаточно, отдельно предложить короткий
   бюджет health-запроса в нашем guardrail. Не менять несколько механизмов
   одновременно и не патчить LiteLLM/Presidio/Triton.

Этот план требует отдельного согласования. Промышленную двухузловую схему и
пункты 6/7б/8б не считать принятыми по результату диагностических трёх запросов.

Временные ресурсы удалены; 44 прежних серверных контейнера сохранили ID,
образы и состояние, локальный стенд не менялся. Четыре регрессии записи
подтвердили неизменность байтов/ошибок и запрет четвёртого запроса; три регрессии
оценщика защищают от ложного вывода о повторном использовании соединения.
