# Очереди и короткие всплески запросов

Дополнение к [Э10](tiny2-capacity.md), 27 октября 2026 года.
Ниже сохранён снимок эксперимента до изменения стандартных значений.
После согласования 2 активных / очередь 32 / ожидание 30 с включены в оба
[стандартных профиля](../deployment.md#стандартные-профили); сами измерения
и их ограничения не менялись.
Цель: 10–20 запросов за две секунды, допустимое ожидание обычного запроса до 60 секунд.
**Промышленные настройки не изменены; качество Э9 и ёмкость на 400 пользователей не приняты.**

## Что именно ставится в очередь

Очередь HTTP-запросов Analyzer уже есть в `main`, это не новая возможность PR #109.
Она отдельная для каждого процесса: по умолчанию один активный анализ, восемь ожидающих и ожидание до одной секунды.
Один элемент — одно текстовое поле, не весь диалог. Активный анализ удерживает место до конца текста, включая все его окна.
Это ожидание в памяти работающего процесса, не надёжное фоновое задание и не очередь Redis.

Перед ней возможна ещё одна задержка: пул HTTP-соединений LiteLLM к Analyzer, по умолчанию 20 на цикл событий.
Далее находятся очередь и пакетная обработка Triton. Задержка формирования пакета 1 мс не ограничивает ожидание пользовательского запроса.
Общий бюджет защитного слоя включает все поля, кэш, ожидание соединений и анализ, но не генерацию внешней LLM.
Очередь ограничена числом запросов, не суммарным объёмом текста; увеличение её размера не добавляет CPU.

## Условия

Docker Desktop ARM64: 10 CPU, 7.75 GiB. Изолированные последовательные прогоны, настоящие LiteLLM/guardrails/Analyzer/Redis/PostgreSQL/Nginx;
у кандидата один Triton CPU FP32, два экземпляра Tiny2, пакет окон 4. Образы и модель закреплены SHA из Э10.
Бюджет анализа: `main` — Analyzer 4 CPU; кандидат — Analyzer 2 CPU + Triton 2 CPU. LiteLLM отдельно 2 CPU/1.5 GiB.
Служебные лимиты снижены под локальную память; это не рекомендации для промышленной установки.

Провайдер имитируется, реальные подписки не используются. Успех означает HTTP 200, завершённый протокол и точное восстановление контрольного значения.
Провайдер не должен получить его открытым. Оба API и обычные/потоковые ответы равномерно чередуются.
Времена начала заданы независимо от завершения предыдущих запросов; фактическая задержка старта записана.
Размер — слово синтетического генератора, **не токен LLM**. Нейтральный текст содержит контрольный EMAIL_ADDRESS; качество остальных классов здесь не оценивается.

## Размер и время ожидания

Один Analyzer, один активный анализ. Ввод без результата в кэше; модель предварительно загружена.

| Очередь / ожидание | Всплеск | Успешных | p95 успешных |
|---|---|---:|---:|
| 8 / 1 с | 16 одновременно, по 1k | 7/16 | 1.15 с |
| 32 / 1 с | 16 одновременно, по 1k | 7/16 | 1.23 с |
| 64 / 1 с | 16 одновременно, по 1k | 7/16 | 1.21 с |
| 64 / 5 с | 20 за 2 с, по 8k | 6/20 | 6.29 с |
| 64 / 15 с | То же | 14/20 | 16.22 с |
| 64 / 30 с | То же | 20/20 | 21.92 с |
| 64 / 60 с | То же | 20/20 | 22.01 с |

Одно увеличение длины очереди заменяет `queue_full` на `queue_timeout`, но не устраняет отказы.
Ожидание 30 с в этой смеси оказалось достаточным; 60 с дополнительного выигрыша не дало.
При 64 коротких одновременных запросах и ожидании 5 с все прошли, но полное время достигло 10.31 с:
часть задержки возникает до очереди Analyzer. Это не нарушение её пятиисекундного таймера.

Отдельный контроль неизменённого `main` с BERT, Analyzer 4 CPU:

| Очередь / ожидание | Успешных 10 x 1k | Успешных 20 x 1k | Максимум на 20 x 1k |
|---|---:|---:|---:|
| 8 / 1 с | 3/10 | 2/20 | 2.65 с среди успешных |
| 32 / 30 с | 10/10 | 20/20 | 27.62 с |

Все волны поступали за 2 с. При тех же 32 / 30 с для десяти новых текстов по 8k прошли только 3/10.
Следовательно, настройка очереди полезна и без миграции модели, но не устраняет недостаток вычислительной ёмкости.

## Параллельность при одинаковых CPU

Ожидание 30 с, суммарная очередь 64, один и тот же Triton 2 CPU / два экземпляра модели.
Все перечисленные волны прошли без ошибок.

| Analyzer | CPU Analyzer | 20 новых по 8k: p95 | Один новый 50k + 20 коротких: p95 | Два новых 50k + 20 коротких: p95 |
|---|---:|---:|---:|---:|
| Один, один активный | 2 | 21.98 с | 9.15 с | 17.41 с |
| Один, два активных | 2 | 15.92 с | 2.27 с | 12.06 с |
| Два, по одному активному | 2 x 1 | 12.67 с | 8.59 с | 9.97 с |

В смешанных волнах p95 относится ко всей волне, включая большие запросы, а не только короткие.
Вариант с двумя активными анализами лучше защищает короткие запросы от одного большого; при нескольких больших преимущество меняется.
Выборочные пики очереди: 19/18 ожидающих у одного Analyzer; у двух — до девяти на каждой реплике.
Это наблюдения раз в 100 мс, не доказательство строгого максимума или одновременной суммы независимых пиков.

## Основной сценарий и границы

Один Analyzer 2 CPU, два активных анализа, очередь 32, ожидание 30 с; Triton 2 CPU / два экземпляра.

- 10 и 20 запросов за 2 с, размеры 1k и 8k, по три повтора: **180/180**; максимум на 20 x 8k — 17.00 с.
- Мгновенные 64 x 1k: **64/64**, максимум 7.75 с. Здесь очередь 32 не хуже 64 благодаря ограничивающему HTTP-пулу; несколько процессов LiteLLM изменят это соотношение.
- Три короткие волны по 20, начала через 1 или 5 с: **120/120**; максимумы 3.57 и 0.91 с.
- Четыре предварительно прогретых сообщения по 50k, затем 20 параллельных запросов одного ключа с одним из этих сообщений и новым 1k: **20/20**, максимум 0.86 с. Это не двадцать полностью новых историй.
- 20 новых текстов по 50k за 2 с: **6/20**, остальные — `queue_timeout`. Большие новые файлы требуют другого запаса вычислений/ожидания; этот профиль не гарантирует для них 60 секунд.

Кандидат для настройки **этого** локального профиля, не новые значения по умолчанию:

```dotenv
PRESIDIO_ANALYZER_CONCURRENCY_LIMIT=2
PRESIDIO_ANALYZER_QUEUE_LIMIT=32
PRESIDIO_ANALYZER_QUEUE_TIMEOUT_SECONDS=30
```

Увеличивать число процессов без измерений памяти не требуется.
Пул соединений и бюджеты клиента/Nginx/guardrail должны оставлять время на ожидание **и** собственно анализ, а при живом провайдере — ещё и генерацию.

## Отказы, повторы и отмена

| Контроль | Результат |
|---|---|
| Перегрузка | `analyzer_overloaded`, причины `queue_full` / `queue_timeout`, HTTP 503 и `Retry-After` |
| Остановка единственного Triton | 4/4 `required analyzer unavailable`, провайдер не вызван; после возврата 4/4 успешных |
| Общий бюджет 2 с при очереди 30 с | 7/8 `time_budget_exceeded`, провайдер получил только один успешный запрос |
| Один повтор с `Retry-After` и задержкой 0–2 с | Из 32 исходных запросов сначала прошли 8; из 24 повторов — 18. Итог **26/32**, не 26/56 пользователей |

Повтор допустим ограниченно для подтверждённой перегрузки до вызова провайдера, с учётом оставшегося клиентского бюджета.
Повторять все 503 немедленно опасно: это увеличивает очередь и не устраняет недоступность модели.
Внутренний Nginx может повторять чистый анализ на другой реплике; POST-инференс Triton и LLM в этих прогонах автоматически не повторяются.

**Исторический результат Э10, до исправления отмены:** отмена 10 ожидающих клиентов из 20 дала 10 успешных ответов и 10 вызовов провайдера,
но Analyzer завершил все 20 анализов. Отмена ещё четырёх клиентов в смешанной волне также не дала лишних вызовов провайдера.
Очереди в итоге опустели, последующие две волны — 20/20, активных `pii_mapping:*` после контроля нет.
Это подтверждает восстановление работоспособности, **но не немедленное освобождение вычислительной ёмкости**.
Точное место задержки отмены между LiteLLM, guardrail и Nginx не локализовано; рабочий и платформенный код не менялись.
Следующий отдельный разбор: сопоставить отмену по участкам цепочки и обоим API, проверить отмену единственного ожидающего и совместный кэш,
затем согласовать минимальную правку нашего интеграционного кода/настроек с регрессиями. Уже принятые вычисления Triton не обязаны прерываться мгновенно.

### Исправление отмены, 28 октября 2026

Причина локализована в LiteLLM 1.98.0: штатное наблюдение за отключением
начинается после предварительного guardrail. Наш ASGI-адаптер подключается
публичным `app.add_middleware` перед штатной CLI; платформенные файлы не меняются.
Ни тело целиком, ни ответ в адаптере не буферизуются. Новых настроек нет.

Повторены 40 диагностических сценариев и 16 обычных API/stream-контролей
на одном и двух экземплярах компонентов. [Краткий отчёт](../../presidio/evaluation/reports/tiny2-cancellation.json).

| Контроль | После исправления |
| --- | --- |
| Волна 20/10, состав 1/1/1 и 2/2/2 | В каждом случае 10 ответов, 10 вызовов провайдера, 10 завершённых анализов и один уже начатый прерван |
| Ограниченный HTTP-пул, оба API × stream | Два здоровых анализа; отменённый третий не запускается |
| Общий анализ | Один ушёл — второй получает ответ; ушли оба — анализ прерывается |
| Готовый кэш | Повтор без нового анализа, точное восстановление |
| Смешанная волна без отмен, 2/2/2 | 20/20, обе реплики каждого компонента участвовали |

Отдельное историческое `analysis_deadline_exceeded` (CANCEL-OBS-01) не повторилось
в трёх контролях очереди без отмены; причина остаётся неизвестной. Немедленная
остановка Triton и своевременный сигнал от любого посредника не гарантируются.
Это проверка отмены, не доказательство ёмкости на 400 пользователей.
Регрессии входят в существующие `make test-guardrail` и
`bash tests/e2e/test_nonstream_disconnect.sh`.

## Выводы и воспроизводимость

Очередь действительно сглаживает короткие всплески, если её ожидание соответствует времени обслуживания.
Для пользовательского сообщения «503 pii guardrail unavailable» причина без точного тела ошибки, журналов и метрик **не установлена**:
контрольная недоступность NER и переполнение очереди дают разные диагностические признаки.
На промышленном стенде нужны точное тело ошибки и связанный `request_id`, счётчики отказов по `reason`,
`capacity_active`/`capacity_waiting`, ожидание очереди и состояние NER. Одна строка HTTP 503 не отличает эти случаи.
Длительная нагрузка выше вычислительной ёмкости, множество новых больших файлов и 400 пользователей остаются отдельными испытаниями.
Потери покрытия Э9 не исправлялись и не принимаются этим отчётом.

Данные: [JSON](../../presidio/evaluation/reports/tiny2-queues.json), включая все попытки, p50/p95/p99 отдельно для успехов и всех исходов,
счётчики причин, фактический старт, ожидание, ресурсы и закреплённые образы.
Пики ресурсов измерены раз в две секунды, без памяти генератора на хосте, не являются рекомендуемыми лимитами.
В группе основных/аварийных проверок наблюдаемые пики одного Analyzer/Triton/LiteLLM — примерно 516/692/1128 MiB;
это независимые пики, не одновременное потребление и не предел памяти на миллионных файлах.
Измеритель [`burst_probe.py`](../../tests/load/burst_probe.py) принимает только ограниченные волны и сохраняет разрешённые поля без ключей/тел;
он использован с существующим изолированным `tests/load/docker-compose.yml`. Его регрессии входят в существующий `make test-flow`, новых Make-команд нет.

Всего 81 волна / 1995 попыток: 1691 успех, 279 намеренных отказов перегрузки, четыре отказа при остановленном NER,
семь отказов по двухсекундному бюджету и 14 отмен. Провайдер получил ровно 1691 запрос, открытого контрольного значения не видел.
Эти числа включают повторы и аварийные сценарии; их нельзя выдавать за долю ошибок обычной эксплуатации.

После измерений `make test test-recognizer-api test-ner-evaluation test-observability-gates`:
6436 выполнений pytest без ошибок, включая шесть тестов измерителя; наборы частично пересекаются. Проверка diff прошла.
Основной `main@1c8c78d` восстановлен: прежние семь контейнеров healthy, тома и защищённые файлы сохранены,
новых контейнеров/сетей/томов нет. Сверены 39 исполняемых файлов и шесть файлов модели, пять проверок Analyzer API — успешны.
