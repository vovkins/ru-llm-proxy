# Два Вычислительных Узла: Выбор Схемы

4 ноября 2026, пункт 5 [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Основа: v0.6.0, `7587d02`. **Исследование, не инструкция развёртывания.**
Схема требует отдельного принятия владельцем перед реализацией пункта 6.
Одноузловой production 2 LiteLLM / 24 Analyzer / 12 Triton не изменён.

## Сравнение

| Свойство | Общий Triton | Локальные пулы |
|---|---|---|
| Вход в анализ | Центральный Nginx видит каждую реплику обоих узлов | Центральный Nginx выбирает один из двух равноправных входов, затем местный Analyzer |
| Исполнение NER | Любой Analyzer обращается через первый сервер к любому Triton | Analyzer обращается к Triton своего узла |
| Nginx на втором узле | Не нужен; нужны адреса отдельных Analyzer/Triton | Один внутренний Nginx, без пользовательской админки |
| Межузловые данные | Исходное текстовое поле, разметка, тензоры и logits | Исходное поле и разметка, без межузловой пересылки окон модели |
| Изменение плотности | Обновление списка опубликованных адресов реплик | Изменение локального пула; межузловой адрес остаётся прежним |
| Разрыв связи | Может затронуть обращения модели с обоих узлов | Местное исполнение модели не зависит от другого узла |
| Недостаток | Больше связей, портов и зависимости от центрального маршрута модели | Дополнительный Nginx и двухуровневая балансировка |

В обоих вариантах первый сервер сохраняет Nginx, LiteLLM, Redis, обе PostgreSQL,
codex-lb и собственный вычислительный пул. Второй содержит только вычисления и,
для локальной схемы, внутренний Nginx. Репликации БД и отказоустойчивости первого
сервера этот этап не добавляет; администрирование и состояние остаются едиными.

Потоки вызовов; ответы возвращаются по тем же соединениям:

```text
Общий пул:
LiteLLM A -> Nginx A:5001 -> Analyzer A или B
Analyzer A или B -> Nginx A:8000 -> Triton A или B

Локальные пулы:
LiteLLM A -> Nginx A:5001 -> местный вход A -> Analyzer A -> Nginx A:8000 -> Triton A
                         -> Nginx B:5001 -> Analyzer B -> Nginx B:8000 -> Triton B
```

Разные порты Nginx A принадлежат одному процессу; это не новые контейнеры.

## Методика

Разрешённый сервер: 32 vCPU / 62.79 GiB, Linux x86_64. Два независимых
Compose-проекта: по 2 Analyzer / 1 Triton; в первом дополнительно 1 LiteLLM,
одноразовые PostgreSQL/Redis и тестовый провайдер. Analyzer 1 CPU / 2 GiB,
Triton 2 CPU / 4 GiB; C2/I2/B4, Q32/W45, HTTP20/10, бюджет 240 с.
Исходные файлы получены через Git archive; хэши рабочего Analyzer и комплект
экспорта сверены. Подписки, `.env` и сертификаты не переносились.

Сети проектов отдельные, связаны только испытательной внутренней сетью.
Это **не два физических Docker-хоста**: здесь нет проверки опубликованных
межсерверных портов, firewall, независимых CPU/RAM и сети 10 Гбит.
Адреса Docker используются только внутри прототипа, не предлагаются для production.
На двух серверах нужны явные адреса хостов и опубликованные внутренние порты;
обычная bridge-сеть Compose не объединяет хосты ([Docker](https://docs.docker.com/compose/how-tos/networking/)).

Запуск включает оба API и stream false/true, точное восстановление, проверку
перехваченного запроса провайдеру и очистки временных замен Redis, волну 20 новых
входов около 8k единиц по пробелам за 2 с и отказные проверки. Это не токены LLM.
Первое сравнение выполнено в MASK; последующий исправительный опыт также
проверил BLOCK. Полный промышленный состав относится к пункту 6.
Внешние модели не вызываются: для выбора внутреннего маршрута достаточно
тестового провайдера с контролем исходных данных.

Две первоначальные попытки не считаются сравнением: первая остановилась до
запросов из-за пересечения автоматически выделенных сетей; во второй общие
служебные DNS-имена ошибочно указывали на второй проект. Артефакты сохранены.
Исправлена только обвязка: явные непересекающиеся подсети и уникальные имена узлов.

## Результаты

[Данные](../../presidio/evaluation/reports/production-two-node-design.json).
До измерений подтверждён доступ к каждому адресату, иначе успешный ответ мог
бы скрыть работу только одного узла. В здоровом сравнении — по 28 запросов:
8 протокольных и 20 новых во всплеске. Все восстановлены точно, тестовый
провайдер не получил исходный контрольный телефон, временные замены удалены.

| Здоровый всплеск | Общий Triton | Локальные пулы |
|---|---:|---:|
| Успехи / до 60 с | 20/20 / 20/20 | 20/20 / 20/20 |
| Полей обработали Analyzer узлов A/B | 10/10 | 10/10 |
| Запросов исполнили Triton A/B | 69/71 | 70/70 |
| p50 / p95 первого восстановленного текста, с | 8.870 / 11.765 | 9.696 / 11.940 |
| Максимум, с | 12.320 | 12.056 |
| Пик активных / ожидающих анализов | 8/12 | 8/12 |

По одному прогону без перестановки порядка недостаточно для вывода о скорости.
Очередь действительно принимала всплеск, но её предельный размер не испытывался.
У общего варианта весь модельный HTTP проходил через Nginx A; у локального
вызовы модели наблюдались в обоих местных Nginx. Учтённые HTTP-байты включают
прогрев и разные дополнительные проверки: это не сравнение сетевой пропускной
способности и не измерение передачи по физическому каналу 10 Гбит.

Дополнительно локальная схема прошла остановку одного Analyzer (8/8) и его
возврат (4/4). При разрыве связи второй узел самостоятельно обработал анализ
через местный Nginx и Triton. Но через общий вход отказный опыт **не пройден**:
4/8 успехов, 2/8 HTTP 503, 2/8 таймаута клиента. Поэтому общий статус локального
испытания в JSON — `failed`, несмотря на успешные независимые проверки.

Ранний общий опыт после исправления коллизии имён, но ещё без проверки полноты
маршрутов, также дал два таймаута: 2/8 успехов и 4/8 HTTP 503. Начальные обычные
запросы тогда шли только в Analyzer A до обновления DNS; этот опыт сохранён
как наблюдение, не как сопоставимое A/B. Здоровый общий прогон повторён с
обязательным подтверждением всех четырёх Analyzer; спорный отказ не повторялся.

**TWO-NODE-LINK-01:** два клиента каждой отказной волны не завершились за 90 с.
В локальном опыте затронуты обычный Chat и Responses SSE; в раннем общем —
Responses SSE. 90 с — предел измерительного клиента, не доказанный таймаут
компонента. Изначально причина не была установлена. Последующая согласованная
[диагностика трёх запросов](production-two-node-link-diagnostic.md) воспроизвела
ожидание `GET /api/v1/health` по сохранённому соединению к отключённому узлу,
до анализа текста и до SSE. Последующий согласованный [исправительный опыт](production-two-node-health-fix.md)
прошёл исходные три запроса. Прежний отдельный
504 после 5 с не объясняет автоматически все зависшие запросы.
Исходный маркер у провайдера не обнаружен, но это не превращает таймаут в успех.

В исправительном опыте здоровый всплеск прошёл 20/20, режимы MASK/BLOCK — 8/8
и 4/4; отказ/возврат отдельного Triton и целого второго проекта проверены с
допустимыми защитными 503. Но последующий разрыв связи дал 6/8 успехов и два
таймаута уже на POST анализа: **TWO-NODE-LINK-02**. Для одного подтверждён
успешный местный health непосредственно перед отправкой POST к отключённому B.
Возврат связи и финальная проверка остановлены до согласования следующего
опыта. Рабочий код, платформы и критерии не менялись. Пункт 5 не объявляется
полностью принятым, а 6/7б/8б остаются открытыми. Исходные неуспехи не удалены.

После опытов все временные контейнеры, сети и тома удалены; 44 прежних серверных
контейнера сохранили ID, образы и состояние. Локальные восемь контейнеров не
останавливались. Частные регрессии с диагностикой и исправительным опытом: 26; штатные статические
проверки: 820 и 32 проверки Make на серверном Python 3.12.
Первый локальный запуск блокировала песочница, затем обнаружена несовместимость
теста `asyncio.Condition` с местным Python 3.9; эти попытки не названы успешными.

## Очереди И Распределение

Центральной очереди здесь нет. Сначала запрос может ждать HTTP-соединение
guardrail (20 на цикл событий), затем место в Analyzer (2 активных / 32 ожидающих
на процесс, ожидание до 45 с), затем исполнение Triton (два исполнения модели,
очередь до 64 запросов модели, срок по умолчанию 60 с с ограничением бюджетом).
Место Analyzer занимает текстовое поле, а запрос Triton — пакет окон,
не пользовательский диалог. Сумма мест не является ёмкостью пользователей.

Nginx `least_conn` учитывает соединения и веса, не реальные очереди модели.
В локальной схеме два входа в пулы должны быть однотипными; нельзя сравнивать
один адрес удалённого пула с 24 отдельными локальными репликами. Очередь Nginx
`queue` не используется: в применяемой открытой версии нет этого коммерческого
механизма ([Nginx](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)).
Разница ёмкости учитывается весами после измерений; веса не обеспечивают
немедленного перераспределения при любой внутренней перегрузке.

HTTP-пул остаётся 20/10. Два вычислительных сервера сами по себе не расширяют
входную параллельность LiteLLM; её достаточность проверяется сквозным опытом.
60 с — ориентир до первого восстановленного текста на оговорённой нагрузке,
не сумма отдельных таймаутов и не гарантия завершения всей генерации.

## Отказы

HTTP 503 Analyzer не повторяется и не служит причиной пассивного исключения:
он может означать как перегрузку, так и неготовность NER. Исходная причина и
`Retry-After` сохраняются. Сетевой отказ отличается от полученного HTTP-ответа
([правила Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream)).
Уже принятый Triton inference автоматически не повторяется. При потере узла
нет обещания перенести выполняющийся анализ на другой сервер без отказа.

Два уровня Analyzer-балансировки требуют общего ограничения повторов:
два адресата на каждом уровне могут дать до четырёх попыток анализа.
В прототипе это наблюдаемый риск, не новое правило production. В пункте 6
нужно выбрать единый ограниченный порядок сетевого переключения и проверить
общий бюджет; не добавлять повтор после перегрузочного 503.
Пассивный возврат по времени не заменяет проверки всех реплик перед
возвращением вычислительного узла после обслуживания.

## Предложение Для Пункта 6

По распределению функций рекомендуется схема локальных пулов. Она не получила
полной отказной приёмки: сначала требуется решение по TWO-NODE-LINK-02 и
отдельное принятие схемы владельцем. Увеличение числа серверов само по себе
не решает все перегрузочные и сетевые отказы.

1. Сохранить обычные functional/production. Выделить роли основного и
   вычислительного узла без новых команд Make; точные параметры выбора роли и
   не содержащий секретов файл адресов согласовать перед реализацией.
2. На вычислительном узле не запускать LiteLLM, Redis, БД или codex-lb и не
   копировать ключи провайдеров. Модель, словарные правила и параметры Analyzer
   должны соответствовать одному выпуску на обоих узлах.
3. Опубликовать один внутренний вход вычислительного Nginx. HTTP допустим
   только в согласованном доверенном контуре: он передаёт исходные данные.
   Доступ ограничивается основным узлом и административной/мониторинговой сетью.
   Порты отдельных Triton и Analyzer остаются внутри вычислительного проекта.
4. Расширить существующие setup/up/restart/health/metrics/down: действие относится
   к явно выбранной локальной роли. Не открывать удалённый Docker API и не
   добавлять собственный оркестратор. Порядок: проверить вычислительный узел,
   подключить его к основному, затем проверить маршруты и вернуть трафик.
5. `health` должен проверять каждую реплику и идентичность модели, а не только
   один удачный ответ балансировщика. Для удалённого узла нужны адресные
   внутренние маршруты здоровья/метрик каждой реплики через тот же Nginx либо
   запуск штатных локальных проверок оператором на каждом сервере.
   Балансированные метрики нельзя считать отдельной репликой или суммировать дважды.
6. Разделить полную готовность и работу с уменьшенной ёмкостью: остановка второго
   узла не должна останавливать исправный местный пул. Обновление/откат —
   согласованным выпуском целиком, с сохранением общего состояния первого узла.

24 Analyzer / 12 Triton на каждом сервере — возможная исходная точка, не
подобранный двухузловой профиль. Плотность и веса определяются измерениями с
переподпиской. Удвоение производительности и ёмкость 400 активных пользователей
не подтверждены. Проверка двух физических хостов, длительной нагрузки,
больших входов и отказа сервера относится к 7б/8б.
