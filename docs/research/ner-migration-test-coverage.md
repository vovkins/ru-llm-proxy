# Покрытие миграции NER проверками

Целевая связка: Tiny2 → ONNX Runtime в CPU Triton, Analyzer с
правилами Presidio и облегчённым spaCy. Решения: [#110](https://github.com/vovkins/ru-llm-proxy/issues/110).
Владелец принял переход с [ограничениями качества](tiny2-quality-comparison.md).
Сравнение классов — Э9/Э13, измерение нагрузки — Э10. Технические проверки
подтверждают принятый контракт, не отсутствие всех пропусков и не промышленную ёмкость.

## Контуры запуска

### Быстрый обязательный контур

`make test` выполняет `test-unit` и `test-static`. Модульные тесты работают
в отдельных контейнерах без сети, загрузки весов Tiny2 и вызовов LLM.
`make test-recognizer-api` отдельно проверяет API и правила.
В CI выполняются и она, и полный `make test-recognizers`, включая новые тесты.
`make test-ner-evaluation` проверяет корпус и расчёт метрик.

### Контур с настоящей моделью

| Команда | Назначение |
| --- | --- |
| `make test-hf-model` | Собрать Analyzer/Triton и проверить реальную модель |
| `make test-hf-model-run` | Проверить уже собранный комплект без повторной сборки |
| `make test-ner-proxy` | Проверить готовые Analyzer/Triton через прокси; собрать тестовые LiteLLM/codex-lb |
| `make test-ner-integration` | Один раз собрать модель и выполнить оба контура |
| `make ner-evaluate STACK=<состав>` | Оценить запущенный Analyzer с идентичностью из доверенного образа |

Тестовые образы: `ru-llm-proxy-ner-tests:*`. Перед запуском фиксируются
неизменяемые Docker ID и проверяется совпадение комплекта Analyzer/Triton
с манифестом текущего кода. Случайный тег `latest` доказательством не является.

Сборка скачивает закреплённые файлы; исполнение NER работает в сети Docker
с `internal: true`. `--network none` используется для проверки состава образа
и метаданных, не для обращения Analyzer к Triton. С компьютера доступны только
тестовый Nginx и проверочный API провайдера на loopback.
Настоящие подписки и пользовательский `.env` не требуются.

Лимиты `tests/e2e/topology-resources.env` предназначены для функциональных
проверок CI/локального компьютера, не для расчёта промышленной ёмкости.
Промышленные рекомендации определяются по Э10.

CI ограничен 60 минутами, использует общий кэш экспорта и сохраняет JSON-отчёты
из `tmp/ner-integration/` без окружения/секретов. При нехватке места проверка
завершается ошибкой, а не пропускает Triton. GitHub CI подтверждается только
на опубликованной ревизии, не по результату старого HEAD.

Ошибка одного независимого поднабора не отменяет остальные: инструкции,
именные проверки, ДКБ, Base64 и развёртывание сохраняют отдельные результаты.
Любая ошибка оставляет общий ненулевой код. Отчёты команд разделены на
integration-model.json, integration-proxy.json и integration-all.json:
успех одной модели не перезаписывает сбой полного набора.

### Холодная проверка

Полная чистая сборка и итоговая регрессия новой связки обязательны в Э12.
Обычный CI с кэшем их не заменяет. Старые результаты
[холодной проверки](ner-migration-cold-validation.md) относятся к прежней
архитектуре и не доказывают готовность Tiny2/Triton.

## Критерии успешности

- Все обязательные тесты реально выполнены, без скрытого пропуска NER.
- Проверены комплект и настоящий вывод; отказ NER не означает работу только правил.
- В проверяемых положительных сквозных сценариях маскирование восстанавливает значения; провайдер исходные данные не получает.
- Блокировка и недоступность Analyzer не приводят к передаче запроса провайдеру.
- Проверены обе политики, оба API и режима потока в предусмотренных сценариях.
- При успехе, ошибке или отмене удаляются только ресурсы конкретного теста.

Разметка и сырые показатели неизменны. В конечном реестре 18 отклонений
инструкционных/именных групп и 20 известных ухудшений покрытия; новые тексты,
пропуски, типы или границы не принимаются автоматически. Корпус подписей имён
исключений не имеет. Исправленный результат по исходной разметке допустим.
Известные неполные значения проверяются только Analyzer и отражаются как
пропуски в сыром отчёте; их не отправляют тестовому провайдеру и не выдают за
успешную защиту. В BLOCK принятые ложные находки означают 422 без провайдера.
Шесть именных случаев остаются в [#105](https://github.com/vovkins/ru-llm-proxy/issues/105).
Сравнительные таблицы Э9 и обнаруженные регрессии: [отчёт](tiny2-quality-comparison.md).
Прохождение протокольных проверок не означает отсутствия пропусков модели:
отдельная сквозная диагностика проверяет значения, не покрытые её масками.
