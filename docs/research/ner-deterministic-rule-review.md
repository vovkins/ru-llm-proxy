# Проверка детерминированных правил новой NER-модели

- **Задача:** #67
- **Статус:** исследование завершено, согласованный набор перенесён в Analyzer
- **Дата проверки:** 3-4 августа 2026 года

## Краткий вывод

Детерминированный слой из репозитория модели нельзя подключать целиком. В нём есть полезные идеи и отдельные правила, но исходный загрузчик меняет смысл конфигурации Gitleaks, не обеспечивает нужную типизацию сущностей и даёт неприемлемое количество ложных срабатываний на обычных технических идентификаторах.

По итогам исследования и отдельного согласования принято решение:

1. адаптировать онтологию пар «ключ-значение» и обработку заполнителей к существующим распознавателям Presidio;
2. адаптировать ограниченный набор правил для аргументов командной строки;
3. не добавлять общую эвристику энтропии;
4. не переносить весь набор Gitleaks;
5. не добавлять безусловное правило `CONTRACT_NUMBER`; на следующем этапе
   проверить строгий контекст как подтверждающий и резервный источник;
6. перенести 23 высокоточных формата ключей и токенов AWS и Bedrock, GitHub,
   Hugging Face, Slack, HashiCorp Vault, Yandex Cloud и `curl`;
7. оставить ещё 174 правила поставщиков вне рабочего процесса до появления
   подтверждённого сценария и отдельной оценки.

Согласованный набор реализован собственными распознавателями Presidio в
`presidio/recognizers/credential_rules.py`. Полная конфигурация Gitleaks и код
исходного загрузчика в рабочий образ не включены.

## Границы исследования

Проверялись текстовые файлы репозитория `fef2/ner_rus_bert-secret_detection` на закреплённой ревизии `52b5b0745aac14f73fcf2ac0f91d9b5001a85ae4`:

- `core/_shim.py`;
- `core/scrubber.py`;
- `core/slot_ontology.yaml`;
- `gitleaks.toml`;
- `predict.py`;
- `README.md`;
- `core/__init__.py`.

Контрольные суммы и сведения о лицензиях находятся в [манифесте источников](../../presidio/evaluation/deterministic_rule_source_manifest.json). Перед изолированным запуском скрипт проверяет каждый файл по SHA-256. Исходный код модели и полный набор регулярных выражений в проект не копируются. Выбранные форматы перенесены в рабочий код только после поштучной оценки.

Изолированное исследование и первоначальный перенос правил не включали:

- интеграция Betterleaks;
- изменение переменных окружения;
- слияние пересекающихся результатов с учётом источника;
- открытый PR #64 и автономная загрузка модели;
- маршрутизация запросов, производительность модели и размер образа.

Слияние с учётом источника и контекстная обработка `CONTRACT_NUMBER` выполнены
на следующем этапе и описаны ниже как последующая проверка. Остальные пункты
остаются вне этого исследования.

## Выявленные проблемы

### Пары «ключ-значение»

Полезными являются онтология ключей, список слов-исключений и возврат только самого значения. Однако исходная реализация:

- считает `svc.billing` и обычное значение с подчёркиваниями ссылками на код и пропускает их;
- не применяет проверку ссылок к заключённым в кавычки значениям и поэтому маскирует `"config.database_password"`;
- слишком широко трактует составную часть `user` и может принять числовой идентификатор пользователя за логин через соседнюю эвристику;
- использует общий разбор пар, который требует дополнительных проверок на JSON, YAML, строки документации и естественный текст.

Рекомендуемая адаптация:

- сохранить строгие ключи `password`, `passwd`, `pwd`, `пароль`, `login`, `username`, `user_name`, `логин`, `api_key`, `client_secret`, `secret_key`, `access_token`, `refresh_token`, `auth_token`, `id_token`, `токен`;
- удалить безусловные слабые правила для любого `user` и любого `token`;
- возвращать только значение, не включая имя ключа и разделитель;
- одинаково обрабатывать ссылки и заполнители внутри и вне кавычек;
- не считать произвольный идентификатор ссылкой на код, если перед ним стоит строгий секретный ключ;
- сохранить отрицательные примеры до включения правила в Analyzer.

### Командная строка

Поддерживаемая часть исходного набора прошла без ложных срабатываний. Полнота ниже из-за отсутствия Redis, PostgreSQL и строк подключения.

Рекомендуемая адаптация:

- перенести разбор `curl -u/--user`, `curl --oauth2-bearer`, паролей `wget`, `mysql -p/--password` и HTTPie `--auth`;
- оставить общее `--password`, только если значение является литералом;
- добавить точное имя `PGPASSWORD` в онтологию пар «ключ-значение»;
- рассмотреть `redis-cli -a/--pass` как отдельное высокосигнальное правило;
- не дублировать строки подключения: они уже покрываются `CredentialUrlRecognizer`;
- не маскировать ссылки `$VAR`, `${VAR}`, подстановки команд и документационные заполнители.

### Непрозрачные значения и энтропия

Эвристика определила как секреты:

- UUID;
- SHA-256 и короткие Git-коммиты;
- контрольную сумму контейнерного образа;
- Base64 из документации;
- артикул;
- шестнадцатеричный идентификатор сборки.

Она также возвращает внутренний тип `SECRET`, которого нет среди восьми типов новой NER-модели и в согласованном контракте проекта. Эту семью рекомендуется отклонить полностью. Энтропию можно использовать только внутри конкретного формата как дополнительную проверку, но не как самостоятельный распознаватель.

### Gitleaks

В конфигурации 222 правила. Исходный загрузчик:

1. выбирает правило, только если его идентификатор содержит `token`, `key` или `secret`;
2. назначает `AUTH_TOKEN` по слову `token`, иначе `SECRET_KEY`;
3. не загружает 31 правило из-за имени;
4. теряет ещё 23 правила, которые не компилируются в Python `re`;
5. в итоге запускает 168 правил;
6. не применяет глобальный список исключений;
7. не применяет списки исключений девяти отдельных правил;
8. не применяет ограничения по пути пяти правил.

Это не эквивалент работы Gitleaks. Например, открытый ключ Flutterwave определяется как `SECRET_KEY`, а документационный `api_key` проходит без исходных исключений. GitHub PAT и GitLab PAT не выбираются по собственным идентификаторам и могут быть найдены общим правилом с типом `SECRET_KEY` вместо `AUTH_TOKEN`.

Поштучный реестр содержит:

| Решение | Количество | Смысл |
| --- | ---: | --- |
| Уже покрыто | 9 | В проекте уже есть структурный распознаватель |
| Адаптировано после согласования | 23 | Формат достаточно строгий; добавлен собственный тип и тесты Presidio |
| Отклонить | 16 | Открытый идентификатор, слишком общее правило или метаданные файла |
| Нужны подтверждения | 174 | Правило конкретного поставщика не относится к активной конфигурации по умолчанию |

Согласованные 23 правила образуют следующие группы:

- AWS и Bedrock: 3;
- недостающие форматы GitHub: 4;
- токены Hugging Face: 2;
- недостающие форматы Slack: 7;
- HashiCorp Vault: 2;
- Yandex Cloud: 3;
- учётные данные `curl`: 2.

Каждый формат перенесён в собственный распознаватель Presidio или в ограниченное
расширение существующего распознавателя с правильным типом и точными границами.
Набор регрессионных тестов проверяет положительные, отрицательные, граничные и
документационные примеры, включая ссылки на переменные и заполнители.

### Номер договора

Контекстное выражение исходного репозитория правильно находит четыре из пяти положительных примеров и не срабатывает в пяти отрицательных. Оно не понимает форму «номер договора: ...».

Новая NER-модель на исходном корпусе покрывала `CONTRACT_NUMBER` с полнотой 100%
и точностью 66,7%. Безусловное регулярное выражение не устраняло ложные
срабатывания, поэтому оно было отклонено.

На следующем этапе правило принято в ограниченной форме: оно требует слова
`договор`, `контракт`, `соглашение`, `contract` или `agreement`, учитывает
склонения и форму «номер договора», отбрасывает версии, даты, шаблоны, номера
заявок и случайные коды. Контекст подтверждает результат BERT и создаёт точный
резервный интервал, если модель пропустила значение, выбрала другой тип или
захватила лишние слова. На расширенном корпусе из 77 примеров точность и полнота
`CONTRACT_NUMBER` составили 100%.

## Принятое решение

1. **Принять с адаптацией:** строгая онтология пар «ключ-значение», единая обработка заполнителей и возврат только значения.
2. **Принять с адаптацией:** правила командной строки для `curl`, `wget`, `mysql`, HTTPie, `redis-cli` и точный ключ `PGPASSWORD`; строки подключения оставить текущему распознавателю.
3. **Отклонить:** самостоятельную эвристику энтропии и внутренний тип `SECRET`.
4. **Отклонить:** загрузчик всех 222 правил Gitleaks и общий `generic-api-key` в его исходном виде.
5. **Принять с ограничением:** `CONTRACT_NUMBER` через BERT и строгий
   контекстный источник; безусловное выражение не использовать.
6. **Принять с адаптацией:** 23 структурных формата AWS, GitHub, Hugging Face, Slack, Vault, Yandex Cloud и `curl`.
7. **Отложить:** 174 правила поставщиков, для которых нет подтверждённого сценария в текущей установке.

Решение реализовано без новых переменных окружения. Рабочий набор перечислен в
`APPROVED_REVIEW_RULE_IDS`, а его соответствие исследовательскому реестру
проверяется в `presidio/tests/test_credential_rules.py`.

После сквозной оценки слой дополнен узкими контекстами для подписи логина,
заголовков авторизации, основного/резервного токена и секретного ключа. Они не
расширяют согласованный набор форматов поставщиков и не вводят общий поиск по
энтропии. На миграционном корпусе `LOGIN`, `PASSWORD`, `AUTH_TOKEN` и
`SECRET_KEY` получили точность и полноту 100%.

## Воспроизведение

Исходные текстовые файлы нужно скачать в отдельный каталог на закреплённой ревизии. Полные веса модели для этого прогона не нужны. Затем в тестовом образе Analyzer выполняется:

```bash
python3 presidio/evaluation/review_deterministic_rules.py \
  --source-dir /path/to/verified-model-source
```

Скрипт сначала проверит SHA-256 всех файлов из манифеста, затем выполнит правила без сети и обновит отчёт и поштучный реестр. Любое расхождение исходников останавливает проверку.
