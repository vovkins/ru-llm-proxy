## Как читать итог

- **П/Ч/Н:** полностью закрыто / закрыто частично / не закрыто ни одного
  непробельного символа. Сумма равна N. Учитывается объединение **любых** масок.
- **Класс B/T:** полностью закрыто правильным классом у BERT/Tiny2, из N.
  **Точно B/T:** совпали и класс, и границы, из N. Эти показатели не взаимозаменяемы.
- **FP B/T:** находки без точного совпадения в области разметки, включая неверные
  границы защищённых значений. Это не число утечек или заведомо лишних масок.
  Из N, точных TP и FP получаются R = TP/N, P = TP/(TP+FP).
- Маски вне частичной разметки не считаются автоматически ложными. Из 2318
  примеров только 70 размечены полностью; 35 из них отрицательные.
  Малые N, повторы и диагностический подбор ограничивают обобщение результатов.
- CVC/CVV исключён **явно**: прежние случайные маски BERT закрывали 6/77,
  Tiny2 — 0/77. Поддержка этого класса не заявляется; разметка не исправлялась.

## Отдельный нейросетевой слой

На восьми собственных классах модели полное покрытие 500 → 598 / 679.

компенсируют большинство таких потерь, но не свободный рассказ о паспорте.

## Примеры и последствия

Ниже сокращён соответствующий фрагмент запроса. Номера плейсхолдеров условны.
Для K01–K07 проверены исходящие тела тестового провайдера и точное восстановление,
оба API, поток/обычный ответ, MASK/BLOCK; это не новые вызовы Э13.

| Исходный фрагмент | BERT | Итог Tiny2/правил → вид у провайдера |
|---|---|---|
| `Московская 156 подъезд 2` | RU_ADDRESS + PASSWORD на подъезде | K01: один RU_ADDRESS → `<RU_ADDRESS_1>` |
| `Фрунзенская набережная 24` | LOCATION на всём адресе | K02: RU_ADDRESS на всём адресе → `<RU_ADDRESS_1>` |
| `адрес: москва, проспект вернадского 30` | LOCATION/LOGIN/PASSWORD, неверные классы | K03: полный RU_ADDRESS → `адрес: <RU_ADDRESS_1>` |
| `марина.кузнецова@inbox.ru` | LOGIN | K04: EMAIL_ADDRESS → `<EMAIL_ADDRESS_1>` |
| `Михаил Соколов mikhail.sokolov@outlook.com` | PERSON на имени, LOGIN на фамилии | K05: полный PERSON и EMAIL_ADDRESS → `<PERSON_1> <EMAIL_ADDRESS_1>` |
| Явное поле номера паспорта, в том числе число JSON | Не общее правило неполного номера | K06/K06-J01: маска строкового представления, после ответа восстановлен исходный числовой тип; строгая числовая схема не поддерживается |
| `Пароль: !?$` | PASSWORD | K07: PASSWORD → `Пароль: <PASSWORD_1>`; для env-форм политика может дать 422 до провайдера |
| Код восстановления из `pii_entity__token_001` | Пропущен | Полностью SECRET_KEY → `<SECRET_KEY_1>`; по разметке это AUTH_TOKEN, класс всё ещё неточен |

**Оставшаяся потеря покрытия:** «потерял паспорт, срочно нужна замена! Серию
не помню, но номер был 122648» (`passport_058`). BERT ошибочно считал число
PASSWORD и скрывал его; Tiny2/правила не находят ничего. В MASK число уходит
провайдеру, в BLOCK такой запрос может пройти. Свободный рассказ явно оставлен
ограничением K06; явная паспортная подпись исправлена, но не решает этот случай.

**Ухудшение уже частичного покрытия:** в «заказ жду на адрес москва, арбат 5,
кв 2» BERT скрывал `москва`/`арбат` как LOCATION и `5` как PASSWORD — 12/17
символов адреса. Tiny2/правила не находят ничего: 0/17, провайдер получает
исходный адрес, BLOCK может пропустить запрос. В
`https://service.local/run?api_key=Ab/C+!?&visible=ordinary` у BERT PASSWORD
закрывает `Ab/C+!` (6/7), у кандидата ключ открыт целиком (0/7); маска
INTERNAL_DOMAIN на хосте не защищает параметр URL. Это не правильная прежняя
классификация, но реальная потеря дополнительного покрытия.

**Q01, принятое ограничение:** `assistant: Done.` → BERT без маски,
Tiny2 даёт PERSON на `Don`, то есть `assistant: <PERSON_1>e.`. Возможны потеря
смысла для LLM и ложный 422 в BLOCK. Восстановление ответа не отменяет изменение
входа модели. Исключений для слова в рабочей обработке не добавляли.

**Q02, принятое ограничение:** `PE` внутри `PERSON`, `ORGANIZA` внутри
`ORGANIZATION`, а в искусственном `STOCK_BRIDGE_ECHO Пароль: !?$` — PERSON
на `оль`. K05 сохраняет всё найденное покрытие, включая лишние подписи и
пунктуацию. Например, может скрыться `assistant` в примере диалога. Это цена
согласованной политики, не доказанное отсутствие ложных находок.

**Q03, принятое ограничение выборочных фильтров:** «Клиент АННА СОКОЛОВА
подтвердил заявку». BERT: PERSON целиком. Tiny2: ORGANIZATION на АННА, PERSON
на СОКОЛОВА. Полный поиск даёт `Клиент <ORGANIZATION_1> <PERSON_1> подтвердил
заявку` и закрывает 12/12 символов; только `entities=["PERSON"]` оставляет
`Клиент АННА <PERSON_1> подтвердил заявку`, то есть 8/12. Подпись `Ф.И.О. =`
на том же имени даёт полный PERSON, а `Компания` — ORGANIZATION. Конкретное
согласование Q03 не распространяется на все возможные потери или фильтры.

## Как читать показатели

`P/R/F1` требуют точного класса и границ. «Защищено» означает, что объединение любых масок закрывает все непробельные символы значения; покрытие пробелов и правильным классом сохранено отдельно. Разрыв только на пробеле не называется утечкой имени. Выборочные фильтры требуют отдельной проверки.
Частичная разметка не превращает остальной текст в доказанно безопасный. Ложные блокировки всего запроса считаются только на полностью размеченных отрицательных примерах; для PII-Bench отдельно показаны маски в пределах классов его разметки. Отсутствующие классы имеют «—», а не выдуманный ноль.

### K06-J01: сохранение числового типа

моделью представления документа точно обратимым не объявляется.

Все 2318 повторных запросов к Analyzer успешны; классы и границы полностью
