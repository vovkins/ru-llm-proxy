# Два Узла: Ограничение Проверки Здоровья

4 ноября 2026, [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Основа v0.6.0, `7587d02`; [данные опыта](../../presidio/evaluation/reports/production-two-node-health-fix.json).
**Частичный результат: исходный сценарий исправлен, расширенная приёмка не пройдена.**
Рабочие конфигурации, платформы, guardrail и модель не менялись.
Последующий согласованный [опыт без хранения межузловых соединений](production-two-node-idle-fix.md)
прошёл прежнюю волну LINK-02 и возврат связи, но обнаружил отдельный LINK-03
при потере уже активного соединения. Ниже сохранён исходный health-опыт.

## Суть Исправления

В [исходной диагностике](production-two-node-link-diagnostic.md) короткий
`GET /api/v1/health` получил сохранённое соединение к отключённому узлу B.
Пятисекундный connect timeout не сработал: соединение уже считалось открытым.
Ожидание ответа определялось общим read timeout 1500 с, рассчитанным на анализ.
Клиент прекратил ожидание через 90 с, до анализа текста и обращения к провайдеру.

По согласованному плану только в испытательную копию центрального Nginx A
добавлен точный маршрут, использующий прежний общий пул адресатов:

```nginx
location = /api/v1/health {
    proxy_pass http://node_analyzers;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_connect_timeout 5s;
    proxy_read_timeout 5s;
    proxy_send_timeout 5s;
    proxy_next_upstream error timeout http_502;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;
    proxy_intercept_errors off;
}
```

10 с ограничивают окно допуска переключения, а не задают жёсткий общий
таймер операции. Семантический 503 не повторяется. POST анализа и маршруты
Triton побайтно прежние; бюджеты анализа 240/1200 с сохранены. Нет новых
переменных или команд Make. Nginx обоих испытательных проектов прошёл `nginx -t`.

## Результаты

Сервер, образы и модель прежние; два проекта на одном Docker-хосте, по
2 Analyzer / 1 Triton. Это не проверка двух физических серверов или сети 10 Гбит.
Использован синтетический провайдер; внешние LLM не вызывались.

Ровно три диагностических запроса B имеют прежние хэши входов и критерии,
без повторов API; предел клиента остался 90 с:

| Сценарий | До исправления A | После исправления B |
|---|---|---|
| Исправная связь, Chat без stream | 200, 0.760 с | 200, 0.742 с |
| Разрыв связи, Chat без stream | 200, 0.278 с | 200, 5.243 с |
| Разрыв связи, Responses SSE | Таймаут 90.091 с | 200, 0.299 с |

Все три B-ответа восстановлены точно; поток завершён. Nginx подтвердил
переключение health с отключённого B на A: `504, 200` за 5.003 с.
Провайдер получил только замаскированные значения, временных замен Redis нет.

Расширенная проверка сохранена целиком, включая неуспех:

| Проверка | Результат |
|---|---|
| MASK: оба API, stream false/true | 8/8 точных ответов |
| 20 новых входов около 8k единиц по пробелам за 2 с | 20/20, p95 12.440 с, максимум 12.469 с |
| BLOCK: оба API, stream false/true | 4/4 HTTP 422, провайдер не вызван |
| Остановка одного Triton узла B | 6/8 успехов, 2 защитных 503 |
| Возврат Triton | 4/4 успехов |
| Остановка всего вычислительного проекта B | 7/8 успехов, 1 защитный 503 |
| Возврат проекта B | 8/8 успехов |
| Отсоединение Nginx B от межузловой сети | 6/8 успехов, **2 таймаута около 90 с** |

Защитные отказы при намеренной потере вычислений разрешены критериями:
они ограничены по времени, без обхода маскирования. Это не обещание отсутствия 503.
На здоровом всплеске Analyzer A/B обработали по 10 полей, Triton по 70 вызовов;
готовность всех реплик и маршруты к обоим пулам проверены до нагрузки и после
возврата компонентов. Все успешные ответы пришли до 60 с.

Расширенная серия: 64 MASK-запроса, из них 59 успехов, 3 защитных 503 и
2 таймаута; отдельно 4 BLOCK-запроса. Исходный контрольный телефон у провайдера
не обнаружен, проверенные временные замены Redis очищены. На центральном
маршруте два полученных POST-ответа 503 не повторялись. Ответа health 503
в этом прогоне не было: его запрет повтора подтверждён конфигурацией, не
отдельным наблюдением такого ответа.

## Новое Наблюдение TWO-NODE-LINK-02

Два таймаута последней волны затронули Responses без stream и Chat со stream.
Оба внутренних `POST /api/v1/analyze` направлены к отключённому B, не получили
заголовков/тела и завершились записью Nginx 499 после ухода клиента.
Для одного на том же входном соединении непосредственно перед POST виден
успешный health локального A за 0.001 с; для второго такой непосредственной
корреляции нет. Нельзя приписывать ему чужую проверку здоровья.

Наглядный случай: проверка «есть ли готовый Analyzer?» успешно отвечает на A,
но балансировка следующего POST независимо выбирает B. Успех GET не закрепляет
следующий запрос за тем же адресатом. Короткий health timeout поэтому не
ограничивает уже последовавшее ожидание анализа.

Повторное использование старого межузлового соединения вероятно, но в этом
прогоне нет записи пакетов: это не такое же прямое TCP-доказательство, как
для LINK-01. Оба запроса начаты уже после разрыва; потеря связи во время
исполняющегося анализа этим не проверена. Отказ произошёл до ответа провайдера,
не в восстановлении SSE и не как доказанное насыщение очередей.

После нового дефекта запросы остановлены. Возврат связи и завершающая полная
проверка не выполнены; общий статус приёмки остаётся `failed`.

## Последующий Согласованный Опыт

План ниже согласован и выполнен; [результат и дальнейшая развилка](production-two-node-idle-fix.md)
опубликованы отдельно. Промышленная схема этим не принята.

1. Сохранить короткий health-маршрут. В копии конфигурации отключить повторное
   использование простаивающих соединений только у центрального пула входов
   в вычислительные узлы. Соединения LiteLLM, местных Analyzer/Triton не менять.
2. Не сокращать POST-бюджеты и не добавлять повтор POST по таймауту. Проверить,
   что новый запрос создаёт свежее TCP-соединение и при недоступном B ограничен
   существующим connect timeout. Не обещать автоматический успех: ограниченный
   защитный 503 в отказном опыте допустим, клиентский таймаут — нет.
3. Сравнить здоровый всплеск и последнюю отказную волну с сохранёнными данными;
   проверить точное восстановление, отсутствие исходного маркера у провайдера,
   очистку Redis, затем возврат связи и всех маршрутов. Отдельно проверить
   потерю связи во время уже начатого анализа: отключение простаивающих
   соединений само по себе этот случай не исправляет.
4. При новом дефекте остановиться и предложить следующий шаг. До отдельного
   принятия владельцем не реализовывать промышленную двухузловую поставку,
   не менять платформы, production, модель или политику семантических 503.

Все временные контейнеры/сети/тома удалены; 44 прежних серверных контейнера
сохранили ID, образы и состояние. Локальные восемь не затронуты. Тела, заголовки
и журналы остаются в приватных каталогах; в Git только отчёт и обезличенные
данные. Частные регрессии обвязки и отчётов: 26 успешных проверок. Штатный
`make test-static` повторён на серверном Python 3.12: 820 pytest и 32 проверки
Make успешны. Эти проверки не отменяют неуспех отказной приёмки.
