# Кэш и ожидание HTTP-пула

Завершение локального разбора пункта 3 [#116](https://github.com/vovkins/ru-llm-proxy/issues/116),
1 ноября 2026. Рабочий код, контракт кэша и настройки `production` не менялись.
Новый дефект распознавания ниже требует отдельного решения владельца.

## Методика

Одноразовый состав P3: 4 Analyzer по 1 CPU, 2 Triton по 2 CPU,
один LiteLLM; C2/I2/B4/Q32/W45. Docker ARM64, 10 CPU / 7,75 GiB.
Диагностический процесс внутри тестового контейнера импортировал неизменённый
guardrail и вызывал его методы. Обслуживающий процесс LiteLLM и библиотеки
не подменялись. SHA-256 модуля совпал с рабочей копией.

Кэш проверен последовательно для четырёх полей одного синтетического диалога.
В двух вариантах менялось только представление JSON-аргументов инструмента;
равенство декодированного содержимого проверено. Пространства кэша независимы.
Ни тексты, ни сущности с исходными значениями в публичный отчёт не входят.

Первый запуск остановился из-за ошибки пробника: сырые сущности содержат
`text`, а кэш намеренно его не сохраняет. По отдельному согласованию исправлено
только сравнение с четырьмя полями эталонной сериализации. Регрессии запрещают
`text` в результате кэша и выявляют изменение координат, класса или оценки.
Неуспешная попытка сохранена отдельно, не считается успешным измерением.

## Кэш

Для одного и того же аргумента инструмента:

| Показатель | JSON с `\u`-экранированием | JSON с UTF-8 |
| --- | ---: | ---: |
| Символов исходного поля | 369 732 | 69 772 |
| Найдено сущностей | 2947 | 1 |
| Из них AUTH_TOKEN | 2946 | 0 |
| Из них EMAIL_ADDRESS | 1 | 1 |
| Размер сериализованной разметки | 245 595 байт | 110 байт |
| Первый анализ | 31,144 с | 1,226 с |
| Повтор | 30,940 с | 0,000254 с |
| Чтение кэша | промах | попадание |

Повтор измерен внутри метода полевого анализа с уже подготовленным контекстом
кэша. Это не время полного HTTP-запроса через LiteLLM с авторизацией.

Воспроизведённый `ValueError` возникает **до записи в Redis**: превышены
2000 сущностей и 65 536 байт разметки. Лимит относится к результату анализа,
не длине исходного текста. Нарушенных координат не обнаружено.
Остальные семь проверенных полей сохранились и прочитались без ошибки;
четыре значимых поля разметки совпали, исходный `text` в кэше отсутствовал.

Таким образом, повторный анализ дорогого поля объясняется отказом кэширования
по контракту. Это не свидетельство недоступности Redis. Проверен один
воспроизводимый случай исходной тяжёлой истории; первоначальные восемь
событий `error` не реконструированы по отдельности.

**Новая находка:** дополнительные AUTH_TOKEN ложные для известного нейтрального
синтетического содержимого. Пока не установлено, какой распознаватель их
создаёт. Маскирование продолжает работать; последствия — лишние маски,
некэшируемая разметка и повторные затраты анализа. Лимиты не увеличивались,
фильтры/модель/нормализация не менялись. Исправление не входит в этот прогон
и требует отдельного согласования, а не безусловного исключения `\u`.

## HTTP-пул

HTTPX 0.28.1 / httpcore 1.0.9, штатный клиент guardrail: 20 соединений,
10 сохраняемых соединений. Использованы публичные request hooks и trace;
содержимое событий, заголовки и исключения не сохраняются.

Измерение до первой отправки заголовков за вычетом завершённого TCP/TLS
соединения даёт **верхнюю оценку ожидания пула**, включая служебное
планирование. Это не точный внутренний таймер очереди. Положительный контроль
на одном соединении и двух запросах к серверу с задержкой 0,2 с зафиксировал
ожидание второго 0,242 с без нового TCP-соединения.

Каждый измеряемый вызов — одно новое поле 8k условных единиц, без кэша.
Перед серией прогрет клиент; реальные новые соединения учтены отдельно.

| Параллельных полей | Успех | p95 ожидания до отправки*, с | p95 после отправки до заголовков, с | p95 всего, с |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1/1 | <0,001 | 1,229 | 1,230 |
| 8 | 8/8 | 0,003 | 3,812 | 3,815 |
| 20 | 20/20 | 0,010 | 8,091 | 8,105 |
| 32 | 32/32 | 5,919 | 9,128 | 12,382 |
| 64 | 64/64 | 17,180 | 10,448 | 23,851 |

* Верхняя оценка с вычетом установления соединения. Время после отправки
включает сеть, Nginx, очередь и работу Analyzer; не называется чистым временем
NER. Процентили разных столбцов не складываются.

Подтверждена дополнительная задержка перед Analyzer при превышении пула.
125/125 вызовов успешны. Это один цикл событий, не агрегат двух промышленных
LiteLLM. Доказательства выигрыша от расширения пула нет: больше соединений
может перенести ожидание в Analyzer и увеличить его перегрузку.

## Дальнейшее решение

Диагностические вопросы о контракте кэша и ожидании пула получили ответы.
Новый дефект AUTH_TOKEN сначала рассматривает владелец: отдельный разбор
источника или принятие ограничения для следующей серверной матрицы.
Самовольное расширение лимитов кэша/пула не требуется.

Следующий основной результат #116 — профиль сервера 32 CPU / 64 GB
с полным промышленным составом. Кандидат P3, число соединений, дорогой
экранированный ввод и непопадания кэша должны проверяться совместно.
Двухузловая схема и изменения стандартных значений согласуются отдельно.

Лабораторные ресурсы удалены. Исходные восемь контейнеров восстановлены
healthy, файлы/образы/тома/ключи/подписки сохранены. Диагностика не вызывала
внешних моделей или тестового провайдера; запускной прогрев учитывался отдельно.
OOM и отказов наблюдателя не наблюдалось.

Проверки после диагностики: 804 статические, 869 проверок защитной обработки,
32 проверки Make; отдельно 85 адресных проверок сравнения и измерителя.
`git diff --check` без замечаний.
