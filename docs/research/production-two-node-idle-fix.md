# Два Узла: Новое Соединение На Каждый Запрос

4 ноября 2026, [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Основа v0.6.0, `7587d02`; [данные опыта](../../presidio/evaluation/reports/production-two-node-idle-fix.json).
**LINK-02 не воспроизвёлся в прежней волне; потеря уже активного соединения
дала отдельный таймаут LINK-03. Полная отказная приёмка не пройдена.**
Это исследование в одноразовых проектах, не промышленная поставка.
Последующий согласованный [опыт TCP-проб](production-two-node-tcp-probes.md)
после двух исправлений частной обвязки прошёл 52/52 MASK и 4 BLOCK: потеря
активного B обнаружена, ответ получен через A за 36.662 с. Ниже сохранён
исходный неуспешный опыт без TCP-проб, не результат новой приёмки.

## Что Изменено

После [короткого health-маршрута](production-two-node-health-fix.md) проверка
здоровья могла успешно ответить с A, а следующий POST попадал по старому
соединению к отключённому B. По согласованию из испытательного центрального
`upstream node_analyzers` удалены только:

```nginx
keepalive 16;
keepalive_timeout 4s;
```

В проверенном Nginx **1.27.5** это отключило хранение свободных соединений
только у пула входов узлов. Health, POST, локальные пулы Analyzer/Triton и пул
LiteLLM побайтно прежние. Не добавлены повторы POST по timeout или 503,
бюджеты анализа 240/1200 с сохранены; принятую операцию Triton не повторяем.
Оба Nginx прошли `nginx -t`. Платформы, модель, guardrail, production, env и
команды Make не менялись. Это не рецепт для произвольной версии: новые
умолчания Nginx отличаются ([документация](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)).

## Проверки

Прежний сервер 32 vCPU / 62.79 GiB; два проекта на одном Docker-хосте,
по 2 Analyzer / 1 Triton. Образы и модель совпадают с прошлым опытом.
Два физических хоста, 10 Гбит и полный промышленный состав здесь не проверены.
Тестовый провайдер изолирует наш контур; внешние LLM не вызывались.

| Сценарий | Предыдущий health-вариант | Без хранения межузловых соединений |
|---|---|---|
| MASK: оба API, stream false/true | 8/8 | 8/8 |
| 20 новых около 8k входов за 2 с | 20/20, p95 12.440 с | 20/20, p95 11.531 с, максимум 12.595 с |
| BLOCK: оба API, stream false/true | 4/4 HTTP 422 | 4/4 HTTP 422, провайдер не вызван |
| Новые запросы после разрыва связи | 6 успехов, 2 таймаута | **8/8**, максимум 5.788 с |
| Возврат связи | Не выполнен после нового дефекта | **8/8**, максимум 0.662 с |

У первых трёх MASK-серий совпадают хэши всех входов: 8 + 20 + 8 запросов.
Контрольный телефон и критерии не менялись, предел клиента остался 90 с.
8k — единицы по пробелам, не токены LLM. По одному всплеску нельзя заявлять
статистически доказанное ускорение. Оба пула работали: на здоровом всплеске
Analyzer A/B обработали по 10 полей, Triton по 70 вызовов.

Пассивная запись только испытательной связи: 1097 пакетов, потерь захвата нет.
Наблюдались 37 исходящих TCP-соединений, из них 33 с HTTP-запросами:
13 GET и 20 POST. Каждый такой запрос имеет предшествующий SYN; более одного
запроса в одном соединении не обнаружено. Число захваченных POST совпадает с
числом POST центрального Nginx к удалённому входу. Это прямое подтверждение
новых соединений, не вывод только по скорости ответа.

## LINK-03: Связь Пропала Во Время Анализа

Отдельно запущен Chat без stream: около 32k единиц по пробелам, 224541 символ.
После подтверждения активной обработки в Analyzer B отключён только его
межузловой вход. Местные Analyzer и Triton B продолжили работать.

1. TCP-запись подтверждает свежее соединение и получение подтверждений на весь
   наблюдаемый POST до разрыва, а не отправку нового запроса в уже сломанный канал.
2. После разрыва входящих пакетов этого соединения на стороне A нет.
3. Analyzer B успешно закончил обработку за **10.508 с**, ожидание очереди
   **0.015 мс**; распознана одна PHONE_NUMBER, выполнены 104 окна NER.
4. Результат не вернулся к A: заголовков и тела нет. Центральный Nginx записал
   499 после ухода клиента; клиент завершился TimeoutError за **90.093 с**.
   Провайдер не вызван. Записи завершённого ответа Nginx B для этого POST нет.

Это не насыщение очереди, не ошибка модели и не проблема SSE: анализ успешно
завершился, потерян транспорт уже принятого запроса. Отключение повторного
использования свободных соединений не обнаруживает отказ активного канала.
90 с — предел клиента; достижения серверного бюджета 240/1200 с не ждали.

Всего 45 MASK-запросов: 44 успеха и один таймаут; отдельно 4 успешные BLOCK-
проверки. Исходный маркер у провайдера не обнаружен; проверенные временные
замены Redis очищены. При новом неуспехе запросы остановлены. Возврат связи
после этого последнего отказа и финальная полная проверка не запускались.
Общий статус `failed` сохранён, исходные A/B-неуспехи не удалены.

## Дальнейшее Решение Владельца

Можно принять редкий отказ уже выполняющегося анализа как явное ограничение
с текущими бюджетами. Если требуется его быстрое обнаружение, предлагается
отдельный опыт, впоследствии согласованный владельцем; его результаты
описаны [отдельно](production-two-node-tcp-probes.md):

1. Сохранить проверенные health и отсутствие межузлового хранения соединений.
   Включить стандартный `proxy_socket_keepalive on` только для исходящих
   соединений центрального входа анализа, не для LiteLLM/модельных маршрутов.
   Это TCP-пробы живого соединения, а не возврат HTTP-кэша свободных соединений
   ([Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_socket_keepalive)).
2. В одноразовом контейнере центрального Nginx проверить изолированные сетевые
   sysctl: начало проб через 10 с, интервал 5 с, три пробы. Около 25 с —
   кандидат для опыта, не гарантия и не готовое production-значение
   ([Linux](https://docs.kernel.org/networking/ip-sysctl.html)). Не менять
   sysctl хоста и не включать privileged. Если контейнерная изоляция не
   поддерживается, остановиться и согласовать другой вариант
   ([Compose](https://docs.docker.com/reference/compose-file/services/#sysctls)).
3. Сначала доказать сохранность хостовых настроек и действие параметров только
   внутри тестового контейнера. Повторить здоровый длинный анализ, превышающий
   выбранный период обнаружения: отсутствие HTTP-ответа при работающем TCP
   не должно считаться отказом. Затем повторить разрыв во время обработки
   с записью TCP-проб, исхода клиента, числа попыток и возврата связи.
4. Бюджеты анализа и правила повторов оставить прежними. Проверить фактические
   попытки POST: существующее сетевое переключение может повторить анализ
   на другом узле; новых повторов Triton inference не добавлять. При новом
   дефекте не расширять опыт автоматически. До отдельного принятия не
   реализовывать промышленную двухузловую схему.

Временные ресурсы удалены. Прежние 44 серверных контейнера сохранили ID,
образы и состояние; локальный стенд не затрагивался. Сырые ответы, журналы и
пакеты приватные. В Git публикуются только этот отчёт и обезличенные данные.
Повторены 39 частных регрессий и штатный `make test-static` на Python 3.12:
820 pytest и 32 проверки Make успешны. Это не отменяет LINK-03 и не означает
успешную полную отказную приёмку.
