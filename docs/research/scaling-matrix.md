# Матрица масштабирования

Документ фиксирует методику, результаты и итоговый расчёт задачи #70. Цель —
независимо измерить Analyzer и LiteLLM, проверить совместные конфигурации для
400 активных пользователей и определить исходную производственную топологию.
Значения Docker Compose по этим измерениям автоматически не меняются.

## Последовательность

1. Калибровка Locust и имитации провайдера без LiteLLM и Analyzer.
2. Исходная конфигурация: один LiteLLM и один Analyzer.
3. Два LiteLLM и 1, 2, 4, затем при необходимости 8 экземпляров Analyzer.
4. Выбранное число Analyzer и 1, 2, 4 экземпляра LiteLLM.
5. Две или три лучшие совместные конфигурации на устойчивой, ступенчатой,
   всплесковой и потоковой нагрузке.

В каждой реплике Analyzer работает один процесс модели. Несколько реплик
распределяются через точку балансировки только внутри `tests/load`; основной
Compose проекта она не изменяет. Серии насыщения используют
`LOAD_INPUT_VARIATION=unique`, а повторяемый ввод применяется отдельно для
оценки выигрыша от кэша.

Две реплики LiteLLM в серии Analyzer отделяют вычислительный предел модели от
затрат прокси на формирование контролируемых `503`. Это число настраивается
через `LOAD_ANALYZER_MATRIX_LITELLM_REPLICAS`; отдельная серия LiteLLM всё равно
нужна для проверки предела самого прокси.

На четвёртом шаге настоящий Analyzer заменяется его лёгкой имитацией из
испытательного контура. Это исключает конкуренцию BERT за CPU и позволяет
измерить LiteLLM, Redis и PostgreSQL отдельно. В этой серии не проверяется
восстановление маски; совместные серии вновь используют настоящую модель и
полную проверку защитного слоя.

## Сравниваемые показатели

- RPS, число успехов и отказов, p50/p95/p99 и время до первого фрагмента;
- CPU, память и число процессов каждой реплики;
- очередь, перегрузка и время Analyzer;
- соединения и ограниченные счётчики Redis/PostgreSQL;
- отсутствие немаскированных данных у имитации провайдера;
- отсутствие смешивания сопоставлений разных виртуальных ключей.

Тексты, ключи, сопоставления и персональные данные не сохраняются. Насыщение
должно возвращать контролируемый HTTP 503; HTTP 500, обход Analyzer и
неконтролируемое зависание считаются дефектами.

## codex-lb

Закреплённая версия `codex-lb` 1.24.0 официально определяет Docker Compose как
однорепличную топологию. Штатный многорепличный режим предоставляется Helm-
пакетом и требует PostgreSQL, выбора лидера, общей криптографической ключевой
информации, одного процесса на реплику и отдельного адреса каждой реплики для
передачи состояния Responses API.

Поэтому в текущем Docker-этапе проверяется производительность одного экземпляра
`codex-lb` коротким реальным сценарием. Горизонтальное масштабирование компонента
переносится в Kubernetes-задачу #59; собственный патч или неподдерживаемое
масштабирование Compose не добавляются.

Источники:

- [Compose для production в codex-lb 1.24.0](https://github.com/Soju06/codex-lb/blob/v1.24.0/docker-compose.prod.yml)
- [Многорепличный режим codex-lb 1.24.0](https://github.com/Soju06/codex-lb/blob/v1.24.0/docs/deployment/kubernetes.md#multi-replica-behavior)

## Локальная проверка методики

Методика проверена на Docker Desktop с 10 CPU и 7,75 GiB RAM. Каждый запуск
длился 60 секунд, использовал 400 пользователей, уникальный ввод размером 1k и
целевую частоту около 26,7 запроса/с. Эти результаты показывают место насыщения
локального компьютера, но не подходят для расчёта промышленной конфигурации.

| Контур | Конфигурация | Полезный RPS | Отказы | p95 успешных запросов | Пиковая память |
| --- | --- | ---: | ---: | ---: | ---: |
| Analyzer | 1 Analyzer / 1 LiteLLM | 0,95 | 1435 | 2,57 с | 0,69 GB |
| Analyzer | 2 Analyzer / 1 LiteLLM | 1,35 | 1399 | 4,92 с | 1,44 GB |
| Analyzer | 4 Analyzer / 1 LiteLLM | 1,45 | 600 | 26,82 с | 2,79 GB |
| LiteLLM | имитация Analyzer / 1 LiteLLM | 25,03 | 0 | 320 мс | 0,99 GB |

| LiteLLM | имитация Analyzer / 4 LiteLLM | 25,04 | 0 | 173 мс | 3,62 GB |

При настоящей модели ограничением стал CPU Analyzer. Все отказы были
контролируемыми `503 analyzer_overloaded` с `Retry-After`; после мягкой остановки
нагрузки завершающие `500/502` не воспроизводятся. При имитации Analyzer одна
реплика LiteLLM уже выдержала целевой поток без ошибок. Две реплики снижают
задержку и дают эксплуатационный запас, а четыре требуют почти вдвое больше
памяти по сравнению с двумя при небольшом дополнительном выигрыше.

Испытания выполнены на одном узле с 28 логическими CPU (14 физических ядер),

генератора и имитации провайдера дала 24,96 RPS без ошибок.

При насыщении штатным результатом был `503 analyzer_overloaded` с
`Retry-After`. Пулы соединений по умолчанию создавали дополнительное ожидание в
LiteLLM и редкие инфраструктурные `500/502`. Контрольный профиль с лимитами 200
HTTP-соединений к Analyzer и 200 Redis-соединений на процесс LiteLLM не дал
таких ошибок: все отказы остались контролируемыми `503`. Это проверочный верхний
предел, а не новое производственное значение по умолчанию.

### Кэш и виды нагрузки

Ключевой параметр ёмкости — частота появления нового текста, а не суммарное
число токенов уже проверенной истории:

- при повторении 400 ранее проверенных полей профиль с шестью Analyzer достиг
  26,7 RPS без отказов после прогрева; p95 успешного запроса за последние две
  минуты составил 258 мс;
- ступенчатая полностью уникальная нагрузка дала 0,88 полезного RPS при 50
  пользователях и 2,59 RPS при 400: даже начальная ступень превышала устойчивую
  холодную ёмкость одного узла;
- синхронный всплеск с настоящим Analyzer завершил 17 из 400 запросов, остальные
  получили контролируемый `503`;
- из 400 потоковых запросов настоящий Analyzer пропустил 22, а с его имитацией
  две реплики LiteLLM обслужили 400 из 400; p95 времени до первого фрагмента
  составил 2,21 с;
- короткая проверка настоящего пути LiteLLM → guardrail → Analyzer → codex-lb →
  OpenAI завершила три запроса без ошибок. Массовая нагрузка на внешний сервис
  не выполнялась.

Redis не отклонял соединения и использовал менее 2 MB данных. Один из 4170
запросов зарегистрировал неблокирующую ошибку записи результата анализа в кэш:
обработанный запрос продолжился без HTTP-ошибки. Этот счётчик необходимо
контролировать в эксплуатации. PostgreSQL не показал откатов транзакций,
временных файлов или взаимных блокировок. Оба хранилища не были ограничением в
проверенном диапазоне.

### Состояние и административные операции

Отдельный строгий профиль проверил 400 активных пользователей, две реплики
LiteLLM, шесть Analyzer и два провайдера моделей. За восемь минут выполнено
7664 запроса с повторяемым вводом 1k без ошибок: p50 составил 72 мс, p95 —
1,34 с, p99 — 2,80 с. Каждый пользователь выполнил не менее шести успешных
запросов.

- первичные привязки распределились между провайдерами как 195/205 и не
  изменились в течение теста;
- 561 временный ключ был создан, прочитан, проверен, удалён и затем отклонён;
- ошибки провайдера 429, 5xx, тайм-аут и разрыв потока не оставили
  `pii_mapping:*`;
- исходные контрольные значения не достигли провайдеров и не смешались между
  пользователями;
- Redis не отклонял и не вытеснял записи, PostgreSQL не показал откатов,
  взаимных блокировок или временных файлов;
- HTTP 500/502 и критические сигналы журналов отсутствовали.

Усиленный профиль с вводом 1k/8k подтвердил прежний предел CPU Analyzer:
из 13 544 запросов 13 414 завершились успешно, 128 получили контролируемый
`503 analyzer_overloaded`, ещё два были отменены клиентом после длительного
ожидания. p95 вырос до 39,58 с, p99 — до 119,41 с. После этих двух отмен
немедленная очистка всех `pii_mapping:*` не подтвердилась; записи остаются
ограничены настроенным сроком жизни. Ошибки провайдера теперь очищаются
отдельным обработчиком, но отмена клиентом после маскирования требует
самостоятельной проверки жизненного цикла LiteLLM и не считается закрытой этим
этапом.

Проверка отзыва ключей учитывает локальный кэш авторизации каждой реплики
LiteLLM. Административный цикл проверяет новый ключ через `/models`, поэтому не
создаёт дополнительную холодную нагрузку на Analyzer. Работающие привязки не
перераспределялись во время операций с другими ключами.

### Отказы и восстановление

Строгий профиль `resilience` выполнен на том же сервере с шестью Analyzer по
4 vCPU и 4 GB RAM, двумя LiteLLM по 2 vCPU и 2 GB RAM, 400 пользователями и
повторяемым вводом 1k. За 25 минут выполнено 29 317 запросов: 28 258 успешных и
1059 ожидаемых отказов только внутри управляемых аварийных окон. Каждый
пользователь выполнил не менее 44 успешных запросов; после последнего сбоя новые
ошибки не появлялись.

| Сценарий | Ответы во время отказа | Восстановление всех пользователей |
| --- | ---: | ---: |
| Остановка 1 из 6 Analyzer | нет | 14 с |
| Остановка 1 из 2 LiteLLM | 7 × HTTP 502 | 14 с |
| Остановка Redis | 479 × HTTP 503 | 46 с |
| Остановка PostgreSQL | 573 × HTTP 503 | 32 с |

HTTP 502 получили только запросы, выполнявшиеся в момент жёсткой остановки
процесса LiteLLM; новые запросы обслужила вторая реплика. При отказе Redis
защитный слой вернул 472 `analyzer_unavailable` и 7
`guardrail_dependency_unavailable`, не передавая непроверенные данные
провайдеру. Отказ PostgreSQL вернулся штатным для LiteLLM типом
`no_db_connection`; собственный патч платформы не добавлялся.

Пять таблиц замен нельзя было удалить во время недоступности Redis. Все записи
имели положительный TTL 6578–6609 секунд при настроенном пределе 7200 секунд.
Проверка сохранила это наблюдение, сократила только их TTL до 15 секунд и
подтвердила нулевой остаток; 409 записей кэша анализа не изменялись. Отдельная
клиентская отмена дала тот же безопасный контракт: немедленной очистки нет,
штатный TTL подтверждён, исходный маркер провайдеру не попал.

Распределение между двумя провайдерами осталось стабильным, смешивания
сопоставлений и исходных контрольных значений не обнаружено. Redis не отклонял
соединения и не вытеснял записи. PostgreSQL не показал откатов, временных файлов
или новых взаимных блокировок. Пиковая память шести Analyzer составила 4,21 GB,
двух LiteLLM — 2,32 GB, PostgreSQL — 197 MB, Redis — 6,5 MB.

## Итоговое решение

### Модель нагрузки

Ёмкость определяет не общий размер накопленной истории, а поток ещё не
проверенных текстовых полей и число BERT-окон в них.

| Вид нагрузки | Поведение | Вывод для расчёта |
| --- | --- | --- |
| Накопленная неизменная история | Результаты полей читаются из Redis | Основную работу выполняют LiteLLM и хранилища; шесть Analyzer выдержали 26,7 RPS после прогрева |
| Новый ввод около 1k | Каждый промах занимает CPU Analyzer | Измеренная предельная ёмкость одного экземпляра — около 0,6–0,7 RPS |
| Большое новое поле | Число фрагментов и BERT-окон растёт вместе с размером | Нельзя оценивать только числом HTTP-запросов; нужны `input_characters`, `text_chunks` и `ner_windows_processed` |
| Одновременный всплеск | Ограниченная очередь быстро заполняется | Лишние запросы должны получить 503 с `Retry-After`, а не ждать без верхней границы |

Для планирования обозначим через `Rnew` частоту новых полей, сопоставимых с
испытательным вводом 1k, а через `C` — измеренную ёмкость одного Analyzer
`0,6–0,7 RPS`. Начальное число экземпляров можно оценивать как
`ceil(Rnew × 1,3 / C)`, где 30% оставляются на неравномерность и восстановление.
Размеры больше 1k необходимо пересчитывать по фактическому времени анализа, а
не считать равными одному запросу.

Четыре Analyzer дают запас примерно для 1,8–2,1 RPS нового ввода 1k. При общем
потоке 26,7 RPS это соответствует доле холодных полей не более 7–8%. До сбора
обезличенного производственного профиля это условие является главным
ограничением исходной конфигурации.

Единичное новое поле около 1m токенов функционально поддерживается, но в
CPU-профиле занимало Analyzer около 964 секунд. Такой запрос нельзя включать в
интерактивную цель задержки. В #59 для него нужно проверить клиентские и
промежуточные тайм-ауты; сокращение времени потребует отдельной оптимизации или
будущего GPU-профиля.

### Исходный производственный профиль

Это отправная точка для распределённой проверки, а не универсальная гарантия
для любого состава трафика.

| Компонент | Минимум | Ресурсы экземпляра | Обоснование |
| --- | ---: | --- | --- |
| Analyzer | 4 | 4 vCPU, 8 GiB | Лучший сбалансированный профиль испытательного узла; один процесс и одна параллельная обработка |
| LiteLLM, клиентский трафик | 2 | 2 vCPU, 4 GiB | Испытанный CPU-профиль, отказоустойчивый минимум и рекомендуемый LiteLLM запас памяти на процесс |
| LiteLLM, фоновые задания | 1 | 1 vCPU, 4 GiB | Отделяет единичные периодические задания от обслуживающих экземпляров; требует проверки поддержки в закреплённой версии |
| `codex-lb` | 3 | запрос 200m/256 MiB, предел 1 vCPU/1 GiB | Штатный производственный профиль Helm 1.24.0; собственная нагрузочная граница в проекте не измерялась |
| Redis | отказоустойчивая служба | начать с 1 vCPU, 2 GiB | В испытаниях не был ограничением; объём уточняется по числу ключей, TTL и политике сохранения |
| PostgreSQL LiteLLM | отказоустойчивая служба | начать с 2 vCPU, 4 GiB | Проверенный поток не был ограничением; итог зависит от аудита, бюджетов и срока хранения |
| PostgreSQL `codex-lb` | отдельная база и учётные данные | начать с 1 vCPU, 2 GiB | Требует независимых миграций, резервного копирования и контроля соединений |

Для прикладных компонентов это около 22 запрошенных vCPU и 45 GiB памяти без
хранилищ и системного резерва. Начальный кластер из трёх рабочих узлов по 16
vCPU и 32 GiB оставляет место для служебных компонентов и планового вывода Pod.
Он не гарантирует полную холодную производительность после потери целого узла:
требование N+1 пересчитывается после измерения `Rnew`.

Для 26,7 RPS полностью нового ввода 1k прежняя оценка остаётся 55–65 Analyzer,
220–260 vCPU и 330–520 GiB памяти. Это экстраполяция с запасом, а не
рекомендуемый начальный размер. Её обязательно подтвердить распределённым
тестом; один испытательный сервер такого профиля не воспроизводит.

Пулы соединений рассчитываются на максимальное число процессов. Значение 200
для HTTP-соединений Analyzer и Redis устранило искусственные ошибки в стресс-
тесте, но не является промышленным значением по умолчанию. Максимальное
число соединений LiteLLM с PostgreSQL должно делиться между всеми обслуживающими
и фоновыми процессами с резервом для миграций и операций администратора.

### Масштабирование

- Analyzer: минимум четыре экземпляра; быстрое увеличение по CPU, устойчивой
  очереди и `capacity_rejections`, медленное уменьшение для сохранения прогретого
  кэша. Верхняя граница определяется доступными узлами и измеренным `Rnew`.
- LiteLLM: минимум два обслуживающих экземпляра, один процесс на Pod,
  масштабирование по CPU с начальной целью 60%. Память используется как
  ограничение, а не основной сигнал масштабирования.
- `codex-lb`: использовать штатный Helm-профиль с минимум тремя экземплярами,
  общей ключевой информацией и PostgreSQL. Уменьшение числа экземпляров должно
  учитывать осушение сессий; число процессов остаётся равным одному на Pod.
- Redis и PostgreSQL: не масштабировать как приложения без собственного
  состояния. Использовать отказоустойчивые службы, контролировать соединения,
  задержку, место и резервное копирование.

Автоматическое масштабирование не заменяет ограниченную очередь Analyzer:
запуск и прогрев нового экземпляра занимают время, поэтому перегрузка должна
оставаться безопасной и возвращать 503 до обращения к провайдеру.

### Цели проверки

Эти значения предназначены для приёмки Kubernetes-контура, а не являются SLA
внешнего модельного провайдера.

| Показатель | Цель |
| --- | --- |
| Режим доступности | 20×5 с согласованными окнами обновления |
| Ошибки вне управляемого отказа или насыщения | 0 |
| Прогретый внутренний контур при 26,7 RPS | p95 не более 2 секунд с имитацией провайдера |
| Восстановление после отказа одного прикладного экземпляра | не более 60 секунд |
| Перегрузка Analyzer | HTTP 503 с `Retry-After`, без вызова провайдера |
| Смешивание сопоставлений и исходные контрольные значения у провайдера | 0 |
| Остаточные сопоставления после недоступности Redis или отмены клиента | только с положительным TTL не выше настроенного предела |

### Перед вводом в эксплуатацию

В задаче #59 необходимо:

1. закрепить версии образов и реализовать описанную топологию штатными средствами
   Kubernetes и официальными пакетами компонентов;
2. выполнить распределённые профили `steady`, `stages`, `burst`, `streams`,
   `stateful` и `resilience` для 400 пользователей;
3. проверить обновление и вывод узла без одновременной потери всех экземпляров
   компонента;
4. подтвердить лимиты соединений при максимальном числе экземпляров;
5. повторить расчёт Analyzer по обезличенным `Rnew`, размерам новых полей,
   доле попаданий кэша и числу BERT-окон реального трафика;
6. отдельно решить допустимый клиентский контракт для единичного холодного
   контекста около 1m токенов.

Испытательные Nginx-балансировщики из `tests/load` не являются частью целевой
архитектуры.
