# Проверка длинного контекста

Исходные измерения и выводы приведены в
[long-context-baseline.md](long-context-baseline.md).

Сценарий `scripts/benchmark_long_context.py` измеряет три разных случая:

- `one-shot` — весь объём приходит одним полем;
- `growing-history` — история растёт, а прежние сообщения передаются повторно.
- `repeated-field` — один фрагмент повторяется отдельными полями до заданного
  суммарного объёма. Этот профиль измеряет попадания в кэш, обработку большого
  JSON и восстановление ответа, но не заменяет `one-shot` для большого нового
  текста.

Генератор использует только синтетический текст. Размер задаётся числом слов,
разделённых пробелами; фактическое число токенов BERT фиксирует Analyzer в
`presidio_ner_inference`. Проверочные адреса электронной почты размещаются в
начале, середине, около шага BERT-окон и в конце текста.

## Уровни

### Analyzer

```bash
python scripts/benchmark_long_context.py \
  --layer analyzer \
  --url http://127.0.0.1:5001 \
  --profile one-shot \
  --sizes 1000,8000,50000 \
  --repetitions 3 \
  --docker-container presidio-analyzer \
  --run-label warm
```

Этот уровень отделяет Presidio, NER и объединение результатов от LiteLLM и
провайдера.

### LiteLLM с имитацией провайдера

Используйте состав `tests/e2e/docker-compose.ner-proxy.yml`, модель `mock-chat`
и тестовый ключ `sk-test-master`. Он позволяет проверять объёмы до миллиона без
стоимости и ограничения контекста внешней модели.

```bash
docker compose -p ru-llm-proxy-long-context \
  -f tests/e2e/docker-compose.ner-proxy.yml \
  up -d redis mock-upstream presidio-analyzer litellm-mask

LITELLM_BENCHMARK_API_KEY=sk-test-master \
python scripts/benchmark_long_context.py \
  --layer proxy-mock \
  --url http://127.0.0.1:14010 \
  --profile growing-history \
  --api responses \
  --model mock-chat \
  --api-key-env LITELLM_BENCHMARK_API_KEY \
  --sizes 1000,8000,50000 \
  --stream
```

Накопленный контекст с повторяющимися полями объёмом до миллиона условных
токенов:

```bash
LITELLM_BENCHMARK_API_KEY=sk-test-master \
python scripts/benchmark_long_context.py \
  --layer proxy-mock \
  --url http://127.0.0.1:14010 \
  --profile repeated-field \
  --api chat \
  --model mock-chat \
  --api-key-env LITELLM_BENCHMARK_API_KEY \
  --sizes 1000000 \
  --repeated-field-tokens 1000 \
  --timeout 180 \
  --output /tmp/long-context-repeated-field.json
```

После ручного испытания удалите временный состав:

```bash
docker compose -p ru-llm-proxy-long-context \
  -f tests/e2e/docker-compose.ner-proxy.yml down -v --remove-orphans
```

### Полный путь через codex-lb

Используйте отдельный виртуальный ключ LiteLLM и только размеры, которые
поддерживает выбранная модель. Флаг `--allow-real-provider` обязателен, чтобы
исключить случайную отправку большого теста во внешний сервис.

```bash
LITELLM_BENCHMARK_API_KEY='<virtual-key>' \
python scripts/benchmark_long_context.py \
  --layer codex-lb \
  --url http://127.0.0.1:4000 \
  --profile growing-history \
  --api responses \
  --model gpt-5.6-luna \
  --api-key-env LITELLM_BENCHMARK_API_KEY \
  --sizes 1000,8000 \
  --stream \
  --allow-real-provider
```

## Отчёт

По умолчанию результат сохраняется в
`/tmp/ru-llm-proxy-long-context-report.json`. В нём есть параметры запуска,
размеры, HTTP-статусы, полная задержка, время до первого непустого текстового
фрагмента потока,
агрегаты p50/p95/p99 отдельно для каждого размера и количества типов сущностей.
Для HTTP-ошибки сохраняются только ограниченные идентификаторы типа и кода.
Текст запроса, ответ модели, сообщение об ошибке, ключ доступа и значения
найденных сущностей не сохраняются.

Необязательный параметр `--docker-container` можно повторить для каждого
измеряемого контейнера. В отчёт попадут только число выборок, пиковая загрузка
CPU, пиковая рабочая память из `docker stats` и сумма `VmRSS` процессов. CPU
может превышать 100%, если контейнер использует несколько ядер. Для каждого
пика сохраняется время относительно начала измерения. Сбор требует доступной
команды Docker и не включается в короткую проверку CI.

Процентили серии короче 20 повторений являются только ориентиром. Для итоговых
нагрузочных показателей используйте достаточную выборку в задаче #70.

Нагрузочный профиль можно указать безопасными полями, например
`--metadata cpu_profile=8cpu-4gb`. Названия, похожие на ключи и секреты,
отклоняются. Для проверки схемы без HTTP используйте `--dry-run`.

Холодный запуск требует предварительного пересоздания Analyzer; отметьте такой
запуск как `--run-label cold`. Для прогретого состояния сначала выполните
короткий запрос или задайте `--warmup-runs 1`. CPU и RSS снимайте отдельно по
контейнерам через `--docker-container`.

Полный тяжёлый сценарий является ручным: обычный `make test` проверяет только
генератор и схему отчёта, но не создаёт большую нагрузку и не вызывает модель.

## Контрольные результаты порционной обработки

На CPU-стенде из [исходных показателей](long-context-baseline.md) один новый
текст обрабатывался так:

| Синтетические токены | Символы | Время | Пик рабочей памяти | Итог |
| ---: | ---: | ---: | ---: | --- |
| 128k | 768 096 | 96,06 с | 1,18 GB | 4/4 контрольных сущности |
| 256k | 1 536 096 | 211,26 с | 1,17 GB | 4/4 контрольных сущности |
| 512k | 3 072 096 | 481,41 с | 1,14 GB | 4/4 контрольных сущности |
| 1m | 6 000 096 | 1 034,01 с | 1,23 GB | 4/4 контрольных сущности |

Вход 1m прошёл без аварийного завершения из-за нехватки памяти и ошибки spaCy;
после него NER осталась готова. Отдельный
сценарий подтвердил сущность, пересекающую жёсткую границу 128 000 символов.
Это функциональная поддержка размера, а не гарантия интерактивного времени
ответа: штатный тайм-аут защитного слоя равен 30 секундам.

Сквозная проверка входа на 128k синтетических токенов с этим тайм-аутом дала
безопасный отказ прокси за 30,13 с и ни одного вызова провайдера. Analyzer
обнаружил закрытие соединения, остановился на границе пакета BERT и освободил
единственное место выполнения примерно через 31,69 с; NER осталась готова.

Для 14 окон BERT медианы трёх прогонов составили 2,901 с при размере пакета 1,
2,612 с при 2, 2,555 с при 4 и 2,549 с при 8. Выбран пакет 4: ускорение примерно
на 12% относительно последовательного запуска без практически бесполезного
удвоения пакета до 8.

## Ресурсные ориентиры

На локальном ARM64 один процесс Analyzer показал следующие рабочие профили:

| Назначение | CPU | Память |
| --- | ---: | ---: |
| Разработка | 2 | 2 GB |
| Одиночная работа | 4 | 4 GB |
| Производительный экземпляр | 8 | 4 GB |

На 8k медиана уменьшилась с 64,51 с при 1 CPU до 5,56 с при 8 CPU. Увеличение
до 10 CPU выигрыша не дало. Контрольный вход 1m при 8 CPU / 4 GB прошёл за
963,65 с с cgroup-пиком 1,26 GB. Полная таблица, границы применимости и
сквозные результаты приведены в
[исходных показателях](long-context-baseline.md#ресурсное-исследование).

Это профили одного процесса, а не готовая конфигурация для команды. Параллельность,
очередь и число экземпляров определяются в #82; нагрузка 400 пользователей — в
#70. Результаты ARM64 необходимо подтвердить на целевом сервере `x86_64`.
