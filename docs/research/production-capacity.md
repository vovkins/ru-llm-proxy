# Производственное насыщение: локальная диагностика

Исследование [#116](https://github.com/vovkins/ru-llm-proxy/issues/116),
контрольный код `main@c8cc806`, 30–31 октября 2026 (МСК). Это локальные измерения,
не выбранный профиль двух серверов и не подтверждение устранения промышленных 503.

## Условия

- Отдельный одноразовый Compose-проект: штатные 2 LiteLLM, 4 Analyzer,
  2 Triton и их CPU/память/очереди из `production.env`; без codex-lb.
- Настоящая Tiny2/ONNX, Redis, PostgreSQL и Nginx; вместо внешней LLM —
  имитация провайдера, возвращающая плейсхолдер. Оба API, все ответы SSE.
- Лабораторная обвязка проверяет здоровье каждые 3 с и отключает автоматический
  перезапуск. Это не полностью идентичные промышленным эксплуатационные условия.
- Локальный Docker: 10 CPU, 7,75 GiB, ARM64. Основной functional-стенд
  оставался запущенным; это не изолированное сравнение вычислительной ёмкости.
- Независимая отправка волны за 2 с. Каждый контекст новый по всей длине,
  без истории; промах кэша подтверждён для каждого запроса. Один запуск на случай.
  Размеры ниже — единицы по пробелам, не токены внешней LLM.

мест Analyzer были заняты, наблюдаемая очередь достигала 32 ожидающих суммарно.

## Найденный механизм отказа

В [нашей конфигурации Nginx](../../nginx/conf.d/production.conf) HTTP 503 входит
в `proxy_next_upstream` для Analyzer. Ответ истёкшей очереди засчитывается как
неуспех реплики; затем возможны `upstream server temporarily disabled` и
`no live upstreams`. Защитный слой получает общий отказ шлюза и возвращает
`analyzer_unavailable` вместо исходного `analyzer_overloaded / queue_timeout`.
При 64×32k так выглядел 31 из 32 отказов. Это согласуется со штатными правилами
[пассивного исключения Nginx](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server).

Таким образом, низкая общая загрузка и массовые отказы могут сосуществовать:
ограничены активные места/пакеты обработки, а балансировщик усиливает перегрузку.
Только увеличение очереди не обеспечивает ожидание до 60 с. Найденный механизм
подтверждён локально; без журналов промышленного стенда нельзя объявить его
единственной причиной всех производственных 503. После отдельного
[A/B-сравнения](production-nginx-ab.md) в рабочем Nginx отключены повторы
и пассивное исключение Analyzer по HTTP 503. Это правка классификации отказа,
не увеличение вычислительной ёмкости; сетевое переключение сохранено.

## История и отмены

После прогрева неизменной нейтральной истории 50k волна 64×(50k+1k нового)
прошла 64/64 с p95 6,562 с. Это контроль кэша, не модель настоящей агентской
истории с множеством сообщений и чувствительных полей.

Минутная смешанная подача 128 запросов: 125 успехов, один отказ очереди,
два `window_boundary_unresolved`. Последние относятся к известному наблюдению
качества, не к недостатку вычислений. При отмене половины из 16 запросов по 50k:
8 отмен и 8 успехов; активные/ожидающие анализы освободились.

## Сравнение при одном бюджете

Для волны 16×32k: один LiteLLM с 1 CPU, Analyzer суммарно 4 CPU,
Triton суммарно 2 CPU, по два исполнения модели внутри каждого Triton.
`C` — активных анализов на Analyzer, `B` — окон в пакете NER.

| Analyzer | Triton | C/B | Успех | p95 SSE успехов, с |
| --- | --- | --- | ---: | ---: |
| 1 × 4 CPU | 2 × 1 CPU | 2/4 | 10/16 | 37,971 |
| 2 × 2 CPU | 2 × 1 CPU | 2/4 | 13/16 | 40,121 |
| 4 × 1 CPU | 2 × 1 CPU | 2/4 | 16/16 | 39,504 |
| 2 × 2 CPU | 1 × 2 CPU | 2/4 | 15/16 | 38,373 |
| 2 × 2 CPU | 4 × 0,5 CPU | 2/4 | 13/16 | 44,333 |
| 2 × 2 CPU | 2 × 1 CPU | 4/4 | 16/16 | 48,616 |
| 2 × 2 CPU | 2 × 1 CPU | 4/8 | 16/16 | 50,342 |

Отдельное увеличение бюджета Triton до 4 CPU (2×2), при двух Analyzer:
16/16, p95 34,157 с. Увеличение числа Analyzer полезно, но меньшее p95 при
частичных отказах не означает лучшую производительность: медленные запросы
могли просто не попасть в выборку успехов. Повторы Nginx здесь не отключались.

Последний случай `C=4/B=16`, 16×32k, завершился OOM обоих Triton:
`OOMKilled=true`, код 137, лимит каждого 2 GiB. Итоги клиентских запросов
не сохранились до неуспешного чтения метрик и не включены в агрегаты.
Периодический суммарный пик около 5,98 GiB не исключает неснятого всплеска
Docker VM; для строгого разделения контейнерного и общего лимита нужен повтор
со счётчиками `memory.events`. Этот вариант не рекомендуется и не принят.

Одна серия прервана до седьмой волны из-за недоступных файлов прежнего временного
Python-окружения генератора; шесть завершённых волн не отброшены. Продолжение
выполнено отдельно, с независимыми зависимостями и проверкой сертификатов.
Сохранены 40 полных тяжёлых/сравнительных волн: 918 попыток, 785 успехов,
125 отказов и 8 отмен; провайдер получил ровно 785 запросов без открытых
контрольных данных. Неучтённый случай OOM из 16 запросов указан отдельно;
вся матрица не объявляется успешно пройденной.

## Дальнейшие действия

Согласованный [A/B Nginx](production-nginx-ab.md) завершён: вариант без повторов
по HTTP 503 убрал ложное исключение реплик и восстановил Retry-After, но не
увеличил число ответов в пределах 60 с. Минимальная правка с оговорками уже
согласована, реализована и прошла регрессии. Продолжение —
[подбор одноузлового профиля](production-single-node.md) с локальным финалистом
и [контроль кэша/HTTP-пула](production-cache-pool.md). Ошибки измерителя
исправлены; ограничения результатов и новая находка AUTH_TOKEN сохранены.
Новые стандартные значения для 32 CPU / 64 GB и двухузловая схема не выбраны.

Данные: [короткие волны](../../presidio/evaluation/reports/production-capacity-initial.json),
[тяжёлые и сравнительные](../../presidio/evaluation/reports/production-capacity-local.json),
включая неуспехи, счётчики и закреплённые образы. Методика запуска пробника —
в [нагрузочном прототипе](load-prototype.md#независимые-всплески).
Начальные средние скорости CPU намеренно не публикуются: чтение счётчиков
первой короткой серии не имело отдельных временных меток для каждого контейнера;
в тяжёлой серии это исправлено. Волны последовательны, без независимых повторов;
состояние пассивного исключения Nginx могло переноситься на следующий случай.
