# Настройка вычислительного пула

2 ноября 2026, [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Все 55 согласованных волн выполнены. Проверены отдельные параметры,
их сочетания и три подтверждающих повтора. Кратного ускорения не получено:
настроенный 24/12 улучшает своевременность большой волны, но не её p95.
[Данные](../../presidio/evaluation/reports/production-tuning.json),
[предыдущее сравнение плотности](production-density-expanded.md).

## Условия

Тот же сервер: 32 vCPU, 16 ядер с SMT, Intel Ice Lake, 62,79 GiB RAM.
382 файла, образы и комплект Tiny2 неизменны. Общие службы сохранены;
внешние LLM не вызываются, провайдер тестовый. Оба API с SSE, 64 виртуальных
ключа, свежие запросы по 32000 единиц генератора за две секунды.
Это не токены внешней LLM. Хэши входов совпали с предыдущим исследованием;
перед волной очереди освобождены, тестовый кэш очищен.

Ресурсы не менялись: Analyzer 1 CPU / 2 GiB, Triton 2 CPU / 4 GiB.
Один процесс Analyzer, его очередь 32 / 45 с, внутренние очереди Triton
и максимальный пакет 32 сохранены. Лимиты не являются резервированием.
Между вариантами вычисления пересоздавались; БД/Redis оставались прежними.
Применённые параметры проверялись у всех реплик, число экземпляров модели —
также через штатный HTTP API Triton.

C — активные анализы на Analyzer; I — экземпляры модели на Triton;
B — окна в клиентском пакете; H — максимум HTTP-соединений LiteLLM к Analyzer
на цикл событий, сохраняемых соединений H/2. Исходный контроль: C2/I2/B4/H20.

## Предварительный подбор

Шесть контрольных волн R6 24/12 и R5 20/10, затем восемь одиночных изменений
R6 на 64/96 запросах. В каждом одиночном опыте все 64 ответа до минуты.

| Изменение | До минуты на 96 | p95 на 64 / 96, с |
|---|---:|---|
| Контроль R6 | 51/96 | 53,890 / 79,980 |
| C1 | 65/96 | 53,819 / 78,756 |
| C4 | 55/96 | 54,424 / 79,149 |
| I1 | 45/96 | 56,942 / 88,695 |
| I4 | 52/96 | 53,618 / 79,023 |
| B8 | 52/96 | 55,085 / 80,079 |
| B16 | 52/96 | 55,518 / 83,305 |
| H40, сохраняемых 20 | 48/96 | 56,707 / 82,102 |
| H80, сохраняемых 40 | 48/96 | 52,536 / 82,914 |

Правило отбора определено заранее: меньше отказов, больше своевременных
ответов на 64, затем 96, затем меньшая сумма отдельных p95; контроль выигрывает
полное равенство. Сочетания проверены, а не объявлены суммой выигрышей:
C1/I4/B8/H20 дал 64/96 до минуты, C1/I4/B4/H20 — 66/96. Выбран второй;
на 64 запросах оба дали 64/64. Перенос на R5: 59/64 и 60/96 до минуты.
Решение о кандидате принималось по предварительным данным; повторы ниже
проверяют его, а не заменяют неудачные измерения более удачными.

## Подтверждение

Три чередуемых повтора каждого варианта на 32/64/96: 27 волн, 1728 ответов.
p95 в таблице — медиана трёх отдельных p95, не объединённый процентиль.
Своевременность требует точно восстановленного первого текста до 60 с
и корректного завершения SSE. На 32 запросах все дали по 96/96 до минуты.

| Вариант | p95 для 32 / 64 / 96, с | До минуты на 64 / 96 |
|---|---|---|
| R6, C2/I2/B4/H20 | 30,06 / 53,78 / 78,58 | 192/192; 160/288 |
| R6, C1/I4/B4/H20 | 32,51 / 53,83 / 78,56 | 192/192; 197/288 |
| R5, C1/I4/B4/H20 | 31,35 / 60,50 / 83,97 | 180/192; 180/288 |

У R6 дополнительно 37 из 288 ответов до минуты: 55,6% → 68,4%, +12,8 п.п.
Но p95 большой волны практически тот же, на 32 задержка выше на 8,1%.
Следовательно, это улучшение части распределения, не доказанный рост
предельного RPS или универсальное ускорение. Ни один состав не уложил
всю волну 96 в минуту. Вклад I4 относительно одиночного C1/I2 подтверждающие
повторы отдельно не выделяют: предварительная разница была один ответ.

## Ресурсы И Очереди

В подтверждающих волнах CPU всего хоста по `/proc/stat`; пики — максимумы
интервальных средних, не мгновенные значения. RAM — выборочная сумма
`memory.current` состава, снятая последовательно, не точный пик всего хоста.

| Вариант | Среднее CPU | Пик CPU из 32 | Интервал пика | RAM состава |
|---|---:|---:|---:|---:|
| R6, исходный | 24,97 | 31,80 (99,4%) | 3,42 с | 22,03 GiB |
| R6, настроенный | 22,41 | 27,68 (86,5%) | 3,37 с | 24,75 GiB |
| R5, настроенный | 19,40 | 23,66 (73,9%) | 3,20 с | 21,29 GiB |

Выборочный максимум активных/ожидающих полей: исходный R6 — 42/0,
настроенный R6 — 24/17, настроенный R5 — 20/20. Суммы неатомарны.
При C1 ожидание стало видно в очереди Analyzer; это не устранение ожидания.
Чистый внутренний таймер HTTP-пула здесь не измерялся. Его простое расширение
не улучшило своевременность одиночного опыта; причина всех задержек этим
не установлена. Очереди не переполнялись, увеличение их размеров не проверялось.
На B16 реально исполнялись пакеты до 32; у подтверждаемых вариантов — до 8.
Это не проверка худшей памяти всех сочетаний или неограниченной длительности.

За весь этап пик состава 32,57 GiB был у C1/I4/B8 на волне 96,
минимум доступной RAM хоста 28,31 GiB. OOM, достижения лимитов и защитных
остановок нет. Максимальный пик одного Triton 1,81 GiB; лимит 4 GiB не снижали.
Все 60 338 строк содержат `memory.stat`. Сохранены 19 пропусков из 27 264
опросов очередей в сравнительных волнах и 70 сбросов статистического соединения
при замене контейнеров вне клиентских волн. Внутри волн ошибок статистики Triton
нет. Максимальный интервал CPU во время волн 5,39 с; короткие пики неизвестны.

## Итог И Границы

3872/3872 сравнительных ответа корректны, 2984 до минуты. С прогревами
3960/3960 корректны, 3072 своевременны, по 1980 на API. 503, утечек маркеров
провайдеру, ошибок восстановления и целевых ошибок Nginx нет. Все опоздания
сохранены. Максимальная задержка старта генератора с прогревами 89 мс.
В сквозных запросах и прогревах 141 207 781 токен NER / 444 906 окон.
Отдельно выполнены 220 прямых проверок Analyzer: десять фиксированных примеров
на каждый из 22 запусков. Типы, границы и количество сущностей совпали с
контролем при пороге 0,35; точные float-оценки не сравнивались. Это ограниченная
регрессия, не новая полная приёмка качества. Ранее принятые ограничения сохранены.

Для следующей приёмки оставляем настроенный R6 как кандидата для всплесков,
исходный R6 — как контроль с меньшей задержкой на 32. Пакет C1/I4 не рекомендуем
для R5 при требовании всех 64 ответов до минуты; саму плотность 20/10 это
не опровергает. Production-настройки автоматически не менялись. Дальше нужны
постоянная подача, смешанные истории/кэш, большие файлы, отмены и отказы.
Два узла согласуются отдельно; обслуживание 400 пользователей не подтверждено.

Прошли 123 частные и 136 адресных проверки локально и на Linux, локально
также 804 статические, 32 проверки Make и 869 проверок защитной обработки.
Наборы пересекаются. Все 382 файла и исторические измерения неизменны.
Вычисления испытаний остановлены с кодом 0, БД/тома сохранены, локальный
стенд 8/8 healthy. Прежний сбой готовности остаётся открытым; собственных
повторов волн и принудительных reload нет. Платформенный код не меняли.

Следующий подэтап: [постоянная подача и кэш](production-steady-cache.md),
частичный результат с отдельным согласованием нового случая отказа.
