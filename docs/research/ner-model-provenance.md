# Происхождение и целостность модели NER

## Закреплённый артефакт

Analyzer использует модель
[`Katerina-Bir/rubert-tiny2-secret-detection`](https://huggingface.co/Katerina-Bir/rubert-tiny2-secret-detection)
в ревизии `4137142e79d52b0b69370e0e3dceb2d6ad82591d`:

- архитектура `BertForTokenClassification`;
- базовая модель `cointegrated/rubert-tiny2`;
- лицензия MIT; сведения о весах и обучающих данных подтверждены владельцем
  после получения сведений автора (#110);
- восемь типов сущностей: `PERSON`, `LOCATION`, `ORGANIZATION`, `LOGIN`,
  `PASSWORD`, `AUTH_TOKEN`, `SECRET_KEY`, `CONTRACT_NUMBER`.

Перед промышленным распространением образа владелец установки должен провести
принятую в организации проверку лицензий модели, базовой модели и зависимостей.

Название DeepPavlov остаётся в неизменяемых исторических отчётах. Активного адаптера
DeepPavlov, его архива, библиотек `deeppavlov` и `pytorch-crf` в коде и образе
Analyzer нет.

## Граница заимствования

Сборка автоматически получает шесть разрешённых файлов: конфигурацию, словарь,
настройки токенизатора, быстрый токенизатор и веса `safetensors`. Все шесть нужны
стадии экспорта. В рабочий Analyzer передаются только файлы токенизатора и
конфигурации, в Triton — ONNX. Код, сценарии запуска и набор правил из репозитория
автора модели автоматически не загружаются и не выполняются.

Правила из репозитория модели рассматриваются отдельно: каждое из них должно
пройти сравнение с действующими распознавателями проекта, проверку ложных
срабатываний, тестирование и явное решение о переносе.

## Воспроизводимость

Файл [`presidio/model_manifest.json`](../../presidio/model_manifest.json)
закрепляет идентификатор, точную ревизию, список разрешённых файлов, размеры и
SHA-256. Сборка выполняется во временный каталог и завершается только после
проверки всех файлов. Тот же манифест помещается в образ. Analyzer проверяет
своё подмножество файлов, экспорт и совместимость сервера; исходные веса ему
не нужны.

Для Triton сборка создаёт ONNX FP32/opset 17 и `export-manifest.json` с хэшами
всех шести источников, графа и порядка меток, вариантом весов и версиями средств
экспорта. Один результат сборки передаётся Triton и Analyzer. Triton проверяет
байты графа при старте, Analyzer сравнивает ответ сервера с локальным доверенным
описанием. Подпись кэша учитывает это описание; первый ответ сервера не является
источником ожидаемого хэша. Проверка обеспечивает согласованность доверенной
поставки, а не удалённую аттестацию произвольного сервера.

Вариант весов уже содержит поправку +2 для PERSON/LOCATION/ORGANIZATION;
экспорт не добавляет её повторно и не включает отдельную O-поправку декодера.
Численное сравнение экспорта не заменяет оценку качества распознавания.

Transformers/PyTorch работают только при экспорте, с локальными проверенными
файлами и без выполнения кода автора модели. Во время обработки запроса их нет
в Analyzer: он использует `tokenizers`, NumPy и HTTPX. Triton исполняет локальный
ONNX через ONNX Runtime. Перед готовностью Analyzer выполняет контрольный вызов
модели через внутренний Nginx; загрузка файлов без успешного вывода не считается
готовностью. Доступ к Hugging Face при обработке не требуется.

Стадия загрузки модели не зависит от Python-библиотек. Docker-цель
`analyzer-test` содержит `pytest`, но не веса NER. Рабочая цель `analyzer`
не содержит вычислительных весов, PyTorch/Transformers, тестовых зависимостей,
компиляторов и `curl`. `make test-hf-model` проверяет состав и метаданные
изолированным запуском с `--network none`, затем запускает реальный Analyzer,
Nginx и Triton в Docker-сети с `internal: true`. Отсутствие внешней сети не
означает отсутствия внутреннего HTTP-соединения с моделью.

## Обновление и откат

Модель обновляется отдельной веткой по точной ревизии, а не по `main` или
плавающему тегу.

1. Проверить карточку, лицензию, архитектуру, базовую модель и набор меток.
2. Скачать только необходимые файлы и проверить, что они не требуют
   `trust_remote_code=True`.
3. Обновить `presidio/model_manifest.json`: ревизию, список файлов, размеры и
   SHA-256.
4. При изменении меток обновить программный контракт и тесты совместимости.
5. Собрать без кэша оба образа и выполнить `make test-hf-model`; изоляцию
   проверки состава и внутреннюю сеть реального вывода создаёт тестовая обвязка.
6. Выполнить модульные, интеграционные и прокси-проверки из
   [ner-migration-test-coverage.md](ner-migration-test-coverage.md).
7. Прогнать обезличенный оценочный корпус через `make ner-evaluate` и сравнить
   результат с неизменяемой исходной точкой.
8. Зафиксировать ревизию образа и результаты проверки до слияния.

Откат не требует совместной поддержки двух моделей. Разверните предыдущий
проверенный выпуск целиком и повторите проверки. Рабочая установка должна ссылаться на проверенный тег или
digest образа, чтобы откат не зависел от состояния внешнего репозитория модели.
