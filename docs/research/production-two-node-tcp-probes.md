# Два Узла: Проверка TCP-Проб

4 ноября 2026, [#116](https://github.com/vovkins/ru-llm-proxy/issues/116).
Основа v0.6.0, `7587d02`; [итоговые данные](../../presidio/evaluation/reports/production-two-node-tcp-probes-paired.json),
[первая попытка](../../presidio/evaluation/reports/production-two-node-tcp-probes.json).
**Согласованный прототип прошёл 52/52 MASK-запроса и 4/4 BLOCK-проверки.
LINK-03 проверен с TCP-пробами; промышленная двухузловая схема ещё не принята.**

## Конфигурация И Изоляция

В отдельной копии центрального Nginx 1.27.5 добавлен только
`proxy_socket_keepalive on` в маршрут входа анализа к пулам A/B.
Предыдущие health-маршрут и отключённое хранение свободных соединений сохранены.
POST-бюджеты 240/1200 с, правила повторов, модель и платформы не менялись.
Конфигурация Nginx B побайтно прежняя; оба `nginx -t` прошли.

Только испытательному контейнеру A заданы через Compose:

```yaml
sysctls:
  net.ipv4.tcp_keepalive_time: "10"
  net.ipv4.tcp_keepalive_intvl: "5"
  net.ipv4.tcp_keepalive_probes: "3"
```

Параметры применились: A использовал 10/5/3, хост до/во время/после удаления
опыта сохранил 7200/75/9. В итоговом прогоне B до и после сохранил 7200/75/9.
В первой остановленной попытке повторный снимок B отсутствовал; её данные сохранены.
Сетевые пространства A, B и хоста различаются, privileged и host network
не используются. Параметры хоста не записывались.

Это TCP-проверки существующего соединения, не возврат HTTP-кэша свободных
соединений. В итоговом опыте первая неуспешная попытка к B заняла 25.837 с;
это одно измерение, не гарантия фиксированного срока обнаружения
([Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_socket_keepalive),
[Linux](https://docs.kernel.org/networking/ip-sysctl.html),
[Compose](https://docs.docker.com/reference/compose-file/services/#sysctls)).

## Что Проверено

Прежний сервер 32 vCPU / 62.79 GiB, два проекта на одном Docker-хосте,
по 2 Analyzer / 1 Triton. Образы и модель совпадают с прошлым опытом.
Промышленные настройки не менялись. Использован тестовый провайдер,
внешние LLM не вызывались; проверка двух физических хостов не выполнена.

| Проверка | Результат |
|---|---|
| MASK, оба API × stream false/true | 8/8 точных ответов |
| Всплеск 20 новых около 8k входов за 2 с | 20/20, p95 11.938 с, максимум 12.552 с |
| Два пересекающихся длинных контроля около 128k | A 45.144 с, B 44.279 с, оба точные |
| BLOCK, оба API × stream false/true | 4/4 HTTP 422, провайдер не вызван |
| Восемь новых запросов после разрыва связи | 8/8, максимум 5.795 с |
| Возврат связи | 8/8, максимум 0.659 с |
| Потеря активного B при двух запросах | Контрольный 11.182 с, целевой 36.662 с, оба точные |
| Возврат после активного отказа | 4/4, максимум 0.299 с |
| Финальное состояние и готовность | Пройдены, OOM и незапланированных рестартов нет |

Единицы объёма здесь по пробелам, не токены LLM. Все исходные маркеры
восстановлены точно, провайдер не получил контрольный телефон, проверенные
временные замены Redis очищены. Это ограниченная приёмка на одном Docker-хосте,
не проверка промышленного размещения двух физических серверов.

## Доказательства TCP И Повторов

В здоровом межузловом POST четыре TCP-пробы получили четыре ACK до появления
HTTP-ответа; первая проба через 10.101 с, ответ через 43.705 с. Длительное
вычисление не вызвало ложного отказа. При потере активного B три пробы остались
без ответа. Доставка тела POST до разрыва подтверждена ACK; после разрыва
пакетов этого соединения от B не было.

Центральный Nginx записал две попытки одного целевого POST: B — `502` за
25.837 с, A — `200` за 10.666 с. Клиент получил точный ответ за 36.662 с.
Это существующая политика `error http_502 non_idempotent`, не добавленный
повтор по таймауту. Принятые операции Triton автоматически не переотправлялись
изменением конфигурации, но **сам анализ выполнен заново на A**: у целевого
request_id есть успешные выполнения B и A. Первый независимый A-контроль —
третье выполнение. Метрики группы Triton A54/B27 включают все три анализа;
нельзя приписывать все 54 вызова целевому запросу. Провайдер получил два
безопасных запроса для двух клиентских обращений, не три.

Целевой запрос — Chat без stream, как в исходном LINK-03, но его синтетический
текст на одно слово длиннее: два параллельных входа должны различаться.
Это проверка того же класса отказа, не побайтно идентичный A/B. Для волн
8/20/8 хэши исходных входов совпадают. В записи 1681 пакет, потерь захвата нет;
54 HTTP-запроса имеют свежие соединения. TCP seq проверены подробным чтением
сохранённого pcap: обычный вывод tcpdump скрывает seq пустых ACK.

## История Обвязки

В первой попытке для каждого длинного запроса журнал Nginx на том же входном
соединении подтверждает пару: успешный `GET /api/v1/health` к B, через
11–13 мс — `POST /api/v1/analyze` к местному A. Счётчики каждого опыта:
одна обработка Analyzer A, ноль B; Triton A 112 вызовов, B ноль.

Обвязка ошибочно рассчитывала получить B повторением последовательных
запросов. Но health и анализ балансируются независимо, и в этом прогоне
парные обращения сохраняли порядок B/A. Это не доказанная неисправность
балансировщика и не отказ NER: все четыре ответа корректны. Длительность
более 25 с была получена, но не на нужном межузловом соединении.

Запись испытательной связи: 960 пакетов, потерь захвата нет; 30 свежих
соединений с 16 GET и 14 POST, HTTP-повторного использования нет. Совпавших
TCP-проб и ответов оценщик не обнаружил. Нельзя считать, что длительные
локальные запросы доказали работоспособность TCP-проб к B.

Повторены 54 частные регрессии (15 новых) и `make test-static` на Python 3.12:
820 pytest и 32 проверки Make успешны. Это не заменяет отсутствующее
межузловое покрытие и не меняет неполный статус опыта.

После четырёх согласованных попыток первый сценарий штатно остановился на запрете
ложной приёмки. Исходный статус `failed` сохранён; в сводке уточнено
`incomplete_harness_control_routing`, а не ошибка продукта. Временные
контейнеры/сети/тома удалены, прежние 44 контейнера неизменны; локальный
стенд не затрагивался. Сырые ответы, журналы и пакеты остаются приватными.

Во втором прогоне парный контроллер получил длинный B-контроль и четыре
ответа на TCP-пробы; 49/49 MASK и 4 BLOCK успешны. Но прежний последовательный
сценарий активного отказа снова не получил B и остановился до отключения.
После отдельного согласования тот же контроллер применён и там. Максимум
два запроса, второй только при занятом A; веса и маршруты не менялись.
Каждый результат связан с Analyzer по уникальному размеру входа, а с Nginx —
по request_id. Агрегатная активность B не считается маршрутом обоих запросов.

Третий прогон прошёл всю согласованную матрицу. Старые неуспехи сохранены
отдельно, их `failed` не заменён на успех. Образы, модель и конфигурации Nginx
всех трёх попыток совпадают; менялась только частная обвязка.

## Границы Вывода

Платформенный и рабочий код не менялись. Исправления пока только в прототипе;
рекомендация локальных пулов и окончательный выбор схемы требуют решения
владельца перед пунктом 6. Настоящие два хоста, сеть 10 Гбит, полный профиль,
длительная нагрузка и ёмкость 400 пользователей этим не приняты. Отказы Triton
и целого проекта проверялись в предыдущем health-варианте, не повторялись
в последнем TCP-прогоне. Нулевых отказов при любой потере сети не обещаем.

После итогового прогона повторены 74 частные регрессии и `make test-static`
на Python 3.12: 820 pytest и 32 проверки Make успешны. Временные ресурсы
удалены, прежние 44 серверных контейнера и локальные восемь сохранены.
