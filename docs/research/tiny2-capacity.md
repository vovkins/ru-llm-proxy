# Tiny2/Triton: скорость, очереди и ресурсы

Итог Э13, 29 октября 2026 года: сводка **существующих локальных измерений**,
не новый нагрузочный прогон. [Качество по всем классам и ограничения](tiny2-quality-comparison.md)
приняты владельцем с явными оговорками. Серверная ёмкость 400 пользователей не подтверждена.

## Измеренный эффект

Docker Desktop ARM64: 10 CPU / 7.75 GiB. В прямом сравнении бюджет анализа
одинаков: BERT Analyzer 4 CPU / 4 GiB; Tiny2 Analyzer 2 CPU / 2 GiB + Triton
2 CPU / 2 GiB. LiteLLM отдельно, провайдер тестовый. Размеры ниже — **слова
синтетического генератора**, не токены внешней LLM; модель прогрета, результат
нового анализа отсутствует в кэше. p95 относится только к успешным запросам.

| Уровень / сценарий | BERT | Tiny2/Triton |
|---|---|---|
| Только Triton HTTP, одно окно 386 позиций, 32 последовательных вызова | Не измерялся этим способом | p50 37.6 мс; 32/32. Это не обработка всего текста |
| Полный Analyzer, новый 1k / 8k / 50k, p50 | 1.172 / 9.725 / 68.276 с | 0.145 / 1.172 / 7.803 с |
| Полный прокси, новый 1k, 8 клиентов | 38/38; 0.77 успешных/с; p95 10.57 с | 259/259; 6.31/с; p95 1.26 с |
| Полный прокси, повтор 1k, 8 клиентов | 391/391; 13.07/с; p95 49 мс | 456/456; 15.25/с; p95 **88 мс**, хуже BERT |
| Полный прокси, новый 8k, 4 клиента | 6/7; 0.092/с; p95 39.29 с | 35/35; 0.80/с; p95 5.04 с |
| Analyzer, новый 1M | Не измерялся | 160.14 с, 3380 окон, 1068329 NER-токенов с перекрытиями |
| Прокси, новый различающийся файл 1M / последний шаг накопленной истории 1M | Не измерялся | 174.59 с / около 82 с; HTTP 200 и точное восстановление |

Это сравнение готовых конфигураций, включая облегчённый spaCy и интеграцию,
не изолированное ускорение весов. Э10 измерен **до K01–K07 и исправления отмены**;
после них проведены отдельные регрессии/функциональная матрица, не повтор всей
нагрузочной матрицы. Модель и ONNX закреплены теми же SHA. История использует
кэш прежних сообщений, новый файл — нет. Миллион единиц генератора не доказывает
поддержку миллиона токенов конкретной внешней модели/подписки.

## Всплески и устойчивый поток

При одном Analyzer, двух активных анализах, очереди 32 и ожидании 30 с,
Triton 2 CPU / два исполнения: **180/180** запросов в повторённых волнах
10–20 за 2 с, размер 1k/8k; максимум 17 с. Но 20 новых по 50k дали **6/20**,
остальные — `queue_timeout`. Увеличение длины очереди при ожидании 1 с не помогло.
Та же настройка 32/30 с полезна и BERT: короткая волна 20/20 вместо 2/20,
поэтому весь выигрыш нельзя приписывать Tiny2.

Лучший короткий сквозной поток: два Analyzer по 1 CPU и два Triton по 2 CPU,
622/622, 13.53 успешных/с за 45 с при 16 замкнутых клиентах. Это не открытый поток
160/с и не длительная ёмкость. Намеренная перегрузка дала 287 успехов / 1887 HTTP
503 с `Retry-After: 1`. Очереди ограничены, находятся в памяти каждого процесса,
не являются надёжными фоновыми заданиями и не гарантируют отсутствие 503.
Подробная [матрица очередей](tiny2-queues.md) сохраняет все исходы и повторы.

## Стандартные профили и границы приёмки

| Параметр | functional | production |
|---|---:|---:|
| LiteLLM / Analyzer / Triton | 1 / 1 / 1 | 2 / 4 / 2 |
| Процессов в Analyzer / активных анализов / очередь | 1 / 2 / 32 | 1 / 2 / 32 |
| Ожидание / пакет окон / исполнений модели на Triton | 30 с / 4 / 2 | 30 с / 4 / 2 |
| Суммарные лимиты CPU / RAM, базовый состав | Без навязанных лимитов | 20 CPU / 48.25 GiB |
| То же, с codex-lb и его БД | Без навязанных лимитов | 23 CPU / 54.25 GiB |

Это согласованный **начальный профиль** для сервера 32 CPU / 64 GB,
не измеренное потребление и не доказанный оптимум. 64 GB меньше 64 GiB;
нужен запас ОС. Распределение по компонентам — в [инструкции](../deployment.md#ресурсы-production).
В коротком быстром прогоне наблюдались пики двух Analyzer около 619 MiB,
двух Triton 1018 MiB, LiteLLM 825 MiB: их нельзя использовать как лимиты
миллионного контекста. Redis 16 GiB учитывает 12.5 GiB состояния на 400 ключей
по 32 MiB, но кэш и накладные расходы тоже требуют памяти; предельное заполнение
не проверялось. Длительная смесь 400 ключей остаётся отдельным экспериментом.

Э12 подтвердил обе топологии/политики и 1/2 Triton: **10/10**, восстановление
**13/13**. При остановке реплики в Э10 были 172 временных 503 при 370 успехах:
восстановление не означает бесшовный отказ. POST-инференс автоматически не
повторяется. Кооперативная отмена своим ASGI-адаптером через публичный API LiteLLM
проверена отдельно; в TCP-контролях освобождение занимало около 0.11–0.35 с,
но это не SLA и не мгновенная остановка уже принятого вычисления Triton.

**Открытые наблюдения:** T01 (причина старого AssertionError не найдена),
CANCEL-OBS-01 (редкий таймаут/задержка освобождения HTTP; один контроль Э12
повторил задержку более 5 с после ожидаемого 503), LIVE04 (GLM Chat-stream:
34 успеха / 1 неуспех, причина неизвестна). Последующие успешные повторы не
отменяют эти события. Отдельный сетевой дефект тестовых подсетей исправлен,
но не объявлен причиной T01. Новых LLM-вызовов в Э13 нет.
Корпоративные посредники, настоящие приложения Codex/OpenCode, GPU и целевой
сервер этим локальным пакетом не проверены. Сервер не арендуется автоматически.

## Э10: производительность Tiny2/Triton на CPU

Локальное сравнение кандидата PR #109 с `main@1c8c78d`, 26 октября 2026 года.
**Это не приёмка миграции:** потери покрытия и ложные срабатывания из [Э9](tiny2-quality-comparison.md) остаются открытыми.
Числа не являются гарантией промышленной ёмкости или поддержки 400 активных пользователей.
В [дополнительной матрице очередей](tiny2-queues.md) отдельно проверены агентские

## Условия и воспроизводимость

- Docker Desktop ARM64: 10 CPU, 7.75 GiB RAM. Все образы ARM64, без эмуляции x86_64; эксперименты последовательные.
- Эталон: BERT/полный spaCy из свежего `main`; кандидат: Tiny2 `4137142e`, FP32 ONNX `0c418bfe`, Triton CPU/облегчённый spaCy из Э9. Исполняемые исходники проверены, распознавание и пороги не менялись.
- Только изолированный тестовый провайдер. Замер сквозного прокси включает настоящий LiteLLM, guardrails, Analyzer, Nginx, Redis, PostgreSQL и проверку восстановления исходного значения. Реальные подписки не нагружались.
- Единица размера — слово синтетического генератора, **не токен внешней LLM**. В JSON сохранены символы, UTF-8, SHA текста, реальные NER-токены/окна, параметры, образы, ошибки, кэш, очереди и ресурсы.
- Счётчик NER-токенов суммирует токены входных фрагментов с внешними перекрытиями Analyzer; он не включает повтор позиций во внутренних окнах и заполнение пакетов. Поэтому фактическую работу модели дополнительно характеризует число обработанных окон.
- Нагрузочный текст нейтральный с контрольным `EMAIL_ADDRESS`; новый файл дополнительно различает фрагменты каждые 32 слова. Это не реальная кодовая база и не проверка качества всех классов: для неё служит Э9.
- «Холодный ввод» означает отсутствие результата анализа в кэше, а не первый запуск контейнера. Модель уже загружена и проверена. Короткие единичные прогоны не заменяют длительное испытание; p95/p99 относятся только к успешным запросам, отказы показаны отдельно.
- Данные: [машинный отчёт](../../presidio/evaluation/reports/tiny2-capacity.json). Обвязка: существующие `tests/load/run.sh`, `locustfile.py`, `sample_metrics.py`, `compare_runs.py`; низкоуровневый измеритель `tests/load/ner_capacity_probe.py` запускается только в одноразовом изолированном процессе, не в рабочем сервисе. Новых Make-команд нет.

Повтор сквозного сравнения двумя Analyzer/одним Triton через существующую команду (результат зависит от оборудования):

```bash
LOAD_USERS=16 LOAD_RUN_TIME=45s LOAD_PACE_SECONDS=0.1 \
LOAD_API=mixed LOAD_STREAM=mixed LOAD_CONTEXT_MODE=one-shot \
LOAD_CONTEXT_SIZES=1000 LOAD_INPUT_VARIATION=unique \
LOAD_ANALYZER_REPLICAS=2 LOAD_ANALYZER_CPUS=1 LOAD_ANALYZER_MEMORY=2g \
LOAD_ANALYZER_CONCURRENCY_LIMIT=1 LOAD_ANALYZER_QUEUE_LIMIT=16 \
LOAD_ANALYZER_QUEUE_TIMEOUT_SECONDS=30 LOAD_TRITON_REPLICAS=1 \
TRITON_CPUS=2 TRITON_MODEL_INSTANCES=2 \
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 \
bash tests/load/run.sh steady
```

Скрипт создаёт собственный тестовый состав и удаляет его после проверки. Образы сравниваемых измерений зафиксированы в JSON; обычный повтор собирает текущие исходники. Суммарные ограничения памяти служебных контейнеров в этой команде могут отличаться от исследовательского стенда, где они были специально уменьшены для локального узла.

## Сравнение полного прокси

Суммарный бюджет анализа одинаковый: эталон Analyzer 4 CPU/4 GiB; кандидат Analyzer 2 CPU/2 GiB + Triton 2 CPU/2 GiB. LiteLLM отдельно 2 CPU/1.5 GiB, одинаковые служебные контейнеры. `OMP/MKL/OpenBLAS=2`, пакет окон 4. Лимит CPU не означает фактическое постоянное потребление всех ядер.

| Ввод | Эталон: успешных / всего | Эталон: успешных/с, p95 | Tiny2: успешных / всего | Tiny2: успешных/с, p95 |
|---|---:|---:|---:|---:|
| Новый, 1000 единиц, 8 клиентов | 38/38 | 0.77; 10.57 с | 259/259 | 6.31; 1.26 с |
| Повтор, 1000, 8 клиентов | 391/391 | 13.07; 49 мс | 456/456 | 15.25; 88 мс |
| Новый, 8000, 4 клиента | 6/7 | 0.092; 39.29 с | 35/35 | 0.80; 5.04 с |

В среднем вводе эталона один HTTP 503 по ожиданию очереди, не ошибка NER. Восстановление всех успешных ответов проверено. У кандидата новый короткий ввод дал 259 промахов кэша; повторный — 448 попаданий из 456. Ускорение NER не означает такого же выигрыша на прогретом кэше: его p95 у кандидата здесь хуже.

Непосредственно полный Analyzer при одном клиенте: p50 на 1000/8000/50000 единиц изменился с 1.172/9.725/68.276 с до 0.145/1.172/7.803 с. Подготовка целого текста на 50000 планирует 157 окон, но внешнее разбиение Analyzer с перекрытием фактически обрабатывает 167 окон и около 52737 NER-токенов. Планируемая и реальная работа не смешиваются.

## Параллельность и очереди

| Вариант | CPU анализа | Успешных / всего | Успешных/с | p95 |
|---|---:|---:|---:|---:|
| 1 Analyzer, 2 активных; 1 Triton, 2 экземпляра модели | 2 + 2 | 412/412 | 8.86 | 1.95 с |
| 2 Analyzer по 1 активному; тот же Triton | 2 x 1 + 2 | 515/515 | 11.12 | 1.51 с |
| 2 Analyzer по 2 активных; 2 Triton по 2 экземпляра | 2 x 1 + 2 x 2 | 622/622 | 13.53 | 1.28 с |

Это 16 клиентов, интервалы 0.1 с, прогоны по 45 с. Номинальные 160 запросов/с замкнутого генератора **не достигнуты**: клиент ждёт ответ перед следующим запросом. Указана фактическая скорость; незавершённых запросов нет.
Среднее ожидание очереди Analyzer в этих трёх вариантах — 1.39/1.11/0.74 с соответственно; даже на коротком вводе оно составляет существенную часть задержки.

- На уровне Analyzer два экземпляра модели в одном Triton и два Triton при том же CPU дали примерно одинаковые 9.7 запроса/с. Удвоение контейнеров без CPU не удваивает ёмкость.
- Пакет 16 оказался хуже пакета 4: около 8.8 вместо 9.7 запроса/с. Четыре активных анализа добавили немного скорости, но ухудшили хвост задержки. Эти настройки пока не предлагается применять по умолчанию.
- Один большой запрос и три коротких при ожидании очереди 1 с: с одним активным анализом короткие получили 3/3 HTTP 503; с двумя активными/двумя экземплярами модели — 3/3 HTTP 200 за 0.60–0.96 с.
- Открытый поток непосредственно к Analyzer, 32 запроса: при 8/с — 28/32 против 32/32; при 16/с улучшенный вариант дал 30/32, фактически 10.9 успешных/с. Дополнительная очередь не заменяет вычислительные ресурсы.
- Намеренная перегрузка полного прокси: 287 успешных, 1887 HTTP 503, все с `Retry-After: 1`. Тестовый провайдер получил ровно 287 запросов, исходного контрольного значения не видел.

## Большие контексты

Последовательный новый запрос непосредственно к Analyzer, без кэша; один замер на размер, не статистика p95:

| Единиц генератора | UTF-8, байт | Время | Результат |
|---:|---:|---:|---|
| 128000 | 2176004 | 20.54 с | HTTP 200 |
| 256000 | 4352004 | 41.05 с | HTTP 200 |
| 512000 | 8704004 | 81.83 с | HTTP 200 |
| 1000000 | 17000004 | 160.14 с | HTTP 200 |

Миллион единиц: фактически 1068329 NER-токенов с перекрытиями, 3380 окон; из 159.85 с серверного анализа около 110.40 с приходится на NER, 48.41 с — на Presidio, 1.02 с — на слияние. Поэтому ускорение одной модели не устраняет остальную стоимость обработки.

Сквозная история: 7/7 успешных запросов для `/responses` с SSE и 7/7 для `/chat/completions` без потока, от 1000 до миллиона единиц. Последний запрос занял 82.06/82.46 с; на этом шаге добавлено 488000 новых единиц, а прежние сообщения уже проанализированы. Для каждой последовательности — 21 попадание кэша и 7 промахов. Отдельно `previous_response_id`: 30/30, зашифрованное состояние: 69/69, оба с потоковыми и обычными ответами. Исходные значения восстановлены; незавершённых запросов нет.

Новый файл с различающимися фрагментами через полный прокси и `/responses` SSE: 128000 единиц за 22.96 с, миллион за 174.59 с; HTTP 200 и точное восстановление в обоих случаях. Миллионный файл: 16215287 байт UTF-8, 1134012 фактически обработанных NER-токенов, 3553 окна. Тестовый провайдер получил по одному запросу с плейсхолдером, без открытого контрольного значения.

Накопленную историю нельзя выдавать за новый файл: кэш прежних сообщений заметно меняет результат. Зашифрованное состояние здесь синтетическое, реальный провайдер его не расшифровывал. Реальные LLM, Codex и OpenCode в Э10 не запускались.

## Ресурсы и ограничения

В самом быстром сквозном коротком прогоне наблюдаемые пики памяти: два Analyzer суммарно около 619 MiB, два Triton около 1018 MiB, LiteLLM около 825 MiB. Это выборочные наблюдения короткого ввода, **не рекомендуемые лимиты** для больших файлов и не максимумы при 400 пользователях. Служебные контейнеры и генератор также потребляют память.

Остановка одной из двух реплик Triton на 8 с: 370 успешных и 172 временных HTTP 503 (`Retry-After` 1 или 5 с); последние 20 ответов после возврата — HTTP 200. Автовосстановление подтверждено, отсутствие ошибок во время отказа — нет. Запросы инференса через Nginx Triton автоматически не повторяются. Маршрут Analyzer допускает повтор чистого анализа на другой реплике; это не повтор обращения к провайдеру LLM.

Повтор матрицы развёртывания: 10/10 вариантов (оба состава, MASK/BLOCK, функциональная/промышленная топология, один/два Triton), включая восстановление, масштабирование и отсутствие повторного POST-инференса. Пик суммарной памяти тестовых контейнеров — 3.82 GiB. Первоначальный T01 из Э9 не воспроизведён повторно, но его причина не установлена и не объявляется исправленной.

Отмена 50000 единиц во время подготовки: очередь/активные задачи освободились, следующий короткий запрос — HTTP 200 за 162 мс. Отмена после начала модельных вычислений: счётчик завершённых вызовов Triton вырос с 11 до 13, число окон с 41 до 46, затем оставался неизменным на проверках через 1 и 3 с; активных задач и локальных HTTP-вызовов не осталось. Следующий запрос — HTTP 200 за 147 мс. Эти счётчики включают служебную работу; по ним нельзя доказать точный момент начала каждого вызова. Мгновенная отмена уже принятого инференса не гарантируется.

## Что проверять дальше

Кандидат для следующего серверного измерения: два Analyzer, пакет 4, по 1–2 активных запроса; один/два Triton с двумя экземплярами модели. Окончательные CPU, память, очередь и ожидание определяются по смеси размеров/новизны, а не по лучшей строке таблицы. Настройки рабочего развёртывания этим отчётом не меняются.

400 пользователей с одним запросом раз в 30/15/5 с — сценарии 13.3/26.7/80 запросов/с, не установленная статистика пользователей. Локальные 13.53/с на коротком холодном вводе не дают запаса даже первому сценарию и не покрывают длинные запросы. Отдельно нужны открытый поток, смесь накопленной истории и новых файлов, длительный прогон, отмены, отказы и контроль памяти Redis. Квота 32 MiB x 400 ключей допускает 12.5 GiB только диалогового состояния, без накладных расходов.

Для измерений предлагается отдельный CPU-сервер x86_64: 16 vCPU, 64 GiB RAM, 150 GB SSD; предпочтительно отдельный генератор 4 vCPU/8 GiB.
