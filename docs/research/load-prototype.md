# Нагрузочный прототип

Прототип в [`tests/load/`](../../tests/load/) измеряет путь
`LiteLLM → защитный слой → Analyzer → имитация провайдера` с настоящими Redis и
PostgreSQL. Он не использует ключи и квоты внешних моделей.

## Быстрая проверка

```bash
tests/load/run.sh smoke
```

Сценарий собирает изолированный Compose-проект, создаёт отдельный временный
ключ LiteLLM для каждого виртуального пользователя, выполняет тест и удаляет
ключи, контейнеры, сеть и том с ключами. Отчёты остаются в выведенном каталоге
`/tmp/ru-llm-proxy-load-*`.

## Профили

| Команда | Нагрузка по умолчанию |
| --- | --- |
| `tests/load/run.sh smoke` | 8 пользователей, оба API, обычные и потоковые ответы |
| `tests/load/run.sh steady` | 400 пользователей, один запрос каждые 15 секунд, около 26,7 RPS |
| `tests/load/run.sh stages` | Ступени 50, 100, 200 и 400 пользователей, около 3,3–26,7 RPS |
| `tests/load/run.sh burst` | Одновременный всплеск из 400 запросов |
| `tests/load/run.sh streams` | Попытка открыть 400 потоков на 45 секунд |
| `tests/load/run.sh context` | Один пользователь, размеры от 1k до 1m условных единиц |

Для 400 пользователей с интервалами 120, 60 и 30 секунд задайте соответственно
`LOAD_PACE_SECONDS=120`, `60` или `30` перед `steady`.

Размеры являются воспроизводимыми единицами, разделёнными пробелами, а не
результатом токенизатора конкретной модели. Основная матрица:

```bash
LOAD_API=chat LOAD_CONTEXT_MODE=full-history tests/load/run.sh context
LOAD_API=responses LOAD_CONTEXT_MODE=full-history tests/load/run.sh context
LOAD_API=responses LOAD_CONTEXT_MODE=previous-response tests/load/run.sh context
LOAD_API=responses LOAD_CONTEXT_MODE=encrypted-state tests/load/run.sh context
LOAD_CONTEXT_MODE=one-shot tests/load/run.sh context
```

Размеры свыше 128k при числе пользователей больше десяти требуют явного
`LOAD_ALLOW_LARGE_CONCURRENT=true`. Это защищает испытательный компьютер от
случайного одновременного создания сотен крупных тел запросов.

## Настройки запуска

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `LOAD_USERS` | Зависит от профиля | Число одновременных пользователей и временных ключей |
| `LOAD_RUN_TIME` | Зависит от профиля | Продолжительность запуска Locust |
| `LOAD_PACE_SECONDS` | `15` | Интервал между запросами одного пользователя |
| `LOAD_CONTEXT_SIZES` | Зависит от профиля | Возрастающий список размеров контекста |
| `LOAD_API` | `mixed` | `chat`, `responses` или равномерная смесь |
| `LOAD_CONTEXT_MODE` | `mixed` | Полная история, разовая загрузка, `previous_response_id` или `encrypted_content` |
| `LOAD_STREAM` | `mixed` | `true`, `false` или равномерная смесь |
| `LOAD_KEEP_STACK` | `false` | Оставить испытательный Compose-проект после запуска |
| `LOAD_RESULTS_DIR` | Временный каталог | Каталог отчётов на рабочей станции |

Профиль Analyzer задаётся через `LOAD_ANALYZER_WORKERS`,
`LOAD_ANALYZER_CONCURRENCY_LIMIT`, `LOAD_ANALYZER_QUEUE_LIMIT` и
`LOAD_ANALYZER_QUEUE_TIMEOUT_SECONDS`. Проверяйте несколько процессов только с
учётом линейного роста памяти модели, описанного в
[профиле Analyzer](analyzer-load-profile.md).

## Результаты

- `locust.html` и `locust_*.csv` содержат агрегаты Locust;
- `samples-local.csv` содержит только API, профиль, размер, код ответа, полную
  задержку, время до первого фрагмента и результат проверки восстановления;
- `summary-local.json` содержит p50/p95/p99, RPS, условную входную пропускную
  способность и долю ошибок;
- `docker-stats.jsonl` содержит CPU, память, сеть и число процессов контейнеров.
- `analyzer-metrics.prom` и `guardrail-metrics.prom` содержат профильные метрики;
- `mock-provider-capture.json` содержит только счётчики и признаки достижения
  имитации провайдера, что позволяет проверить безопасный отказ до исходящего вызова.

Тексты запросов и ответов, персональные данные и ключи в отчёты не записываются.
Имитация провайдера возвращает маскированную служебную метку; защитный слой
должен восстановить значение именно текущего пользователя. Несовпадение
учитывается как `mapping_isolation_mismatch`.

В текущей реализации поток Responses API с `response.output_text.delta`
возвращает безопасную маскированную метку вместо восстановленного
значения. Такой результат учитывается отдельно как
`masked_only`, а чужое значение по-прежнему считается ошибкой. Для строгой
проверки после реализации потокового восстановления задайте
`LOAD_REQUIRE_STREAM_RESTORATION=true`.

`smoke` завершается ошибкой при любом неуспешном запросе. Остальные профили
возвращают отчёт даже при ожидаемом достижении точки насыщения; задайте
`LOAD_EXIT_CODE_ON_ERROR=1`, если для конкретного запуска нужен строгий порог.

## Полный путь

Запуск через работающий LiteLLM и `codex-lb` разрешён только явно и с малым
числом запросов:

```bash
LOAD_CONTOUR=existing \
LOAD_ALLOW_REAL_PROVIDER=true \
LOAD_TARGET_URL=http://host.docker.internal:4000 \
LOAD_EXTERNAL_KEY_FILE=/absolute/path/load-keys.json \
LOAD_MODEL=gpt-5.6-luna \
LOAD_USERS=2 \
tests/load/run.sh smoke
```

Файл должен иметь формат `{"keys":["sk-...","sk-..."]}`, права `0600` и
содержать только временные пользовательские ключи LiteLLM. Сценарий не создаёт
и не удаляет такие ключи, не снимает статистику чужих контейнеров и не обходит
лимиты провайдера. Проверка точного восстановления по умолчанию отключена,
поскольку ответ реальной модели недетерминирован. Служебные Compose-артефакты
удаляются после запуска.

Один процесс Locust достаточен для первоначальных 400 пользователей. Для
нескольких генераторов подготовленный список ключей делится без пересечений с
помощью `LOAD_KEY_SHARD_INDEX` и `LOAD_KEY_SHARD_COUNT`; каждому процессу нужен
собственный `LOAD_REPORT_NODE`.
