# Одноузловой профиль: локальные измерения

[#116](https://github.com/vovkins/ru-llm-proxy/issues/116), 31 октября 2026.
Доступные локальные проверки S1–S7 завершены. **Профиль для сервера
32 CPU / 64 GB не выбран:** требуется серверная приёмка. Платформы,
модель, правила распознавания и стандартные значения `production` не менялись.
Использован согласованный Nginx варианта B.

## Условия

Docker ARM64, 10 CPU / 7,75 GiB. Основной стенд временно остановлен.
Настоящие Analyzer/Triton, тестовый SSE-провайдер, оба API; это измерение
защитного контура, не задержки реальных GLM/GPT. Размеры — условные единицы
по пробелам, **не токены LLM**. Фактические токены/окна NER сохранены отдельно.
Между волнами — прогрев, освобождение очередей и очистка только тестового
кэша. В знаменателе остаются все попытки; поздний правильный ответ не
считается выполнением требования SSE ≤60 с.

Контроль `production`: 4 Analyzer по 2 CPU, 2 Triton по 2 CPU и 2 LiteLLM;
суммарные квоты выше локальных 10 CPU. P1–P6: одинаковые 4 CPU Analyzer
и 2 CPU Triton, один LiteLLM с квотой 1 CPU. Это равенство CPU, не памяти.
Один процесс/Analyzer; исходно C=2 активных анализа, I=2 исполнения
модели/Triton, B=4 окна в пакете, Q=32 ожидающих, W=30 с ожидания.
История с инструментами проверена также одним ключом в разных диалогах.

Три повтора: 20 тяжёлых запросов 32k и 12 коротких 1k по фиксированному
расписанию. Остальные параметры P3 2/2/4 неизменны.

| Q / W | Успех тяжёлых | Успех коротких | Всего SSE ≤60 с |
| --- | ---: | ---: | ---: |
| 32 / 15 с | 29/60 | 33/36 | 62/96 |
| 32 / 30 с | 51/60 | 36/36 | 87/96 |
| 32 / 45 с | 60/60 | 36/36 | 96/96 |
| 16 / 45 с | 53/60 | 36/36 | 88/96 |
| 64 / 45 с | 55/60 | 36/36 | 91/96 |

Все отказы — `queue_timeout`, не переполнение очереди. Наблюдаемый максимум
три ожидающих поля/Analyzer. Различия Q16/Q32/Q64 не доказывают влияние
вместимости: лимит не достигнут, варианты шли последовательно. Контроль
Q32/W45 в новом контуре дал 94/96 своевременных ответов: тяжёлые 58/60,
короткие 36/36, два `queue_timeout`; все три хеша тел совпали.
45 с помогают, но не гарантируют отсутствие отказов. Влияние порядка и
перезапуска не исключено.

## Увеличение CPU-бюджета

В S3 Triton P3 использовал около 0,92 CPU/контейнер при квоте 1 CPU,
ограничение действовало примерно в 90% cgroup-периодов. Analyzer — около
0,30 CPU/контейнер при квоте 1 CPU. Низкая общая загрузка не исключает
насыщения отдельной квоты.

При 2 CPU/Triton и прежних остальных параметрах Q32/W30: короткие волны
60/60 своевременно; тяжёлые 88/96 правильно, 75/96 своевременно, восемь
`queue_timeout`. Исходный P3 дал 83/96 и 65/96. p95 тяжёлых успехов
56,316 / 62,343 / 68,813 с. Все шесть хешей тел совпали с S3;
серии не чередовались. Сумма квот вычислений 8 CPU, со служебными
компонентами 10,5 CPU при VM 10 CPU; квоты не являются резервированием.

## Устойчивость S6

Кандидат: P3 C2/I2/B4, Triton по 2 CPU, Q32/W45. Это не стандартная
промышленная конфигурация.

| --- | ---: | ---: | ---: |

| Та же смесь, 20 | 20/20 | 20/20 | 23,307 |
| Та же смесь, 32 | 32/32 | 32/32 | 42,037 |
| Та же смесь, 64 | 64/64 | 38/64 | 105,271 |
| 0,25 запроса/с, 120 с | 30/30 | 30/30 | 5,692 |
| 0,5 запроса/с, 120 с | 60/60 | 60/60 | 5,931 |
| 1 запрос/с, 120 с | 118/120 | 118/120 | 8,563 |
| 0,5 запроса/с, 600 с | 300/300 | 300/300 | 8,169 |
| Четыре поля, 20 × 32k, холодный | 8/20 | 0/20 | 137,959 |
| Та же история, заполнение кэша | 8/20 | 0/20 | 146,951 |
| Повтор истории с новым сообщением | 8/20 | 0/20 | 133,765 |

На 1 запросе/с два известных `window_boundary_unresolved`, не перегрузка.
Повышение остановлено по строгому критерию полного успеха, 2 запроса/с не
проверены. Поэтому **0,5 не является установленным пределом CPU**.
Непрерывный прогон: 4,56 млн токенов / 14 477 окон NER, ноль попаданий
кэша, максимальная задержка старта генератора 6,7 мс. Это не результат
повторного использования одинаковых входов.

Эквивалентные аргументы JSON, два повтора четырёх запросов 8k: все 16
восстановлены; p95 с `\u`-экранированием 21,757 / 20,666 с, в UTF-8
1,606 / 1,498 с. Первый повтор потребовал 293 535 против 31 531 токена NER.
Это не полный корпус проверки качества и не основание менять нормализацию.

При отмене половины 16 клиентов: восемь отменены, остальные восемь успешно
завершены; отменённые не считаются успехами. При отключении Analyzer:
14/16 успехов, два 503 `unexpected_failure`; при отключении Triton:
10/16 успехов, шесть 503 `triton_unavailable`. Провайдер вызван только для
успехов. После каждого восстановления — 4/4 успеха. Это подтверждение
защитного отказа и восстановления, не прозрачной отказоустойчивости.

## Границы выводов и следующий шаг

- Сам размер очереди не добавляет вычислительной мощности. Ожидание 45 с
  и больший CPU-бюджет помогают, но крупные холодные истории остаются проблемой.
- Повтор 20 историй не был полностью прогрет: 26 попаданий, 30 промахов,
  восемь событий кэша `error`. Это включает и отказ сохранять результат
  вне контракта, не доказывает сбой Redis. Последующий
  [контроль](production-cache-pool.md) воспроизвёл превышение обоих лимитов
  для экранированных аргументов с ложными AUTH_TOKEN; отдельные исходные
  восемь событий не реконструированы. Полный прогрев не заявляется.
- Пик памяти S6 по выборкам 5,216 GiB; OOM/отказы наблюдателя не наблюдались.
  Неснятые пики не исключены. Сочетание P3 C4/I2/B4 остаётся непроверенным.
- Для увеличения плотности Analyzer/Triton и выбора стандартов нужен один
  сопоставимый Linux-сервер 32 vCPU / 64 GiB / 100 GB SSD, без GPU.
  Автоматической аренды нет; двухузловая схема согласуется отдельно.

## Измеритель и проверки

Исправлены две ошибки частной обвязки: переходный Docker `0B` больше не
передаётся валидатору положительных лимитов; общие/профильные/явные значения
объединяются последовательно без мутации. Гибель наблюдателя или защитные
данные старше 20 с прекращают нагрузку. Проверены штатная остановка,
частичный снимок с контролем по VM и отмена активной работы. Валидатор
конфигурационных лимитов не менялся.

Пройдены 124 адресные регрессии, включая 10 проверок контроллера;
`make test-static test-flow`: 787 + 869 pytest-проверок и 32 проверки Make.
Восемь исходных контейнеров восстановлены healthy, защищённые файлы,
образы, тома и количество ключей/подписок сохранены. Временные ресурсы
удалены. Исходные контрольные маркеры у провайдера не обнаружены.
