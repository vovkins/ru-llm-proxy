# Холодная проверка миграции NER

## Решение

**GO:** миграция Analyzer с DeepPavlov на закреплённую модель
`fef2/ner_rus_bert-secret_detection` готова к проверке в pull request и
последующему объединению с основной веткой.

Холодная сборка, автономный запуск без сети, полный состав Docker Compose и все
связанные с миграцией автоматические проверки завершились успешно. Блокирующих
дефектов не обнаружено.

Решение не означает, что завершены отдельные работы по оптимизации CPU/GPU-образов
[#62](https://github.com/vovkins/ru-llm-proxy/issues/62) и нагрузочному
исследованию [#55](https://github.com/vovkins/ru-llm-proxy/issues/55).

## Условия проверки

Проверка выполнена 4 августа 2026 года на Apple Silicon (`arm64`):

- macOS Darwin 24.6.0;
- Docker Engine 29.6.1;
- Docker Desktop 4.81.0;
- исходный коммит ветки: `26935215590cbcf0789c5ed7a7a73d7d9c017dcd`;
- сборка производственного образа Analyzer: `linux/arm64`;
- локальные изменения задачи #67 присутствовали и ещё не были зафиксированы
  коммитом.

Для полного запуска использовались только искусственные значения секретов и
пустой файл окружения. Настоящие ключи поставщиков моделей и обращения к ним не
требовались.

## Холодная сборка

Перед сборкой контейнеры проекта отсутствовали. Производственный образ собран
штатной командой без использования кэша проекта:

```bash
docker compose build --no-cache --pull
```

| Показатель | Результат |
| --- | ---: |
| Время сборки | 749,52 с (около 12 мин 30 с) |
| Идентификатор образа | `sha256:95c3f7749939e0f9979f5fb20a7d3a5dc07c2af6d3282a4e619fca342473eebe` |
| Размер образа по Docker API | 3 890 653 145 байт |
| Архитектура | `arm64` |
| Время этапа загрузки закреплённой модели | около 119 с |

Сборка получила только шесть файлов ревизии
`52b5b0745aac14f73fcf2ac0f91d9b5001a85ae4` и проверила их размеры и SHA-256.
Наиболее крупные несжатые слои: зависимости Python — около 5,31 ГБ, модель —
714 МБ, русская модель spaCy — 88,9 МБ, системные пакеты сборки — 263 МБ.

`torch 2.13.0` по-прежнему подтягивает CUDA 13 и пакеты NVIDIA, хотя проверка
выполнялась на CPU. Это подтверждает актуальность #62, но не влияет на
корректность текущей миграции.

## Автономный запуск Analyzer

Производственный образ запущен с `--network none`. Сервис стал готов через
3,555 с и сообщил:

- `status=ok`;
- `ner_state=ready`;
- `ner_warmed_up=true`;
- `ner_backend=huggingface_transformers`;
- ожидаемые модель и ревизию.

Короткий текст вернул `PERSON` и `CONTRACT_NUMBER`. Текст длиной 5309 символов
с чувствительным значением в хвосте вернул `PERSON`; исходный текст и смещения
сохранились. В журналах отсутствовали обращения к Hugging Face и попытки
загрузки файлов. Сетевая изоляция контейнера исключала скрытое обращение наружу.

## Ресурсы и задержка

Измерения выполнены последовательно, одним рабочим процессом Analyzer, после
обычного запуска Docker Compose. Это диагностические значения для сравнения, а
не результаты нагрузочного испытания.

| Сценарий | Результат |
| --- | ---: |
| Готовность Analyzer | 3,325 с |
| Короткий текст, 55 символов, 10 запросов | минимум 43,525 мс; p50 45,023 мс; p95 88,305 мс |
| Длинный текст, 5309 символов, 10 запросов | минимум 602,139 мс; p50 606,298 мс; p95 651,470 мс |
| Память до первого длинного запроса | 357,4 МиБ |
| Пиковая память после пяти длинных запросов | 742,8 МиБ |
| Память после обработки | 742,1 МиБ |

Каждый длинный запрос был обработан тремя окнами. Ошибок вывода, неполных
ответов и перехода в частичный режим только с детерминированными правилами не
зафиксировано.

## Полный состав Docker Compose

LiteLLM, Analyzer, PostgreSQL и Redis подняты с чистым томом базы командой
`docker compose up -d --wait`. Все сервисы стали здоровыми через 21,70 с.

Проверено:

- `make health` видит все четыре сервиса готовыми;
- `/guardrails/list` содержит защитные слои проекта;
- `/metrics` LiteLLM доступен без ключа после штатного перенаправления и
  содержит метрики `litellm_*`;
- Analyzer публикует `ru_presidio_analyzer_*`, включая успешный вывод NER и
  число обработанных окон;
- метрики и журналы не содержат искусственных секретов, исходных чувствительных
  строк и смещений;
- состояние Analyzer после запросов остаётся `ready` с ожидаемой ревизией.

При первой инициализации PostgreSQL записал восемь ошибок об отсутствующих
служебных представлениях LiteLLM. Они возникли во время параллельной проверки
схемы до завершения миграций. LiteLLM затем успешно применил все миграции, а
повторная проверка подтвердила наличие каждого из восьми представлений. Это
переходный шум первой инициализации, а не отказ базы или прокси.

Сопутствующее предупреждение LiteLLM относится к пользовательским именам
`glm-5.1` и `glm-5.2`: они отсутствуют во встроенной таблице стоимости, поэтому
стоимость создания и чтения кэша по умолчанию равна нулю. Это не влияет на NER,
маршрутизацию или доступность прокси, но до использования денежных показателей
в промышленном мониторинге для моделей следует явно настроить тарифы.

## Ограничения

- проверка выполнена на одной ARM64-машине с Docker Desktop;
- задержка измерена на последовательных запросах без конкурентной нагрузки;
- время холодной сборки зависит от скорости сети и состояния внешних реестров;
- не проверялись производственные ключи, внешние модели и пропускная способность
  под нагрузкой;
- текущий CPU-образ остаётся тяжёлым из-за CUDA-зависимостей.

Эти ограничения не меняют решение по корректности миграции. Планирование
ресурсов и профилей образа выполняется в #62, а полноценные испытания
производительности — в #55.

## Откат

Миграция намеренно не поддерживает две NER-модели и переключатель во время
работы. При необходимости отката следует развернуть целиком предыдущий
неизменяемый образ или выпуск проекта, вернуть совместимые конфигурацию и код
Analyzer, затем проверить `/api/v1/health` и основные режимы защитного обработчика.

Нельзя смешивать старый Analyzer с новым кодом слияния результатов и новыми
типами сущностей: единицей выпуска и отката является весь согласованный набор
изменений #67.
