# Перегрузка Analyzer: сравнение Nginx

Исследование [#116](https://github.com/vovkins/ru-llm-proxy/issues/116),
31 октября 2026 (МСК), контрольный код `main@c8cc806`.
В ходе A/B рабочий конфиг не изменялся; экспериментальная копия B отличается только
удалением `http_503` из `proxy_next_upstream` для Analyzer.

## Методика

Одна локальная ARM64 VM: 10 CPU / 7,75 GiB. Настоящие Analyzer/Triton,
штатные количества и ресурсы production, пакет 4, тестовый провайдер вместо LLM.
Тестовая проверка здоровья каждые 3 с, автоматический перезапуск отключён.
Основной стенд остановлен на время опытов, затем восстановлен без удаления данных.

Порядок A→B→B→A. В каждой волне 64 новых запроса по 32k условных единиц
за 2 с и 12 коротких запросов по 1k в заданные моменты между 1-й и 60-й секундами.
Оба API, все ответы SSE. Тела и виртуальные ключи одинаковы; перед каждой волной
очищен только испытательный кэш анализа, попаданий в него не было.
Между волнами — освобождение активных мест, пауза 12 с и одинаковый прогрев.
Условные единицы по пробелам не равны токенам внешней LLM.

## Результат

| Прогон | Вариант | Все успехи | Крупные | Короткие | `no live upstreams` |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | A: исходный | 43/76 | 40/64 | 3/12 | 25 |
| 2 | B: без `http_503` | 42/76 | 36/64 | 6/12 | 0 |
| 3 | B: без `http_503` | 42/76 | 37/64 | 5/12 | 0 |
| 4 | A: исходный | 36/76 | 34/64 | 2/12 | 35 |

Итого A: 79/152, B: 84/152. Короткие запросы: 5/24 против 11/24.
**Первый содержательный SSE не позднее 60 с получили по 66 запросов у обоих
вариантов.** Следовательно, доказательства роста ёмкости или выполнения общего
60-секундного требования нет. Двух повторов также недостаточно для утверждения
статистического превосходства по общей доле успехов.

В A из 73 отказов 13 сохранили `queue_timeout` и `Retry-After: 30`,
а 60 превратились в общую недоступность/неготовность с `Retry-After: 1`.
В B все 68 отказов сохранили `queue_timeout` и `Retry-After: 30`;
ложного исключения реплик на ответах перегрузки не было.

Отдельный одноразовый адресат с отказом соединения добавлен в испытательную
группу Analyzer: у каждого варианта 20/20 успешных запросов и по одному
подтверждённому `Connection refused`. Это проверка отказа соединения, не
доказательство обработки всех сетевых сбоев или отказа отдельного сервера.

Провайдер получил ровно 163 успешных запроса основных волн и 40 сетевой проверки;
открытых контрольных данных не увидел. OOM и рестартов не было.
Исходные 8 контейнеров, образы, файлы, тома, число ключей/подписок сохранены;
лабораторные ресурсы удалены.

## Вывод и согласованная правка

B устраняет подтверждённую ошибку классификации перегрузки и сохраняет корректную
задержку повторной попытки. Он **не добавляет вычислительной мощности** и теряет
возможность спасти отдельный запрос автоматическим повтором после HTTP 503.
Для крупных запросов получилось 74/128 у A и 73/128 у B.

Владелец согласовал B как минимальную правку корректности, не как
завершение оптимизации, с явной оговоркой:
Nginx перестанет пассивно исключать Analyzer по любому HTTP 503, включая
настоящую неготовность модели. Ошибки соединения и HTTP 502 остаются отдельными
основаниями переключения; готовность каждого экземпляра надо проверять отдельно.

В `nginx/conf.d/production.conf` удалён только `http_503` из условий
переключения Analyzer; предел двух попыток и маршруты LiteLLM/Triton сохранены.
Регрессия на исходном конфиге получила нежелательный 502 после ожидаемых 503.
Исправленный вариант сохранил по 8 ответов перегрузки и неготовности с телом
и `Retry-After`; смешанная группа вернула как 200, так и 503. После восстановления
прошли 8 запросов, при отказе соединения — 16 с подтверждённым переключением.
Различия перегрузки и неготовности описаны в [мониторинге](../monitoring.md).
Платформенные патчи и новые команды Make не добавлялись.
Стандартные CPU/память/очереди и двухузловое размещение этим опытом не выбираются.

Проверки после правки: `make test-static test-flow` — 769 статических,
863 проверки обработки запросов и 32 проверки Make. Контейнерная матрица
прошла все 10 сочетаний двух составов, топологий, политик и числа Triton
на ограниченном [тестовом профиле](../../tests/e2e/topology-resources.env),
с настоящей NER и тестовым провайдером. Четыре серии отказов охватили оба API
и режима ответа: 32 ожидаемых 503 без вызова провайдера, затем 16 штатных
результатов после восстановления (200 с восстановлением в MASK, 422 в BLOCK).
Этот прогон не является нагрузочной приёмкой сервера 32 CPU / 64 GB.

Данные: [JSON](../../presidio/evaluation/reports/production-nginx-ab.json),
включая результаты отдельных коротких запросов, контрольные суммы тел/конфигов,
счётчики кэша/NER, признаки журналов и проверку восстановления стенда.
JSON фиксирует исходный A/B, до изменения рабочего конфига.
