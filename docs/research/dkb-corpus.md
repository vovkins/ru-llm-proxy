## Политика Base64

Явные подписи `Base64:`/`b64:` и поля с суффиксом `_base64`/`_b64` защищают
всё значение, даже короткое или некорректно закодированное. Доступны стандартный
алфавит, Base64URL и переносы внутри кавычек либо продолжение на строках с отступом.
Известное назначение поля сохраняет класс `PASSWORD`, `LOGIN`, `AUTH_TOKEN` или
`SECRET_KEY`; для остальных используется `BASE64_DATA`.

Если текст состоит из нескольких фрагментов Analyzer, полные диапазоны явно
обозначенных значений определяются по исходному тексту. Граница фрагмента или
его перекрытия не обрезает значение и не меняет его класс. Фильтр сущностей и
`score_threshold` сохраняются; бесконтекстное декодирование остаётся ограниченным.

Без подписи проверяются только отдельные строки длиной от 8 до 16384 символов.
Декодирование строгое: допустимый алфавит, корректное дополнение и каноническое
представление. Если результат является UTF-8-текстом с чувствительными данными,
подтверждёнными существующими детерминированными правилами, исходная строка
заменяется целиком. BERT повторно не запускается, рекурсивного декодирования нет.

Бюджет дополнительной проверки одного анализируемого фрагмента: 64 кандидата и
64 КиБ декодированных данных. После его исчерпания оставшиеся неподписанные
кандидаты не проверяются. Явно обозначенные значения защищаются независимо от
этого бюджета. Успешное декодирование само по себе не является основанием для
маскирования: обычные слова, идентификаторы и произвольные хеши не объявляются секретами.

Неподписанные двоичные данные, произвольный закодированный пароль без контекста,
неподписанные переносы и вложенные кодировки остаются ограничениями. Служебное
поле Responses `encrypted_content` исключено из обработки; текст пользователя
с таким названием исключением не становится.
Без кавычек пробел разделяет значения; многострочное значение требует кавычек
или отдельных строк Base64 с отступом.

## Другие ограничения

SQL-проверка поддерживает INSERT с явными именами столбцов, строковыми литералами
VALUES, несколькими строками и удвоенными кавычками. Один участок ограничен
8192 символами; выражения, функции, INSERT SELECT и динамический SQL не вычисляются.
Хеш пароля относится к `PASSWORD`, а не к новому классу хешей.

В строковых значениях корректного JSON детерминированные правила применяются
к декодированному тексту. Найденные диапазоны переносятся в исходную строку,
поэтому экранированные кавычки, переводы строк и символы Unicode восстанавливаются
без изменений. Проверяется один уровень JSON размером до 65536 символов;
код из строк не выполняется, дополнительного запуска BERT нет. Некорректный
или более длинный JSON не разбирается этим правилом, но обычные распознаватели
продолжают работать с исходным текстом.

Неполный PEM в виде конкатенации строк распознаётся только при однозначных
границах; неоднозначный маркер остаётся для действующей проверки утечки.
Подлинность PEM-ключа и пригодность учётных данных не проверяются.

CVV, срок действия карты и новые классы идентификаторов не входят в работу.
Проверки контрольных сумм карт и банковских счетов не ослаблены.

## Воспроизведение

`make test-recognizers`, `make test-guardrail`, `make test-flow`,
`make test-static`, `make test-ner-proxy` и `make test-egress-security`.
Контейнерный сценарий использует настоящие BERT и spaCy и локального провайдера,
который возвращает полученный текст; это не проверка ответа внешней модели.

Матрица корпуса: оба API, обычный и потоковый ответ, текст и входные аргументы
инструментов. Проверяются 53 размеченных диапазона в исходном тексте и защита
каждого их значимого символа внутри JSON, 112 точных восстановлений
и 144 блокирования без передачи провайдеру. Ещё 32 запроса из файлов `1`, `3`,
`4`, `7` блокируются существующей завершающей проверкой утечек: она запрещает
некоторые конфигурационные присваивания даже после маскирования. Это отдельная
политика, а не отсутствие распознавания. Проверки чистого маскирования и
восстановления всех 18 файлов выполняются отдельно в `make test-flow`.

Дополнительно проверяются три случая на границах фрагментов: длинное значение,
смещённое поле и многострочное типизированное поле. Контейнерный сценарий
проверяет 24 точных восстановления и 24 блокировки без передачи провайдеру;
модульный полный цикл также проверяет длинные выходные аргументы инструментов.
