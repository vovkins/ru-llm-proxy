# Конфигурация

## Единый комплект NER

Обе топологии используют Tiny2 на CPU через Triton/ONNX Runtime. Модель,
токенизатор, алгоритм обработки и маршрут `http://nginx:8000` закреплены кодом
и проверяемыми метаданными сборки, а не переменными окружения.
Поставка, проверка и откат описаны в [руководстве Triton](ner-triton.md).

### Переход со старой конфигурации

Перед запуском удалите из окружения и `ENV_FILE` старые селекторы
`ANALYZER_PROFILE`, `LOAD_ANALYZER_PROFILE`, `NER_MODEL_PROFILE`,
`PRESIDIO_ANALYZER_NER_MODEL_PROFILE`, `PRESIDIO_ANALYZER_NER_BACKEND`,
`PRESIDIO_ANALYZER_DEVICE_PROFILE`, `PRESIDIO_ANALYZER_GPU_PRECISION`,
`PYTORCH_GPU_INDEX_URL`, параметры `TINY2_*`,
`PRESIDIO_ANALYZER_NER_O_LOGIT_BIAS`, `PRESIDIO_ANALYZER_NER_SPAN_POSTPROCESSING`,
`PRESIDIO_ANALYZER_NER_BOUNDARY_RECHECK`, `PRESIDIO_ANALYZER_TRITON_URL`,
`PRESIDIO_ANALYZER_TRITON_MODEL_NAME`, `PRESIDIO_ANALYZER_TRITON_MODEL_VERSION`,
`NER_EVALUATION_MODEL_SHA256`, `NER_EVALUATION_SYSTEM`.
Даже пустые или совпадающие с прежними значениями записи отклоняются с именами
параметров, без раскрытия значений. Автоматического переписывания `.env` нет.
Параметры `TINY2_ANALYZER_*` заменены существующими `PRESIDIO_ANALYZER_*`.
Ресурсы Triton перенесите в файл топологии; противоречащие ему значения в `.env`
или оболочке запрещены. Старые дополнительные Compose-файлы модели и GPU удалены.

Этот документ является единым справочником по переменным окружения проекта. `.env.example` намеренно содержит только минимальные значения для быстрого запуска; остальные настройки задаются через `docker-compose.yml`, `litellm-config.yaml`, административный интерфейс LiteLLM, параметры Makefile или переменные окружения конкретных быстрых проверок.

Правило эксплуатации: секреты и локальные значения первичной настройки лежат в `.env`, публичные имена моделей, пользовательские ключи, бюджеты и доступы пользователей администрируются через административный интерфейс LiteLLM, а расширенные политики запуска меняются только осознанно и документируются в заявке на изменение.

## Запуск и хранилища LiteLLM

### Топологии и ресурсы

Параметры Make не записываются в `.env`, кроме явно выбранного режима защиты.
Порядок запуска и переключения — в [deployment.md](deployment.md).

| Параметр | По умолчанию | Допустимые значения | На что влияет |
| --- | --- | --- | --- |
| `STACK` | Требуется для команд стенда | `litellm-presidio`, `litellm-presidio-codex-lb` | Выбирает состав; второй включает первый и добавляет codex-lb с его базой |
| `TOPOLOGY` | `functional` | `functional`, `production` | Один экземпляр или CPU-пул на одном сервере |
| `ENV_FILE` | `.env` | Путь к файлу | Источник секретов и настроек Compose |
| `TOPOLOGY_ENV` | Пусто | Путь к файлу | Переопределяет только ресурсы и количества из production-пресета; в functional запрещён |
| `STACK_START_TIMEOUT` | `180` | Положительное целое, секунд | Ожидание готовности каждого этапа запуска |

Файл [`deploy/topologies/production.env`](../deploy/topologies/production.env)
содержит только следующие параметры. Пользовательский файл может содержать их
подмножество; значения из него имеют приоритет над пресетом. Ресурсные параметры
не считываются из `.env` и окружения: используйте `TOPOLOGY_ENV`.

| Параметры | Значения по умолчанию | Допустимые значения и влияние |
| --- | --- | --- |
| `LITELLM_REPLICAS`, `ANALYZER_REPLICAS` | `2`, `4` | Положительные целые; число контейнеров соответствующего сервиса |
| `LITELLM_CPUS`, `LITELLM_MEMORY` | `2.0`, `4g` | CPU и память каждого LiteLLM |
| `ANALYZER_CPUS`, `ANALYZER_MEMORY` | `2.0`, `4g` | CPU и память каждого Analyzer |
| `NGINX_CPUS`, `NGINX_MEMORY` | `1.0`, `256m` | CPU и память единственного Nginx |
| `REDIS_CPUS`, `REDIS_MEMORY` | `1.0`, `16g` | CPU и память единственного Redis; учитывает квоту диалогового состояния, но не гарантирует предельную ёмкость всех кэшей |
| `DB_CPUS`, `DB_MEMORY` | `2.0`, `4g` | CPU и память PostgreSQL LiteLLM |
| `CODEX_LB_CPUS`, `CODEX_LB_MEMORY` | `2.0`, `4g` | CPU и память codex-lb, только расширенный состав |
| `CODEX_LB_DB_CPUS`, `CODEX_LB_DB_MEMORY` | `1.0`, `2g` | CPU и память PostgreSQL codex-lb, только расширенный состав |
| `TRITON_REPLICAS` | `2` | `1` или `2`; независимые контейнеры с одной моделью через общий Nginx в production; в functional один |
| `TRITON_CPUS`, `TRITON_MEMORY` | `2.0`, `2g` | CPU и память каждого Triton в production |
| `TRITON_MODEL_INSTANCES` | `2` | Целое от 1 до 32; параллельные исполнения внутри каждого Triton, не число контейнеров; в functional фиксировано два |

Единственный источник ресурсов production —
[`production.env`](../deploy/topologies/production.env) и его `TOPOLOGY_ENV`.
В functional используется один Triton с двумя исполнениями, без новых жёстких
ресурсных ограничений. Стандартный production-профиль рассчитан на исходный
сервер 32 CPU / 64 GB: полный состав имеет лимиты 23 CPU / 54.25 GiB.
Основание и границы: [очереди Э10](research/tiny2-queues.md),
[профили запуска](deployment.md#стандартные-профили). Ёмкость на 400 пользователей
и оптимальность распределения ресурсов на целевом сервере ещё не подтверждены.

CPU — положительное число, допускается дробная часть. Память — положительный
размер в байтах либо с суффиксом `k`, `m`, `g`, `t` (множитель 1024).
Это верхние ограничения Docker, не резервирование ресурсов. Неизвестные
параметры, секреты, дубликаты и неположительные значения отклоняются.

## Пул ChatGPT OAuth-подписок codex-lb

Эти настройки используются только в составе `STACK=litellm-presidio-codex-lb`.
Обычный GLM-профиль от них не зависит. Администратор вручную создаёт пароль и
импортирует подписки через штатный интерфейс, после чего `make setup` включает
аутентификацию API и выпускает служебный ключ через официальный API `codex-lb`.
Полный порядок запуска, первичной настройки, резервного копирования и обновления:
[codex-lb.md](codex-lb.md).

| Переменная | Значение по умолчанию | Допустимые значения | На что влияет |
| --- | --- | --- | --- |
| `CODEX_LB_POSTGRES_PASSWORD` | Генерируется `make setup STACK=litellm-presidio-codex-lb` | Стойкая строка из латинских букв, цифр, `-` и `_` | Пароль отдельного PostgreSQL `codex-lb`. Входит во внутренний `CODEX_LB_DATABASE_URL`; вручную заданный пароль не перезаписывается. |
| `CODEX_LB_API_KEY` | `***` до первичной настройки | Служебный ключ вида `sk-clb-...` | `make setup STACK=litellm-presidio-codex-lb` создаёт или перевыпускает именованный ключ через штатный административный API, проверяет его и атомарно сохраняет в `.env`. Используется только LiteLLM для внутренних вызовов. |
| `CODEX_LB_PORT` | `2455` | TCP-порт хоста | Порт административного интерфейса и API. В расширенном составе его публикует общий Nginx, а не контейнер `codex-lb`. В `.env.example` не добавляется. |
| `CODEX_LB_METRICS_PORT` | `9090` | TCP-порт хоста | Необязательное переопределение опубликованного порта штатных метрик. В `.env.example` не добавляется. |
| `CODEX_LB_DATA_DIR` | `/var/lib/codex-lb` | Путь внутри контейнера | Внутренняя постоянная директория ключа шифрования и служебных данных. Зафиксирована в Compose и хранится в отдельном томе `codex-lb-data`; для восстановления нужна вместе с базой. |
| `CODEX_LB_DATABASE_URL` | Внутренний PostgreSQL URL | URL `postgresql+asyncpg://...` | Соединяет `codex-lb` с отдельным контейнером `codex-lb-db`; формируется Compose из фиксированных имени пользователя/БД и `CODEX_LB_POSTGRES_PASSWORD`. |
| `CODEX_LB_DASHBOARD_AUTH_MODE` | `standard` | `standard` в этом профиле | Включает штатную парольную защиту административного интерфейса. TOTP остаётся необязательной настройкой администратора. |
| `CODEX_LB_METRICS_ENABLED` | `true` | `true` в этом профиле | Включает штатный сервер метрик на внутреннем порту `9090`. |
| `CODEX_LB_TELEMETRY_ENABLED` | `false` | `false` в этом составе | Запрещает внешнюю телеметрию `codex-lb` с первого запуска. |
| `CODEX_LB_HTTP_RESPONSES_SESSION_BRIDGE_ENABLED` | `true` | `true`, `false` | Разрешает `codex-lb` преобразовывать входящие HTTP-запросы Responses API в сеанс с постоянным соединением до ChatGPT. Установите `false`, если корпоративный прокси не пропускает WebSocket. Между LiteLLM и `codex-lb` по-прежнему используется HTTP. |
| `CODEX_LB_UPSTREAM_STREAM_TRANSPORT` | `auto` | `auto`, `http`, `websocket` | Выбирает транспорт от `codex-lb` до ChatGPT. Значение `http` принудительно использует HTTP/SSE и подходит для прокси без WebSocket; `auto` сохраняет штатный выбор платформы. |

## Изолированная корпоративная среда

Эти переменные используются при запуске в корпоративном окружении. Пошаговая
инструкция находится в [air-gapped.md](air-gapped.md).

| Переменная | Значение по умолчанию | Допустимые значения | На что влияет |
| --- | --- | --- | --- |
| `NGINX_HTTP_PORT` | `80` | TCP-порт | Порт общей точки входа LiteLLM. В расширенном составе тот же Nginx публикует `codex-lb` через `CODEX_LB_PORT`. |
| `HTTP_PROXY` | Пусто | URL HTTP-прокси без встроенных секретов | Общий прокси для загрузок при сборке и исходящих HTTP-соединений LiteLLM и `codex-lb`. |
| `HTTPS_PROXY` | Пусто | URL HTTP-прокси с поддержкой CONNECT | Общий прокси для HTTPS-загрузок, вызовов провайдеров, OAuth и ChatGPT. |
| `NO_PROXY` | Имена локальных сервисов | Список узлов, доменов и подсетей через запятую | Исключает Analyzer, Redis, обе базы PostgreSQL, Nginx, LiteLLM и `codex-lb` из проксирования. |
| `PIP_INDEX_URL` | Пусто | URL простого индекса Python-пакетов | Внутреннее зеркало обычных зависимостей Analyzer и тестового образа защитного слоя. При пустом значении используется стандартный индекс pip. |
| `PIP_TRUSTED_HOST` | Пусто | Имя узла | Отключает проверку TLS только для указанного зеркала pip. Не задавать, если зеркало использует доверенный сертификат. |
| `PIP_PROXY` | Пусто | URL отдельного прокси без встроенных секретов | Переопределяет общий прокси только для pip. |
| `PYTORCH_INDEX_URL` | `https://download.pytorch.org/whl/cpu` | URL индекса с `torch==2.13.0+cpu` | Отдельный источник CPU-only PyTorch. В изолированной сети должен указывать на одобренное зеркало точной версии. |
| `NER_MODEL_PROXY` | Пусто | URL HTTP-прокси без встроенных секретов | Переопределяет общий прокси только для загрузки закрепленных файлов NER-модели во время сборки. |

Корпоративная цепочка сертификатов хранится локально в верхнеуровневых файлах
`certs/*.crt`; это не переменные окружения и не часть репозитория. Вся
директория передаётся в контекст сборки, поэтому её содержимое проверяет
оператор. В расширенном составе цепочка добавляется также в системное и Python-
хранилища доверия `codex-lb`.

| `PRESIDIO_ANALYZER_BASE64_POLICY` | `content` | `content`, `logistic` | `content` сохраняет исходную политику; `logistic` дополняет её поиском Base64 по форме с фиксированными весами логистической регрессии. Явные объявления и исходные правила сохраняются. Режим входит в подпись анализа и разделяет кэш. [Алгоритм, проверка и ограничения](base64-logistic.md). |
| `PRESIDIO_ANALYZER_NER_BATCH_SIZE` | `4` | Целое от 1 до 32 | Число окон в одном HTTP-запросе к Triton. Не меняет модель и алгоритм распознавания. |
| `PRESIDIO_ANALYZER_TRITON_TIMEOUT_SECONDS` | `60` | Конечное число больше 0, не более 600 | Сетевой предел одного вызова Triton; общий бюджет документа задаётся отдельно. |

Эффективная параллельность Analyzer: `replicas * PRESIDIO_ANALYZER_WORKERS *
PRESIDIO_ANALYZER_CONCURRENCY_LIMIT`. Перегрузка Analyzer всегда трактуется
защитным слоем как безопасный отказ независимо от
`PII_GUARDRAIL_FAILURE_MODE`.

Прежний [нагрузочный профиль Analyzer](research/analyzer-load-profile.md)
описывает старую реализацию, не нормативы Tiny2/Triton.
Значения 2/32/30 приняты по [локальным измерениям](research/tiny2-queues.md)
всплесков 10–20 запросов, но не гарантируют обслуживание 400 пользователей.
HTTP-пул LiteLLM может добавлять ожидание до очереди Analyzer.
Старые измерения BERT/GPU находятся в
`docs/research/` как исторические данные, не инструкция к новому комплекту.
GPU в этом PR не поддерживается. В образе Analyzer внутренние потоки
OMP/MKL/OpenBLAS ограничены двумя, потоки ONNX Runtime внутри одного исполнения
модели — одним; новых настроек быстрого запуска для этого нет.

## Политики защитного слоя

В обоих конфигурационных файлах LiteLLM включена штатная настройка
`general_settings.cancel_on_disconnect: true`. При обнаруженном отключении
непотокового клиента LiteLLM отменяет ожидание провайдера, регистрирует `499`
и вызывает очистку сопоставления. Дополнительной переменной окружения нет.
Настройка не заменяет обработчик потоковых ответов и не гарантирует остановку
генерации или списания токенов у внешнего провайдера.

Стандартный Compose также использует `litellm_guardrails.server`: наш адаптер
ASGI-отключения регистрируется публичным методом FastAPI до вызова штатной CLI.
Он отменяет нашу предварительную обработку до провайдера, включая оба режима
потока. Новых переменных нет; миграции, аргументы CLI и настройки LiteLLM
не копируются. Прямой запуск обычной команды `litellm` вне Compose не подключает
этот адаптер: для него нужен `python -m litellm_guardrails.server` с теми же
аргументами и доступным модулем проекта.

| Переменная | Значение по умолчанию | Допустимые значения | На что влияет |
| --- | --- | --- | --- |
| `PII_GUARDRAIL_MODE` | `mask` | `MASK`, `BLOCK`, `mask`, `block` | Маскирование с восстановлением либо блокировка до провайдера. Превышение общего бюджета возвращает HTTP 503 `pii_preprocessing_timeout` с
`retryable=false`, без `Retry-After` и без вызова провайдера, в том числе при
`fail_open`. Повтор того же большого нового текста без изменения бюджета
не является способом исправления. Перегрузка очереди отличается: она возвращает
`analyzer_overloaded` с ограниченным `Retry-After`.

HTTP-тайм-ауты HTTPX ограничивают ожидание отдельных фаз, а не автоматически
всего запроса. Общий бюджет guardrail задаётся отдельно в коде, используя ту же
переменную. Nginx ждёт данные LiteLLM и Analyzer до 1500 секунд; маршрут
codex-lb сохраняет 600 секунд, LiteLLM задаёт 60 секунд для провайдера.
Эти пределы не следует складывать или увеличивать одинаково. Выбор бюджета
действует на весь процесс, не автоматически по размеру запроса.
[Профиль большого ввода](deployment.md#большой-новый-ввод) требует согласованного
ожидания клиента; до завершения проверки первое событие SSE не выдаётся.

LiteLLM 1.98.0 начинает следить за отключением клиента после предварительного
хука. Ранний обрыв не отменяет анализ немедленно: его ограничивает общий бюджет.
Возможна попытка уже замаскированного вызова провайдера перед отменой.
Ограничение принято без патча платформы; большой бюджет увеличивает возможное
время ненужных вычислений после обрыва.

## Закреплённая модель NER

Сборка использует только `Katerina-Bir/rubert-tiny2-secret-detection` в ревизии `4137142e79d52b0b69370e0e3dceb2d6ad82591d`. Идентификатор модели, ревизия, разрешённые файлы, размеры и SHA-256 записаны в `presidio/model_manifest.json`. Пользовательских переменных окружения для замены модели или отключения NER нет; ручная поставка весов не требуется.

Большие поля делятся внутри Analyzer автоматически; размер фрагмента и его
перекрытие зафиксированы в коде. Внутри фрагмента используются окна 384/64;
пакет по умолчанию содержит четыре окна и отправляется в Triton.
Неизменившиеся поля повторно используются из HMAC-кэша. Время больших новых
полей зависит от числа окон, конкуренции и ресурсов; бюджет и ограничения
описаны в [развёртывании](deployment.md#большой-новый-ввод), измерения — в
[Э10](research/tiny2-capacity.md). Единицы синтетического генератора не являются
подтверждёнными токенами внешней LLM.

Модель скачивается и проверяется в отдельной стадии сборки, независимой от
Python-зависимостей. PyTorch `2.13.0+cpu` и Transformers нужны только для экспорта
и численного сравнения ONNX в сборочной стадии. Рабочий `analyzer` содержит
правила, облегчённый spaCy, `tokenizers`, NumPy и доверенное описание экспорта,
но не вычислительные веса, PyTorch или Transformers. Цель `ner-triton` содержит
ONNX и штатный Triton с ONNX Runtime на CPU. `analyzer-test` добавляет `pytest`
без весов; рабочий Analyzer не содержит тестовых зависимостей, компиляторов и `curl`.

Во время работы сетевого поиска файлов модели нет. Analyzer загружает локальный
токенизатор из `/opt/models/rubert-tiny2-secret-detection`, сверяет комплект
Triton и выполняет прогрев. Отсутствующие или повреждённые файлы и чужой контракт
не дают готовности; только регулярные правила вместо NER не используются.
Источники, целостность и обновление описаны в
[документе о происхождении модели](research/ner-model-provenance.md).

## Внутренние переменные разработки и контейнеров

## Где что настраивать

| Что меняется | Где менять |
| --- | --- |
| Секреты локального запуска, GLM-ключи, пароль администратора, пароль БД | `.env`, создается через `make setup` |
| Пользователи, клиентские ключи, лимиты, доступы к группам моделей | Административный интерфейс LiteLLM или `scripts/create_virtual_key.sh` для автоматизации |
| Список имён моделей и провайдеров | `litellm-config.yaml` или отдельная конфигурация, управляемая через GitOps |
| Значения политик защитного слоя по умолчанию для контейнера | Значения окружения по умолчанию в `docker-compose.yml` или манифест промышленного оркестратора |
| Публикация Kubernetes, сетевых настроек и настроек безопасности | Отдельные манифесты запуска и сетевые политики |
| Разовые параметры быстрых проверок | Переменные окружения конкретной команды |
