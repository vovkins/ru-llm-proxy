# Codex CLI и Codex App

Codex подключается через OpenAI Responses API. Сценарий относится к Codex CLI и
локальным задачам Codex App; облачные задачи не используют локальную
конфигурацию.

## Граница ключей

```bash
export RU_LLM_PROXY_TOKEN="sk-..."
```

Не кладите `OPENAI_API_KEY` или `LITELLM_MASTER_KEY` в локальную конфигурацию
Codex. В обычном режиме они остаются на сервере. Общие правила:
[README.md](README.md).

## Настройка

Добавьте в `~/.codex/config.toml`:

```toml
model_provider = "ru_llm_proxy"
model = "gpt-6-luna"

[model_providers.ru_llm_proxy]
name = "ru-llm-proxy"
base_url = "http://localhost:4000/v1"
env_key = "RU_LLM_PROXY_TOKEN"
wire_api = "responses"
```

В базовом составе для Responses доступны `glm-5.3-flash` и `glm-5.3`:
замените `model` в примере, дополнительный провайдер не нужен.
Расширенный состав с `codex-lb` публикует
`gpt-6-luna` и другие проверенные имена; порядок запуска приведён в
[`docs/codex-lb.md`](../codex-lb.md).

GLM-профили включают штатное преобразование LiteLLM
`use_chat_completions_api: true`: Z.AI получает Chat Completions, клиент —
Responses. Проверены оба режима, включая восстановление текста и аргументов
инструментов. В потоке наш защитный транспорт подключается к внутреннему
Chat-вызову. GPT через `codex-lb` остаётся на непосредственном Responses-маршруте.

Для Codex App, который не наследует окружение оболочки, сохраните токен в
`~/.codex/.env` и перезапустите приложение:

```env
RU_LLM_PROXY_TOKEN=sk-...
```

## Подписка ChatGPT

В расширенном составе локальный Codex не передаёт собственную подписку.
Администратор отдельно импортирует OAuth-сессии в `codex-lb`, а пользователь
получает только ключ LiteLLM. Не копируйте пользовательский `auth.json` в
клиентскую конфигурацию прокси и не используйте одну импортированную сессию
одновременно в локальном Codex.

## Проверка

```bash
RESPONSES_MODEL=gpt-6-luna \
  make client-auth-smoke STACK=litellm-presidio-codex-lb
```

## Продолжение диалога

Для GPT через `codex-lb` `previous_response_id` работает только с тем же
виртуальным ключом и публичным именем модели, пока доступно состояние прокси
и провайдера. Срок новой связи
по умолчанию — час; успешный следующий ход сохраняет наследуемые замены заново.
Общий бюджет ключа — 1024 ссылки на ответы и 32 МиБ для всех его диалогов и
моделей. Старые версии могут удаляться по бюджету хранения; активный диалог
может вытеснить ссылки другого диалога.

Для GLM через штатный мост передавайте полную видимую историю без
`previous_response_id`. Такое продолжение отклоняется до провайдера с HTTP 400
и кодом `responses_chat_bridge_history_unsupported`: таблица замен Redis не
хранит текст диалога. Запись содержимого запросов ради продолжения не включается.
Неизвестный или недоступный ID может раньше получить общий отказ 409.

Потоковый GLM Responses с `tool_choice={"type":"function","name":"…"}`
получает HTTP 400 `responses_chat_bridge_named_tool_unsupported` до провайдера
из-за ограничения LiteLLM 1.98.0. Используйте Chat Completions, непотоковый
Responses или `tool_choice="required"` с единственным инструментом.
Выбор по имени не подменяется автоматически. [Проверки и ограничения](../research/release-040-followups.md#исправление-и-повторная-проверка-моста-glm).

Выходной защитный слой исправляет нумерацию Responses после восстановления.
Усечение с вложенным `status=incomplete` передаётся как `response.incomplete`,
а не как успешный ответ или искусственный обрыв. Такой ответ не сохраняется
для продолжения по ID; недописанный JSON инструмента остаётся недописанным.
Результаты и принятые ограничения сохранены в отчёте.
[Результаты](../research/release-040-followups.md#исправление-sse-и-проверка-усечённых-аргументов).

При `409 pii_history_unavailable` начните новый запрос с полной видимой
историей, **без** прежнего `previous_response_id`. Не подставляйте чужой ключ
и не повторяйте тот же ID бесконечно. При `503` учитывайте причину,
`retryable` и `Retry-After`: перегрузка допускает отложенный повтор,
`window_boundary_unresolved` — нет. При `413` сократите объём чувствительных данных.
После ошибки SSE незавершённый ответ
не следует считать успешным ходом. Подробности: [архитектура](../architecture.md#продолжение-responses).
