# Base64: каскад с логистической регрессией

Режим `PRESIDIO_ANALYZER_BASE64_POLICY=logistic` дополняет политику `content`:
всё, что защищает `content`, защищается так же, а каскад дополнительно находит
Base64 по форме, независимо от содержимого. По умолчанию остаётся `content`.
Режим включается явно. Локальные проверки не заменяют приёмку на внутреннем трафике.

## Включение

```dotenv
PRESIDIO_ANALYZER_BASE64_POLICY=logistic
```

Compose передаёт настройку в Analyzer; после смены пересоздать Analyzer.
Неизвестное значение — ошибка запуска. Режим и исходники входят в подпись анализа,
поэтому разные режимы не делят записи кэша.

## Путь обработки

1. **Фрагменты (`Base64DataRecognizer.analyze`)** — ровно политика `content` в обоих
   режимах: явно обозначенные значения (`base64: …`, `password_base64`, data URI)
   с полным диапазоном и типом и ограниченная проверка чувствительного содержимого
   неподписанных кандидатов.
2. **Документ (`Base64DataRecognizer.analyze_document`)** — в режиме `logistic` один раз
   на запрос, вне дедупликации Presidio по фрагментам: `base64_logistic.find_spans()`
   для исходного текста и для строк JSON (с проекцией на экранированные смещения).
   Из найденного вычитаются объявленные значения любых типов, в том числе по
   раскодированным ключам JSON (`password_b\u0061se64` = `password_base64`).
   Для JSON-поля тип определяется декодированным ключом, а диапазон включает всё
   исходное значение, в том числе экранированные пробелы по краям. Например,
   `{"\u0070assword_base64":"\n...\n"}` остаётся `PASSWORD`, а не `BASE64_DATA`.
3. **Слияние** сохраняет все исходные находки и типы; находки каскада добавляют только
   непокрытые части одним проходом по отсортированным диапазонам. Объявленные
   контейнеры защищены и тогда, когда их тип исключён фильтром `entities`.
4. Gateway маскирует и восстанавливает значения штатно.

## Как каскад решает, что строка — Base64

Кандидат — непрерывная строка из алфавита Base64/Base64URL. Проверки по порядку:

1. data URI, JWT, PEM — всегда Base64.
2. Отсев по форме: длина, которой у Base64 не бывает (остаток 1 при делении на 4
   без `=`; строки от 33 символов проверяются и без последнего символа), неверное
   число завершающих `=`, смешение алфавитов, шестнадцатеричные строки, UUID,
   только цифры, пути, имена через `-`/`_`.
3. Декодирование префикса ≤ 256 символов (O(1) на кандидата): читаемый текст или
   много нулевых байтов — Base64. Короткие строки 8–15 символов принимаются только так
   (для 8–11 символов ещё и с `=`).
4. Остальное — логистическая регрессия по 8 признакам строки: доли гласных, цифр и
   заглавных, средняя длина кусков после разбиения camelCase, самое длинное «слово»,
   доля символов в словах от 4 букв и в «произносимых» кусках, длина. Порог зависит
   от длины и паддинга. Пример: `getUserProfileById` −6,4, случайная строка той же
   длины +6,5, порог 1,5.
5. Рядом с пометкой `base64`/`b64` берутся короткие значения в кавычках, если они
   декодируются в текст.

Строки MIME/PEM объединяются, только если строка имеет ширину 64 или 76 символов и
дальше идёт один перевод строки (LF, CRLF или экранированный в JSON). Короткая
последняя строка добавляется, только если это целая строка, длина блока вместе с ней
кратна 4 (полные строки кратны 4, блок дополнен `=`) и есть признак кодировки: `=`,
`+`/`/` (не путь) или случайный вид по оценке каскада — только от 8 символов, потому что
на коротких строках оценка ненадёжна. Hex не присоединяется. На 1197 идентификаторах
с цифрами из кода transformers/pydantic/fastapi (`Version2`, `Qwen2Model`, `H264` …)
так присоединяется 1,0% (12, из них один настоящий Base64) против 100% по прежнему правилу «есть цифра», а последние строки
настоящих блоков — 98,2% против 99,8%. Компромисс: хвост из 4 букв и цифр без `=`
(до 3 байт) не присоединяется — по форме он неотличим от `H264` или `IPv6`.

## Происхождение модели

- Исходный модуль — `b64_masker.py` из архива `b64_bench (1).zip`
  (SHA256 архива `08554f372dee79e51baaf8557457633b55aa2adaeb3916bfab5fb5564c9ad810`,
  SHA256 модуля `59e2b297abfa23c11afe1076201271e0d0adbebf6625bd34e65c59bf5fa4be38`).
  Код и коэффициенты сгенерированы ассистентом Claude (Anthropic) по запросу автора PR;
  архив не опубликован. Сторонний код в модуль не включён.
- Коэффициенты `_W`, `_B` и пороги перенесены без изменений. Обучение из архива:
  `LogisticRegression(C=3)`; негативы — строки «серой зоны» (16–63 символа, прошли
  синтаксис, не декодируются в текст) из stdlib Python и публичных репозиториев
  vLLM, openai-agents-python, SWE-agent, BFCL, express, cobra, spring-petclinic,
  kubernetes/examples, terraform-aws-vpc, loghub, natasha; позитивы — синтетический
  Base64 от случайных байтов и текста; разбиение 50/50 по хэшу токена; ложное
  срабатывание весит в 5 раз больше пропуска.
- **Ограничение:** корпуса скачивались с HEAD без фиксации коммитов, поэтому обучение
  нельзя повторить побайтно, а метрики обучения из архива здесь не используются.
  Заявления о качестве ниже опираются только на воспроизводимую оценку.

## Воспроизводимая оценка

`presidio/evaluation/base64_policies.py` запускает каждую политику в отдельном процессе
через тот же путь Base64, что и Analyzer (проход по документу, внешние фрагменты,
подавление, слияние), без spaCy и NER. Вставки генерируются с фиксированным seed;
значение засчитывается, только если покрыт весь его диапазон.

```bash
python -m pip install --no-deps --target /tmp/b64-corpus \
  transformers==4.57.6 pydantic==2.13.5 fastapi==0.115.14 starlette==0.46.2 httpx==0.28.1 spacy==3.8.16
mkdir -p /tmp/b64-docs && git archive da4f50a docs | tar -x -C /tmp/b64-docs
python presidio/evaluation/base64_policies.py \
  --corpus /tmp/b64-corpus/{transformers,pydantic,fastapi,starlette,httpx,spacy} /tmp/b64-docs/docs \
  --output presidio/evaluation/reports/base64-policies.json
```

Результат в [reports/base64-policies.json](../presidio/evaluation/reports/base64-policies.json):
618 файлов, 12 011 420 символов, 4000 вставок; Python 3.12, Mac arm64.

| Вариант | Маски BASE64_DATA на чистом корпусе | Найдено, ≥16 символов | 12–15 | <12 |
| --- | ---: | ---: | ---: | ---: |
| `content` (main) | 7 | 411/2573 (16%) | 0/119 | 349/1308 (27%) |
| `logistic` | 8 | 2538/2573 (98,6%) | 0/119 | 665/1308 (51%) |
| регулярка `[A-Za-z0-9+/_-]{16,}` | 77 374 | 2092/2573 (81%) | 0/119 | 0/1308 |
| то же + заглавная, строчная и цифра | 3 343 | 1634/2573 (64%) | 0/119 | 0/1308 |

Как читать: доля — полное покрытие вставленных кодировок указанной длины, а не качество
обнаружения персональных данных; политики различаются по смыслу: `content` ищет известное
чувствительное содержимое, каскад скрывает кодировку независимо от содержимого. Всех
вставок `content` закрывает 760/4000 (19%), `logistic` — 3203/4000 (80%). В группу
12–15 символов генератор поместил только Base64 от 9 случайных байтов; Base64 текста
такой длины каскад находит. Маски на чистом корпусе не равны ложным срабатываниям и
разобраны отдельно: все 7 у `content` — значения после объявленного ключа (`*_b64:`,
`Base64:`), у `logistic` те же 7 и токен `hf_…`; все 8 — не канонический Base64.
Значения, которые находит `content`, `logistic` находит всегда: для фрагментов это
один и тот же код (проверяется тестами).

| Содержимое вставки | `content` | `logistic` |
| --- | ---: | ---: |
| случайные байты 3–192 | 0% | 68% |
| бинарь с нулевыми байтами | 0% | 98% |
| MIME-блок 64/76 | 0% | 99,8% |
| русский текст | 47% | 96% |
| английский текст и учётные данные | 34% | 79% |
| короткие email (`a@b.ru` и т.п.) | 67% | 74% |
| цифры | 0% | 58% |

По окружению: `key=value` и URL — 0% у `content` (кандидат не начинается после `=`),
68% и 71% у `logistic`; текст, кавычки, JSON и русская фраза — 30–34% против 80–83%.
Пропуски `logistic` — почти полностью строки короче 16 символов.

| Время, медиана, с | `content` | `logistic` |
| --- | ---: | ---: |
| чистый текст 50 000 символов | 0,003 | 0,008 |
| чистый текст 400 000 символов | 0,036 | 0,064 |
| 1 000 значений Base64 (43k символов) | 0,016, закрыто 64 | 0,021, закрыто 1 000 |
| 16 000 значений Base64 (688k символов) | 0,200, закрыто 379 | 0,316, закрыто 16 000 |

`content` быстрее, потому что проверяет не больше 64 кандидатов на фрагмент;
`logistic` закрывает все значения, время растёт линейно (`find_spans` на 16 000
значений — 0,04 с). Цифры для сравнения вариантов, не SLA.

## Ограничения

- Короткий Base64 без паддинга и пометки не обнаруживается по форме: `dGVzdA` (test)
  неотличим от идентификатора. Случайный бинарь 12–15 символов — 0% в обоих режимах;
  короткие чувствительные значения без `=` после `key=` или в URL — тоже.
- Декодированная проекция JSON ограничена корректным документом до 65 536 символов.
  Более крупные документы анализируются как исходный текст; экранированные имена полей
  за этой границей не имеют той же гарантии классификации.
- Одинаковые значения получают разные плейсхолдеры — текущее поведение Gateway.
- Responses API с сохранённой историей (`litellm_guardrails/responses_state.py`):
  один набор соответствий — до 1 МиБ и 10 000 пар; отдельно квота владельца —
  32 МиБ и 1 024 ссылки, она не отменяет первую. Base64-вложение примерно от 780 КБ
  исходных данных маскируется целиком, и запрос отклоняется с 413 `pii_history_too_large`
  (fail-closed, незамаскированное значение не отправляется); в `content` такое значение
  без чувствительного содержимого не маскировалось. Лимиты не меняются.
- Кэш анализа: до 2 000 сущностей и 64 КиБ на запись. Поле, которое не помещается,
  не кэшируется и анализируется на каждом запросе (метрика `write_error`); маскирование
  при этом выполняется полностью.
- На входах с тысячами объявленных значений (`b64 = '…'`) время растёт квадратично одинаково
  в `content` и `logistic`: правило объявлений и дедупликация Presidio, вне этого изменения.
- На синтетических контролях с Base64 длиной в сотни символов без пробелов внутри JSON
  наблюдался 503 `window_boundary_unresolved` от NER — одинаково в обоих режимах; к
  каскаду не относится, поведение NER не меняется.
- Полноценная многопользовательская нагрузка и корпоративный сетевой маршрут
  требуют отдельной проверки; сравнительные измерения выше их не заменяют.

## Проверка

- `test_base64_logistic.py` — режим, кэш, объявленные значения и типы, совпадение
  находок `content` на фрагментах, корпус ДКБ, слияние.
- `test_base64_logistic_review.py` — случаи из ревью PR #104: короткие значения
  напрямую, через API и в JSON; 5 000 значений и внешние фрагменты; MIME 64/76,
  CRLF, JSON-экранирование, текст и идентификаторы с цифрами после блока, настоящие
  короткие хвосты; фильтр типов, экранированные ключи JSON во вложенных объектах и
  массивах, идемпотентность слияния.
- `test_base64_logistic_full_path.py` — полный API со всеми правилами и проходом по
  документу: корпус ДКБ, он же внутри JSON и синтетические объявленные значения; `content`
  сохраняется в `logistic`, исключённые объявленные типы не становятся BASE64_DATA,
  включая экранированные ключи и пробелы по краям значений.
- `test_base64_policies_evaluation.py` — категории оценщика: паддинг, каноничность,
  алфавиты.
- `test_base64_logistic_cases.py` — синтетические аналоги кейсов безопасников,
  обычный код и текст без масок.
- `test_base64_logistic_api.py` — HTTP, длинный текст через внешние фрагменты,
  JSON-экранирование; вычисления NER подменены.
- `make test-ner-proxy` — собранные Analyzer/Triton, настоящая Tiny2, Redis и тестовый провайдер:
  оба API, текст и аргументы инструментов, `stream=False/True`, восстановление,
  блокировка без обращения к провайдеру и границы внешних фрагментов.
  Для новой политики: `PRESIDIO_ANALYZER_BASE64_POLICY=logistic make test-ner-proxy`.
  В CI последовательно проверяются обе политики.
- `make test-pre-egress-proxy` проверяет отказ `413` до обращения к провайдеру
  при превышении лимита истории, в том числе для потокового запроса. Анализатор
  здесь подменён, а LiteLLM и Redis настоящие: это проверка лимита, не скорости NER.
