# Пул ChatGPT OAuth-подписок

Экспериментальный профиль подключает штатный `codex-lb` к неизменённому LiteLLM.
Клиенты по-прежнему обращаются только к LiteLLM и используют его пользовательские
ключи. `codex-lb` выбирает OAuth-подписку ChatGPT, учитывает её состояние и
передаёт запрос OpenAI после защитной обработки.

Профиль не меняет обычный запуск с GLM и включается только через
`docker-compose.codex-lb.yml`. Его слияние в `main` отложено до ручного сравнения
с экспериментом из задачи #72. Сейчас закреплён официальный образ
`v1.24.0-beta.3`; локальных патчей LiteLLM или `codex-lb` нет.

## Состав и поток запроса

| Компонент | Ответственность |
| --- | --- |
| LiteLLM | Клиентские API и ключи, публичные имена моделей, защитные обработчики и выбор направления |
| PII Guardrail и Presidio Analyzer | Проверка, блокировка или маскирование до выхода из прокси; восстановление ответа |
| `codex-lb` | OAuth-подписки ChatGPT, каталог моделей, квоты, выбор учётной записи и привязка по диалогу/кэшу |
| PostgreSQL LiteLLM | Пользователи, ключи, бюджеты и состояние LiteLLM |
| PostgreSQL `codex-lb` | Учётные записи, настройки, маршрутизация и журналы `codex-lb` |
| Redis | Временные `pii_mapping:*` и привязки LiteLLM для моделей, обслуживаемых напрямую |

```text
Клиент -> LiteLLM -> PII Guardrail -> Presidio Analyzer
       -> PII Guardrail -> codex-lb -> OAuth-подписка -> OpenAI
       -> PII Guardrail -> клиент

Клиент -> LiteLLM -> тот же защитный путь -> Z.AI/другой провайдер напрямую
```

LiteLLM передаёт `codex-lb` уже подготовленный запрос. Непрозрачное состояние
`reasoning/compaction.encrypted_content` не анализируется и не изменяется.

## Запуск

Сначала подготовьте обычный `.env`:

```bash
make setup
```

Проверьте, что заполнены два ключа Z.AI, а `CODEX_LB_POSTGRES_PASSWORD`
сгенерирован. Первичное значение `CODEX_LB_API_KEY=***` будет заменено после
настройки `codex-lb`.

```bash
docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose.codex-lb.yml \
  pull

docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose.codex-lb.yml \
  up -d --build
```

Состав включает шесть рабочих контейнеров: LiteLLM, Analyzer, Redis, PostgreSQL
LiteLLM, `codex-lb` и отдельный PostgreSQL `codex-lb`.

## Первичная настройка

1. Откройте `http://<адрес-сервера>:2455` из внутренней сети.
2. Задайте сложный пароль администратора. При удалённом первом входе используйте
   одноразовый код начальной настройки из журнала `codex-lb`; не помещайте его в
   заявки или общий журнал команд.
3. Добавьте OAuth-подписки штатными средствами интерфейса. Для импорта используйте
   отдельные сессии `auth.json`; после импорта не запускайте ту же сессию
   одновременно в локальном Codex.
4. Создайте в разделе API Keys отдельный служебный ключ для LiteLLM. Полное
   значение показывается только при создании.
5. В Settings включите **API key authentication**. Без этого контейнерный запрос
   LiteLLM считается не локальным и может получать `401`, даже если ключ уже
   создан.
6. Запишите служебный ключ в локальный `.env` как `CODEX_LB_API_KEY`. Клиентам
   этот ключ не выдаётся.
7. Пересоздайте только LiteLLM, чтобы он перечитал ключ:

```bash
docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose.codex-lb.yml \
  up -d --force-recreate --no-deps litellm
```

Порт обратного вызова `1455` на хост не публикуется. Используйте доступные в
интерфейсе способы импорта, код устройства или ручную передачу адреса обратного
вызова; собственный импортёр проект не добавляет.

## Проверка

```bash
docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose.codex-lb.yml \
  ps

curl -fsS http://localhost:2455/health/ready
make health
```

Через пользовательский ключ LiteLLM проверьте каталог и лёгкую модель:

```bash
curl -fsS http://localhost:4000/v1/models \
  -H "Authorization: Bearer $RU_LLM_PROXY_TOKEN"

CHAT_MODEL=gpt-5.6-luna RESPONSES_MODEL=gpt-5.6-luna \
  PROTOCOL_SMOKE_ENABLED=true make guardrails-smoke
```

Проверенная конфигурация публикует `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.5`,
`gpt-5.6-luna`, `gpt-5.6-sol` и `gpt-5.6-terra`. Доступность зависит от
подписки и выпуска `codex-lb`; перед изменением списка сверяйтесь с живым
`GET /v1/models`.

## Администрирование

- Добавляйте, отключайте и повторно авторизуйте подписки через интерфейс
  `codex-lb`; перезапуск LiteLLM для этого не требуется.
- Управляйте пользовательскими ключами, бюджетами и доступными публичными
  моделями в LiteLLM. Не выдавайте пользователям служебный ключ `codex-lb`.
- Для ротации служебного ключа сначала создайте новый ключ, обновите `.env` и
  пересоздайте LiteLLM, проверьте запрос, затем отзовите старый ключ.
- TOTP не обязателен в этом профиле, но может быть включён администратором
  штатными средствами `codex-lb`.

## Резервное копирование

Для полного восстановления нужны два независимых объекта:

1. Дамп базы `codex_lb` из контейнера `codex-lb-db`.
2. Защищённая копия тома `codex-lb-data`, особенно файла шифрования из
   `/var/lib/codex-lb`. Без прежнего ключа зашифрованные OAuth-данные в базе
   использовать нельзя.

Пример дампа в каталог, расположенный вне репозитория:

```bash
docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose.codex-lb.yml \
  exec -T codex-lb-db \
  pg_dump -U codex_lb -d codex_lb -Fc \
  > /secure-backups/codex-lb.dump
```

Том и дамп храните зашифрованными вместе с версией образа и digest. Проверяйте
восстановление на отдельном стенде. Перед восстановлением остановите `codex-lb`;
не заменяйте ключ шифрования поверх действующей базы.

## Обновление

Образы закреплены по версии и digest в `docker-compose.codex-lb.yml`. Обновляйте
`codex-lb` отдельно от LiteLLM:

1. Изучите изменения выпуска и миграций базы.
2. Сохраните PostgreSQL `codex-lb` и том `codex-lb-data`.
3. Обновите тег и digest образа в Compose после стендовой проверки.
4. Загрузите образ и пересоздайте `codex-lb`.
5. Проверьте состояние, каталог моделей, обе подписки, Chat Completions,
   Responses API, потоковые ответы, защитные обработчики, журналы и метрики.

Возврат только старого образа может быть недостаточен после миграции схемы;
держите согласованную резервную копию базы и тома. Порядок обновления LiteLLM
описан в [monitoring.md](monitoring.md#обновление-litellm).

## Сеть и доступ

Compose публикует HTTP без TLS:

| Порт | Назначение |
| --- | --- |
| `4000` | Клиентский и административный API LiteLLM |
| `5001` | Analyzer API и метрики |
| `2455` | Интерфейс и API `codex-lb` |
| `9090` | Метрики `codex-lb` |

Порты предназначены только для доверенной внутренней сети. Доступ к
административным маршрутам и метрикам ограничивайте межсетевым экраном или
сетями контейнерной платформы. PostgreSQL, Redis и callback-порт `1455` наружу
не публикуются. HTTPS и обратный прокси в этот эксперимент не входят.

Во время работы `codex-lb` обращается к `chatgpt.com:443` и
`auth.openai.com:443`. Телеметрия отключена через
`CODEX_LB_TELEMETRY_ENABLED=false`. Дополнительные проверки новых выпусков могут
обращаться к GitHub или реестру npm; разрешайте их только при необходимости.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| `codex-lb` не готов | `GET /health/ready`, состояние `codex-lb-db`, журнал запуска и доступность ключа шифрования |
| `/v1/models` возвращает `401` | Создан ли служебный ключ, включена ли **API key authentication**, совпадает ли `CODEX_LB_API_KEY`, пересоздан ли LiteLLM |
| Нет доступных моделей | Состояние OAuth-подписок и живой каталог `codex-lb` |
| Запросы OpenAI не проходят | Внутренний адрес `http://codex-lb:2455/v1`, служебный ключ, квоты и журналы выбранной подписки |
| GLM не работает | Ключи Z.AI и прямой маршрут LiteLLM; `codex-lb` в нём не участвует |
| Нет восстановления значений | Журналы защитного слоя и отсутствие преждевременного удаления `pii_mapping:*` |
| Нет метрик `codex-lb` | `CODEX_LB_METRICS_ENABLED=true`, порт `9090` и сетевой доступ Prometheus |

Журналы и отчёты не должны содержать OAuth-токены, `auth.json`, служебный ключ,
полные заголовки `Authorization` или исходные чувствительные данные.
