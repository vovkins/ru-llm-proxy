# Запуск в изолированной корпоративной среде

Инструкция относится к целевому комплекту Tiny2/Triton. Для обновления
прежней установки используйте порядок [перехода целым выпуском](deployment.md#применение-к-существующей-установке).
На изолированном стенде внешние соединения
проходят через корпоративный прокси, TLS переподписывается корпоративным
удостоверяющим центром, а пакеты Python берутся из внутреннего зеркала.

Проверка TLS остается включенной. Проект добавляет согласованный корпоративный
сертификат в хранилища доверия, а не использует `SSL_VERIFY=False`.

Инструкция ниже использует `TOPOLOGY=functional`. Для CPU-пула выбирайте
`TOPOLOGY=production` во всех командах стенда. Состав, ресурсы и BLOCK/MASK
описаны в [руководстве по развёртыванию](deployment.md); сертификаты и настройка
исходящего прокси одинаковы для обеих топологий.

## Что подготовить

- адрес корпоративного HTTP-прокси;
- цепочку корневых и промежуточных сертификатов прокси в файлах `certs/*.crt`;
- адрес внутреннего индекса Python-пакетов;
- отдельный индекс с `torch==2.13.0+cpu` для сборочного экспорта;
- доступ через прокси к закреплённой Tiny2 на Hugging Face и образам Docker,
  включая официальный Triton в NGC (`nvcr.io`);
- для состава с `codex-lb` — доступ к конечным точкам OAuth и ChatGPT;
- два ключа Z.AI и секреты локального запуска.

Прокси для загрузки базовых образов настраивается в Docker daemon. Переменные
контейнеров и параметры сборки не влияют на `docker pull`.

## Настройка

1. Создайте `.env` и заполните ключи провайдера и сетевые настройки:

   ```bash
   cp .env.example .env
   ```

2. Поместите корпоративную цепочку в один или несколько верхнеуровневых файлов
   `certs/*.crt`. Требования к содержимому директории описаны в
   [certs/README.md](../certs/README.md).

3. Задайте сетевые параметры в `.env`:

   ```dotenv
   HTTP_PROXY=http://proxy.corp.example:3128
   HTTPS_PROXY=http://proxy.corp.example:3128
   NO_PROXY=localhost,127.0.0.1,db,redis,presidio-analyzer,ner-triton,litellm,nginx,codex-lb,codex-lb-db

   # Используйте эти значения, если корпоративный прокси не поддерживает WebSocket.
   CODEX_LB_HTTP_RESPONSES_SESSION_BRIDGE_ENABLED=false
   CODEX_LB_UPSTREAM_STREAM_TRANSPORT=http

   PIP_INDEX_URL=https://pypi.corp.example/simple
   PIP_TRUSTED_HOST=
   PIP_PROXY=
   PYTORCH_INDEX_URL=https://pypi.corp.example/pytorch-cpu/simple
   NER_MODEL_PROXY=http://model-proxy.corp.example:3128
   ```

   Добавьте в `NO_PROXY` внутренние домены и подсети стенда. Не удаляйте имена
   сервисов проекта: иначе обращения к Analyzer, Redis и PostgreSQL уйдут во
   внешний прокси.

   LiteLLM всегда обращается к `codex-lb` по HTTP. Две настройки выше управляют
   только участком `codex-lb` -> ChatGPT: они отключают преобразование HTTP-
   запросов в WebSocket-сеанс и сохраняют потоковые ответы через HTTP/SSE.
   Оставьте штатные `true` и `auto`, если WebSocket разрешён.

   `PIP_TRUSTED_HOST` отключает проверку TLS для указанного узла. Оставляйте его
   пустым, если внутреннее зеркало использует сертификат из согласованной
   цепочки. Не помещайте логины и пароли в URL параметров сборки.

## Сборка и запуск

```bash
make build
make setup STACK=litellm-presidio-codex-lb
make up STACK=litellm-presidio-codex-lb
make health STACK=litellm-presidio-codex-lb
```

Для запуска без `codex-lb` используйте `STACK=litellm-presidio`. Расширенный
состав уже включает базовый: выполнять
обе команды setup подряд не нужно. `make build` общий и готовит образы обоих
составов; `setup` отвечает за секреты и первичную настройку, а `up` не выполняет
сборку.

Во время сборки:

- `apt`, `pip` и spaCy используют общий прокси;
- обычные зависимости берутся из `PIP_INDEX_URL`;
- PyTorch для экспорта берётся из `PYTORCH_INDEX_URL`; ONNX собирается и проверяется
  до создания рабочего Analyzer и образа Triton;
- разрешенные файлы модели скачиваются через `NER_MODEL_PROXY` либо общий
  `HTTPS_PROXY` и проверяются по размеру и SHA-256;
- корпоративные сертификаты проверяются и добавляются в образы LiteLLM,
  Analyzer, тестов и, в расширенном составе, `codex-lb`; повреждённая
  PEM-цепочка останавливает сборку.

Во время работы Analyzer использует локальный токенизатор и обращается к
Tiny2/Triton по HTTP через `nginx:8000`. Triton исполняет ONNX на CPU без загрузок
из интернета. Корпоративный CA в Triton не добавляется: исходящие TLS-вызовы для
обработки ему не нужны. Внешний доступ требуется LiteLLM для прямых провайдеров,
а `codex-lb` — для OAuth и ChatGPT.

## Проверка

Один контейнер Nginx публикует LiteLLM на `NGINX_HTTP_PORT`, по умолчанию `80`:

```bash
curl -fsS http://localhost/health/liveliness

curl -fsS http://localhost/v1/chat/completions \
  -H "Authorization: Bearer $RU_LLM_PROXY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"glm-5.3-flash","messages":[{"role":"user","content":"ping"}],"max_tokens":8}'
```

После запуска выполните проверки защитного слоя:

```bash
make guardrails-smoke STACK=litellm-presidio-codex-lb
make routing-smoke STACK=litellm-presidio-codex-lb
```

Для запроса выше нужен пользовательский ключ LiteLLM, не административный
`LITELLM_MASTER_KEY`. Обновление существующей установки и возврат без удаления
постоянных данных описаны в [deployment.md](deployment.md#применение-к-существующей-установке).

В расширенном составе тот же Nginx публикует административный интерфейс
`codex-lb` на `CODEX_LB_PORT`, по умолчанию `2455`. Контейнер `codex-lb` этот
порт напрямую не публикует.

Порт LiteLLM `4000` и порт Analyzer `5001` оставлены опубликованными
для диагностики. На стенде ограничьте их межсетевым экраном и предоставляйте
клиентам только nginx.

В production эти порты публикует сам Nginx, а не отдельные реплики.

## Диагностика

| Ошибка | Что проверить |
| --- | --- |
| LiteLLM не доверяет сертификату провайдера | Наличие корректных `certs/*.crt`, затем полная пересборка образа LiteLLM |
| `codex-lb` не доверяет OpenAI или OAuth | Наличие корректных `certs/*.crt`, прокси-переменные и полная пересборка образа `codex-lb` |
| Сборка останавливается на проверке сертификатов | Формат PEM и полная цепочка в `certs/*.crt`; удалите поврежденные и посторонние файлы |
| `pip` не находит пакет | `PIP_INDEX_URL`, доступ через прокси и наличие пакета во внутреннем зеркале |
| Не найден `torch==2.13.0+cpu` | Отдельный `PYTORCH_INDEX_URL` и точная версия CPU-пакета |
| Не скачивается NER-модель | `NER_MODEL_PROXY` или общий `HTTPS_PROXY`, доступ к `huggingface.co` |
| Внутренние запросы уходят в прокси | Имена сервисов и внутренние домены в `NO_PROXY` |
| Не загружается базовый образ | Настройки прокси Docker daemon вне проекта |
| Не загружается Triton | Доступ Docker daemon к `nvcr.io` и наличие закреплённого образа во внутреннем реестре |
| Analyzer не видит модель | Внутренний маршрут `nginx:8000`, готовность каждого Triton и совпадение комплекта; `make health` |
