# Продолжение запроса при совпадении с прежним псевдонимом

Локальный opt-in вариант поверх восстановления Anthropic Messages. Строгий
режим по умолчанию сохранён. Новый режим пока не принят для production.

## Настройка

Параметр конструктора `RuPIIGuardrail`:

```yaml
litellm_params:
  guardrail: litellm_guardrails.pii_guardrail.RuPIIGuardrail
  mode: pre_call
  dictionary_collision_resolution: unique_aliases
```

Это фрагмент существующей настройки guardrail: остальные параметры словаря,
защиты и post-call восстановления нужно сохранить. Никакая конфигурация сервера
этим изменением автоматически не обновляется. Значение по умолчанию — `reject`.
Неизвестное значение отвергается при создании guardrail.

## Поведение

Перед изменением текста планируются подмены для всего запроса. Если обычный
псевдоним уже есть в исходных данных, оригинал получает новое свободное
обозначение. Оно совместимо с ASCII-идентификаторами и путями пакетов и не
встречается в исходных строках или реальных декодированных JSON-скалярах.
Повтор одного написания получает одну маску; разные регистры восстанавливаются
точно. JSON/base64/код не исполняются; Base64 не декодируется.

Существующий псевдоним не объявляется автоматически другим оригиналом: он
остаётся исходными данными и проходит обычную NER-проверку. Для доверенного
серверного mapping продолжают действовать его сохранённые соответствия.
План неизменяем и передаётся локально через ContextVar; параллельные запросы
не меняют общую policy. Все будущие маски словаря резервируются до выдачи
native-плейсхолдеров.

Обычный NER, native findings, pre-egress/final leak checks, JSON provenance,
отказы Analyzer и хранилища, очистка mapping остаются включёнными. Планирование
ограничено суммарным объёмом ссылочных строк, количеством оригиналов и попыток
выдачи масок. При невозможности построить план запрос безопасно отклоняется.
Для запроса без словарных совпадений новые лимиты планирования не добавляются.

При `reject` прежние проверки неоднозначности и поведение остаются. При
`unique_aliases` устраняется словарный конфликт, но старые ошибочные импорты
не переписываются по догадке. Агенту ещё нужно исправить их по контексту.

## Проверка и границы

Проверены новые unit-сценарии, полный guardrail/flow-набор и четыре реальных тела
запросов Claude Code через локальный LiteLLM/Analyzer с исходной ONNX CPU.
LLM/Redis в HTTP-стенде подставные: ответ LLM следует текущему mapping. Это
подтверждает доступность запроса и точность text/tool roundtrip, а не успешное
рассуждение реального агента, чтение чужого frontend-репозитория или полноту DLP.
После первых опытов получена конфигурация из 67 активных обратимых правил.
С ней прошли 364 codec-проверки всех правил и 8 повторов четырёх полных тел
запросов в stream/nonstream. В отправляемых payload не осталось совпадений
исходных словарных правил. Установка именно этой конфигурации на сервере
независимо не проверялась.

Дополнительная компонентная матрица содержит 513 development-записей
(511 уникальных пар текст/порог), три режима и 1539 точных восстановлений.
На 77 записях новые обозначения действительно меняют видимый Analyzer контекст.
Относительно обычных подмен не найдено новых открытых нужных позиций или лишних
масок. Новые положительные контроли охватывают все 30 типов в трёх формах:
значения закрыты, у Bearer открыта только публичная схема.

Разметка частичная: в прежних development-контролях остаются 25 open и 16 partial.
Это оценки по исходной разметке, не число подтверждённых производственных утечек;
границы и роль значений требуют отдельной проверки. В 8 из 68 новых сценариев
найдены маски, отмеченные исходной разметкой как лишние. После опыта уточнено,
что Goinvest — компания: её маскирование само по себе не обязательно лишнее,
но LOGIN — неверный тип; решение о словарной подмене оставлено отдельно.
Синтетические функции с этим именем не являются исходниками коллег.

Отсутствие новых потерь не означает полноту DLP. Веса и пороги NER, словарь,
кэш и общие исключения кода в этом изменении не менялись.

До включения требуются целевой стек, настоящий Redis/provider/агент, прогон
чтения, изменения файлов и сборки, latency/load и согласованное обновление workers.
