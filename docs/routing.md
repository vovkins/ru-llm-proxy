# Закрепление провайдера модели за клиентом

Когда за одним публичным именем модели стоят несколько аккаунтов или
провайдеров, LiteLLM старается направлять запросы одного клиентского ключа к
одному и тому же провайдеру. Это повышает вероятность повторного использования
кэша входных токенов.

Закрепление не отменяет балансировку и переключение при отказе. Недоступный
провайдер заменяется другим участником той же группы.

Этот механизм относится к моделям, которые LiteLLM обслуживает напрямую,
например к двум подпискам Z.AI. В экспериментальном профиле OpenAI LiteLLM видит
один внутренний адрес `codex-lb`, а выбор OAuth-подписки по диалогу и кэшу
выполняет сам `codex-lb`. Эти две привязки не дублируют друг друга.

## Настройка

В `litellm-config.yaml` включена проверка `deployment_affinity`:

```yaml
router_settings:
  redis_url: os.environ/REDIS_URL
  routing_strategy: simple-shuffle
  optional_pre_call_checks:
    - deployment_affinity
  deployment_affinity_ttl_seconds: 86400
```

| Параметр | Назначение |
| --- | --- |
| `redis_url` | Хранилище привязок |
| `deployment_affinity_ttl_seconds` | Время жизни привязки, сейчас 24 часа |
| `routing_strategy` | Выбор провайдера при отсутствии рабочей привязки |

LiteLLM использует `user_api_key_hash`, поэтому исходный клиентский ключ в Redis
не сохраняется.

## Порядок выбора

1. Клиент запрашивает публичную модель, например `glm-5.2`.
2. LiteLLM получает доступных провайдеров этой группы.
3. `deployment_affinity` ищет ранее сохранённый `model_info.id` по хэшу ключа.
4. Доступный закреплённый провайдер получает запрос.
5. Если привязки нет, она истекла или провайдер недоступен, маршрутизатор выбирает
   другого и сохраняет новую привязку.

Привязка по `metadata.session_id`, если её включить отдельно, имеет приоритет над
привязкой по ключу. В текущей конфигурации используется только ключ клиента.

Для моделей OpenAI из `litellm-config.codex-lb.yaml` значение
`deployment_affinity` закрепляет только внутренний маршрут к `codex-lb`.
Состояние конкретной OAuth-подписки хранится в PostgreSQL `codex-lb`, а не в
Redis проекта. Подробности: [codex-lb.md](codex-lb.md).

## Требования к моделям

Все провайдеры одной группы используют одинаковый `model_name` и разные
постоянные `model_info.id`:

```yaml
model_list:
  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_key: os.environ/ZAI_API_KEY
    model_info:
      id: glm-5-2-zai-coding-primary

  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_key: os.environ/ZAI_API_KEY_2
    model_info:
      id: glm-5-2-zai-coding-secondary
```

Не меняйте `model_info.id` без миграционной причины: старые привязки и ряды
метрик потеряют смысл. Тот же принцип применяется к внутреннему или другому
внешнему провайдеру. `glm-5.1` остаётся отдельным публичным именем.

## Проверка

```bash
make routing-smoke
```

Команда выполняет два запроса одним ключом и сравнивает
`x-litellm-model-id`. По умолчанию используется административный ключ; для
проверки реального потребителя задайте:

```env
LITELLM_ROUTING_TEST_KEY=sk-...
```

При единственном провайдере команда проверяет только путь маршрутизации и наличие
заголовка, но не само закрепление между несколькими вариантами.

Для экспериментального пула OpenAI дополнительно проверяйте запросы через
`gpt-5.6-luna`, журнал выбора учётной записи и распределение запросов в
административном интерфейсе `codex-lb`.

## Наблюдаемость

- `x-litellm-model-id` подходит для синтетической проверки и диагностики.
- Метрики `litellm_deployment_*` показывают нагрузку и ошибки по провайдерам.
- Redis нужно контролировать как зависимость маршрутизации и маскирования.
- Разным командам и приложениям выдавайте разные пользовательские ключи.

После обновления LiteLLM выполните `make health`, `make routing-smoke` и
`make monitor-smoke`. Полный регламент обновления: [monitoring.md](monitoring.md).
Переменные проверки: [configuration.md](configuration.md).
