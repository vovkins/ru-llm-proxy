# Маршрутизация провайдеров моделей и закрепление маршрута

Этот документ описывает, как `ru-llm-proxy` удерживает одного клиента на одном провайдере модели, когда за публичной моделью настроено несколько провайдеров или несколько аккаунтов одного провайдера.

Переменные окружения, которые используются в примерах маршрутизации и быстрых проверках, описаны в [configuration.md](configuration.md).

## Зачем это нужно

Многие LLM-провайдеры умеют кэшировать входные токены и префикс запроса на своей стороне. Если запросы одного клиента постоянно попадают на разные аккаунты или разные провайдеры моделей, эффективность такого кэша падает. Закрепление маршрута повышает шанс, что повторяющийся контекст одного клиента будет обрабатываться одним и тем же провайдером модели.

В проекте это не заменяет балансировку нагрузки и отказоустойчивое переключение. Это дополнительная проверка LiteLLM Router до вызова модели: если для клиентского ключа уже выбран доступный провайдер модели, LiteLLM отдаёт приоритет ему.

## Текущая настройка

Закрепление маршрута включено в `litellm-config.yaml` через `optional_pre_call_checks`:

```yaml
router_settings:
  redis_url: os.environ/REDIS_URL
  routing_strategy: simple-shuffle
  optional_pre_call_checks:
    - deployment_affinity
  deployment_affinity_ttl_seconds: 86400
```

Ключевые параметры:

| Параметр | Назначение |
| --- | --- |
| `redis_url` | Хранилище для сопоставления закрепления. Используется тот же Redis, что и для временных сопоставлений персональных данных. |
| `optional_pre_call_checks` | Включает проверку `deployment_affinity` до вызова модели. |
| `deployment_affinity_ttl_seconds` | Время жизни привязки клиентского ключа к провайдеру модели. Сейчас `86400` секунд. |
| `routing_strategy` | Базовая стратегия выбора провайдера модели, если закрепления ещё нет или закреплённый провайдер модели недоступен. |

## Как LiteLLM выбирает провайдера модели

LiteLLM Proxy добавляет в метаданные запроса хэш клиентского API-ключа: `user_api_key_hash`. Проверка `deployment_affinity` использует этот идентификатор, а не исходный токен.

Поток выбора:

1. Клиент вызывает публичную модель, например `glm-5.2`.
2. LiteLLM получает список доступных провайдеров моделей для этой группы моделей.
3. Проверка до вызова модели ищет в Redis идентификатор провайдера модели, ранее связанный с `user_api_key_hash`.
4. Если провайдер модели найден и сейчас доступен, LiteLLM выбирает его.
5. Если сопоставление отсутствует, устарело или провайдер модели недоступен, LiteLLM выбирает провайдера модели обычной стратегией маршрутизатора и сохраняет новую привязку.

Если в запросе когда-нибудь будет включена `session_affinity` с `metadata.session_id`, привязка к сессии имеет приоритет над привязкой к ключу. В текущем проекте включена именно привязка провайдера модели к ключу, потому что пользовательский токен LiteLLM естественно соответствует клиенту/потребителю прокси.

## Стабильные идентификаторы провайдеров моделей

Каждый провайдер модели должен иметь стабильный `model_info.id`. Этот идентификатор попадает в сопоставление закрепления, поэтому его нельзя менять без причины.

Текущая группа моделей по умолчанию:

```yaml
model_list:
  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_base: https://api.z.ai/api/coding/paas/v4
      api_key: os.environ/ZAI_API_KEY
    model_info:
      id: glm-5-2-zai-coding-primary
      base_model: glm-5.2

  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_base: https://api.z.ai/api/coding/paas/v4
      api_key: os.environ/ZAI_API_KEY_2
    model_info:
      id: glm-5-2-zai-coding-secondary
      base_model: glm-5.2
```

`model_name` — публичное имя, которое видит клиент. Несколько записей с одинаковым `model_name` образуют одну группу моделей. `model_info.id` — внутренний стабильный идентификатор провайдера модели.

`glm-5.1` остаётся дополнительным публичным именем для инсталляций, которым нужна предыдущая версия модели. Быстрые проверки и быстрый запуск по умолчанию используют `glm-5.2`.

## Два аккаунта Z.AI

Профиль запуска по умолчанию ожидает два ключа Z.AI Coding Plan:

```env
ZAI_API_KEY=...
ZAI_API_KEY_2=...
```

Обе переменные участвуют в группе моделей `glm-5.2` сразу после запуска. Если оператор меняет состав провайдеров моделей, правило остаётся тем же: один публичный `model_name`, разные учётные данные внешнего провайдера и разные стабильные `model_info.id`.

Пример:

```yaml
model_list:
  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_base: https://api.z.ai/api/coding/paas/v4
      api_key: os.environ/ZAI_API_KEY
    model_info:
      id: glm-5-2-zai-coding-primary
      base_model: glm-5.2

  - model_name: glm-5.2
    litellm_params:
      model: openai/glm-5.2
      api_base: https://api.z.ai/api/coding/paas/v4
      api_key: os.environ/ZAI_API_KEY_2
    model_info:
      id: glm-5-2-zai-coding-secondary
      base_model: glm-5.2
```

Для другого внешнего провайдера или внутреннего провайдера модели схема такая же: оставьте тот же публичный `model_name`, задайте провайдерские `litellm_params` и уникальный стабильный `model_info.id`.

## Проверка

Для быстрой проверки используйте:

```bash
make routing-smoke
```

Команда отправляет два запроса к живому сервису с одним и тем же ключом, проверяет HTTP-статус каждого ответа, читает заголовок ответа `x-litellm-model-id` и проверяет, что оба запроса попали к одному провайдеру модели.

Если LiteLLM недоступен, провайдер вернул `4xx/5xx` или прокси не вернул `x-litellm-model-id`, команда завершится с ненулевым кодом. При HTTP-ошибке она печатает статус и безопасные заголовки ответа, но не печатает токен прокси или полезную нагрузку запроса.

По умолчанию используется `LITELLM_MASTER_KEY`. Для более реалистичной проверки создайте пользовательский ключ в интерфейсе LiteLLM или через API, затем задайте его в `.env`:

```env
LITELLM_ROUTING_TEST_KEY=sk-...
```

После этого `make routing-smoke` будет использовать пользовательский ключ вместо административного ключа.

Если оператор временно оставил только одного провайдера модели, быстрая проверка тоже должна проходить, но она доказывает только работоспособность пути маршрутизации и наличие `x-litellm-model-id`. Конфигурация проекта по умолчанию рассчитана на двух провайдеров моделей, чтобы закрепление можно было проверять на реальной группе моделей с несколькими провайдерами.

## Наблюдаемость

Для диагностики маршрутизации:

- проверяйте заголовок ответа `x-litellm-model-id` на запросах к живому сервису;
- смотрите метрики провайдеров моделей LiteLLM в `/metrics`, особенно `litellm_deployment_*`;
- держите `model_info.id` стабильными, чтобы метрики и сопоставления закрепления не меняли смысл после перезапуска;
- используйте отдельные пользовательские ключи для разных команд/приложений, чтобы закрепление отражало реальных потребителей.

Redis хранит сопоставления закрепления отдельно от сопоставлений персональных данных. Время жизни сопоставлений персональных данных задаётся `PII_MAPPING_TTL_SECONDS`, время жизни закрепления маршрута — `deployment_affinity_ttl_seconds`.

## Обновления LiteLLM

`deployment_affinity` реализован в LiteLLM Router как дополнительная проверка до вызова модели. Если текущий образ не принимает `optional_pre_call_checks` или не возвращает `x-litellm-model-id`, обновите LiteLLM:

```bash
make update-litellm
```

После обновления проверьте:

```bash
make health
make guardrails-list
make routing-smoke
make monitor-smoke
```
