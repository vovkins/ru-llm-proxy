# Tiny2 через Triton и ONNX Runtime

Единая CPU-связка Tiny2/Triton — целевой механизм NER. Поставка модели и состав
единые, рабочий Analyzer использует только Triton, без резервного BERT-пути.
Владелец принял переход с [ограничениями качества](research/tiny2-quality-comparison.md);
это не гарантия полного распознавания или ёмкости 400 пользователей.

## Запуск

Сборка автоматически получает шесть файлов
[`Katerina-Bir/rubert-tiny2-secret-detection`](https://huggingface.co/Katerina-Bir/rubert-tiny2-secret-detection/tree/4137142e79d52b0b69370e0e3dceb2d6ad82591d)
на ревизии `4137142e79d52b0b69370e0e3dceb2d6ad82591d`.
Размеры и SHA-256 закреплены в `presidio/model_manifest.json`; ручного варианта
поставки и выбора модели нет. CA и прокси сборки сохраняются. Новых ключей LLM
для проверки экспорта не требуется.

```bash
make build
make setup STACK=litellm-presidio
make up STACK=litellm-presidio
make health STACK=litellm-presidio
```

Единый состав использует CPU FP32 и пакет из 4 окон. ONNX экспортируется во время сборки из
автоматически полученных и проверенных весов. Интернет во время работы модели не требуется.
Порты Triton не публикуются на хост; Analyzer обращается по внутренней сети.
GPU не используется. В functional один Triton с двумя исполнениями модели
и один процесс Analyzer. Ресурсы и число контейнеров production задаются
в общем файле топологии, а не отдельным профилем модели.

```bash
curl --fail http://localhost:5001/api/v1/health
curl --fail http://localhost:5001/api/v1/analyze \
  -H 'Content-Type: application/json' \
  -d '{"text":"password=pine-dawn727; postgresql://svc-a:1592@db","language":"ru","score_threshold":0.35}'
```

Текст в примере фиктивный. В рабочем процессе и журнале указан `triton`.
Nginx сразу запускается с полной конфигурацией. Пользовательский трафик на
время работ исключает оператор. Порядок проверки: каждый Triton, каждый
прогретый Analyzer, LiteLLM. Подробности: [развёртывание](deployment.md#tiny2).

## Контракт

- Исходные веса/токенизатор проверяются манифестом Tiny2.
- В Analyzer установлены только токенизатор, конфигурация и доверенное описание
  комплекта модели; правила Presidio и облегчённый spaCy сохраняются.
  PyTorch/Transformers и исходные вычислительные веса остаются в стадии
  экспорта, ONNX исполняется в Triton. Токенизация и декодирование Analyzer
  используют `tokenizers` и NumPy.
- Экспорт FP32/opset17 проверяется сравнением logits PyTorch/ONNX Runtime
  для пакетов 1/2/4/32, включая пустой текст, Unicode и 384 содержательных токена.
- Triton при старте проверяет SHA-256 ONNX. Analyzer сверяет source-model,
  tokenizer и label-contract SHA, precision, CPU instances, tensor shapes/types.
- Версия модели указана явно. Ожидаемый SHA-256 графа берётся из того же результата
  сборки (`/opt/ner-export/export-manifest.json`), не из первого ответа сервера.
  Описание содержит ревизию/хэши источников, вариант весов и версии средств экспорта.
- Окна содержат до 384 токенов с перекрытием 64. BIO-декодирование, поправка
  к классу O и обработка границ выполняются в Analyzer; поправка не меняет
  исходную оценку сущности. Дополнение до 386 позиций позволяет объединять окна.
- Triton объединяет пакеты: максимум 32, задержка формирования до 1 мс,
  по одному intra/inter-op потоку на исполнение ONNX Runtime.
- При недоступности либо неправильном ответе Triton — безопасный отказ.
  Автоматического перехода на PyTorch нет. После временного сетевого отказа
  Analyzer повторно проверяет тот же комплект и выполняет контрольное вычисление.
  Несовпадение модели или нарушение контракта фиксирует критическое состояние:
  автоматического возврата в готовность нет, требуется исправление и перезапуск.
- Backend включён в analysis signature; старый Redis-кэш не смешивается с новым.

Binary HTTP описан в [документации Triton](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/protocol/extension_binary_data.html).

## Отказы и ограничения

Один HTTPX-клиент на процесс использует пул размером `concurrency_limit + 1`:
рабочие вызовы ограничены параллельностью Analyzer, дополнительное соединение —
для единственной контрольной проверки. Готовность проверяется не чаще раза
в 2 с; после временного отказа повторная проверка возможна через 5 с.
Возврат в готовность требует проверки закреплённого комплекта и контрольного
вычисления; пользовательский POST автоматически не повторяется.
Переполнение очереди возвращает `503` и `Retry-After`, не ломая состояние модели.

Неполная сущность на границе окна сначала проверяется в смещённом окне.
Если этого недостаточно, существующая обработка границ может расширить находку
до полного значения, сохранив её класс, оценку и всё положительное покрытие.
В JSON это может означать маскирование строкового значения целиком, без кавычек
и изменения структуры. Если расширение не закрывает все спорные края,
возвращается `503 required_ner_unavailable` с
`failure_class=window_boundary_unresolved` только для текущего запроса;
готовность модели не сбрасывается. Отрицательный ответ повторного окна сам
по себе не удаляет первоначальную находку.

При пересечении с точным правилом NER сохраняет все неперекрытые части
уже принятой находки: слева, справа и между другими значениями. Класс и границы
точной находки не меняются. Приоритет — не потерять покрытие; подпись поля или
обычные слова, захваченные моделью вместе со значением, тоже могут оказаться
под маской. Это не отменяет фильтры классов, пороги и нормализацию границ строк.

Правило `RU_ADDRESS` присоединяет к подтверждённому ядру хвост `подъезд 2`
или `подъезд № 2` и следующую квартиру. Номер подъезда — 1–3 цифры;
перехода через строку, предложение или соседнее поле нет. Сокращения, этажи
и отдельное поле `entrance` этим расширением не обрабатываются.
Прежнее ложное срабатывание на `Адрес: Подъезд 2` сохранено по решению владельца:
неформальная грамматика может принять заглавное слово за название улицы.

Тип улицы может следовать за названием: `Фрунзенская набережная 24`,
`Малый Кисловский переулок 3`. Подпись `адрес` не обязательна. Для новой
формы номер проверяется целиком, а `24 метра`, `15 лет` или `3 человека`
не подтверждают дом. Существующие требования к регистру названия сохранены;
произвольные адреса строчными буквами этим исправлением не добавлены.
Если цепочка уже содержит несколько компонентов улицы, ещё один
неподтверждённый заглавный префикс слева не присоединяется. Это ограничивает
захват имени перед составным адресом, сохраняя сам город и адресную цепочку.

При явной подписи `адрес`, `адрес доставки/проживания/регистрации`, `address`
или `addr` с `:`/`=` допускается строчное название улицы:
`адрес: москва, проспект вернадского 30`. Тип улицы и проверенный номер дома
обязательны; оценка — 0.6. Новое правило ограничено тем же строковым значением,
одной строкой и 200 символами; город без `г.` требует запятой. Регистр исходных
данных и координаты не меняются, соседние поля не присоединяются.
Согласованная оговорка: в `Адрес: пожалуйста доставьте фрунзенская набережная 24`
маскируется всё значение после подписи, поскольку начало может выглядеть
как составное название улицы. Словарных исключений нет; обычный хвост после
завершённого адреса не присоединяется. Восстановление возвращает исходный текст.

Правило `EMAIL_ADDRESS` поддерживает латиницу и кириллицу в обеих частях адреса,
смешанные написания и домены `xn--`, включая последний компонент.
Например, `марина.кузнецова@inbox.ru` и `фёдор@пример.рф` скрываются целиком
без обязательной подписи «почта». Базовая оценка — 0.85; регистр, написание
и экранирование оригинала сохраняются для восстановления. Это распознавание
чувствительного значения, не проверка существования ящика или всех форм RFC;
новых настроек и сетевых проверок нет.

Guardrail передаёт оставшееся время через внутренний заголовок
`X-Ru-LLM-Analysis-Budget-Seconds` (положительное конечное число, до 86400 с).
Без заголовка Analyzer использует `PII_GUARDRAIL_ANALYZER_TIMEOUT_SECONDS`,
по умолчанию 240 с. Бюджет общий для очереди и всех пакетов; сетевой предел
одного вызова не становится пределом всего длинного документа.
Истечение бюджета не рекомендует слепую повторную попытку.

Ответы читаются с ограничением: конфигурация до 256 КиБ, ошибка до 8 КиБ,
готовность до 4 КиБ; тензоры — ровно ожидаемый размер плюс заголовок до 64 КиБ.
Сжатие и перенаправления не принимаются. После обнаруженной локальной отмены
новые пакеты не запускаются,
но текущая блокирующая операция завершается в пределах сетевых фаз. Прерывание
локального HTTP не гарантирует остановку уже принятого вычисления Triton.
`ru_presidio_triton_local_inflight` показывает локальные вызовы;
`ru_presidio_ner_ready` — последнее известное состояние готовности;
`ru_presidio_triton_unconfirmed_completions` — накопленное число вызовов
с неизвестным завершением на сервере, а не текущую удалённую параллельность.

Очередь Triton ограничена штатной политикой отказа: до 64 ожидающих запросов,
ожидание до 60 с; запрос может сократить ожидание оставшимся бюджетом
([политика очереди](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/batcher.md)).
Эта внутренняя очередь оставлена без изменений; она не заменяет очередь
пользовательских запросов Analyzer. Стандартные ресурсы и настройки по
измерениям Э10 приведены в [профилях запуска](deployment.md#стандартные-профили).

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PRESIDIO_ANALYZER_TRITON_TIMEOUT_SECONDS` | `60` | Таймаут вызова, максимум600с |
| `TRITON_REPLICAS` | `1` functional / `2` production | Контейнеры Triton, 1 или 2; переопределение только production.env/TOPOLOGY_ENV |
| `TRITON_MODEL_INSTANCES` | `2` | CPU-исполнения внутри каждого Triton, 1–32; в production тот же файл, в functional фиксировано два |

Количество процессов Analyzer задаёт существующая `PRESIDIO_ANALYZER_WORKERS`.
Это отдельный параметр, как очередь, параллельность и размер пакета окон.
Адрес `http://nginx:8000`, имя `tiny2`, версия `1` и алгоритм не настраиваются
через env. Описание модели и SHA графа для `make health` берутся из целевого
собранного образа, не из ответа первого сервера. Проверяется каждый экземпляр.
Старые настройки отклоняются до запуска ([миграция](configuration.md#переход-со-старой-конфигурации)).

## Откат

Возврат выполняется [предыдущим выпуском целиком](deployment.md#возврат-к-предыдущему-выпуску),
без резервного NER-профиля в новом комплекте. Доработки ветки пока не являются
окончательно принятой промышленной конфигурацией.

## Границы проверки

Подключение Triton не означает задержки около секунды или ёмкости 400 пользователей.
Текущие локальные [измерения](research/tiny2-capacity.md) и
[качество](research/tiny2-quality-comparison.md) оцениваются отдельно.
На целевом сервере нужны собственные измерения. При всплеске очередь ограничивает
число ожиданий, но не устраняет недостаток CPU. В стандартном Compose наш
ASGI-адаптер передаёт обнаруженное отключение в предварительную обработку:
ожидающий удаляется из очереди, активный анализ останавливается кооперативно.
Это не гарантирует своевременный сигнал от любого посредника или мгновенную
остановку уже принятого Triton вычисления.
